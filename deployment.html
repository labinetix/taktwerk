taktwerk

Deploying to devices

A bundle goes to a Linux device as a release named by its manifest’s hash. On the device, taktwerk agent verifies and activates releases under an install root and drives their systemd units; the host (taktwerk device, taktwerk deploy, the desktop app) calls it over SSH and copies files by SFTP.

taktwerk device add line-1 --host 192.168.1.20 --user taktwerk --privilege sudo
taktwerk device verify line-1                  # pins the host key, probes the device
taktwerk deploy plant --device line-1          # the plan
taktwerk deploy plant --device line-1 --yes
taktwerk device install-unit line-1 --yes      # once, through sudo
taktwerk device start line-1 plant --yes
taktwerk device tunnel line-1 plant            # http://127.0.0.1:<port>/ to the engine

The desktop app and taktwerk serve do the same from the workbench’s Devices page, on the same registry.

Bundle

A bundle is a folder with one or more project files, the model packages they use and optional companion processes, described by taktwerk-bundle.toml at its top:

name = "plant"                          # lowercase letters, digits, `_`, `-`; at most 64
projects = ["sim.toml", "closed-loop.toml"]  # the first is selected on a device's first activation
exclude = ["records", "campaigns"]      # left out, with everything below

[[companion]]                           # a process of its own, started and stopped with the engine
id = "bridge"
command = "bin/bridge"                  # relative to the bundle
args = ["--port", "9000"]
env = { LOG = "info" }

Every regular file below the folder belongs to the bundle, except hidden entries (a name starting with .) and what exclude names. A link to a file inside the folder is carried as that file; a link out of the folder, or to a directory, is refused. Project and command paths use letters, digits and ._/+- only.

A bundle is checked per target architecture (aarch64, x86_64, arm): every project file parses, every model package it references lies inside the bundle (no path escapes it) and has a library for the architecture (lib/<arch>/ of a raw package, binaries/<platform>/ of an FMU, packed or extracted), and every companion’s command is in the bundle.

Manifest

The manifest lists the bundle, the taktwerk version that runs it, the architecture and every file with its size and sha256. Its canonical form is one line of JSON, keys in this order, files sorted by path:

{"format":1,"bundle":"plant","taktwerk":"0.8.1","arch":"aarch64","files":[{"path":"bin/bridge","size":1024,"sha256":"…","exec":true}]}

exec marks a companion’s command, installed executable. The sha256 of these bytes, in lowercase hex, names the release. The agent refuses a manifest that is not canonical, whose hash is not the release’s name, or whose paths leave the bundle.

Device layout

<root>/bin/taktwerk-<version>                    engine binaries
<root>/bundles/<name>/staging/<hash>/            an upload: the files, and .taktwerk/manifest.json
<root>/bundles/<name>/releases/<hash>/           activated releases
<root>/bundles/<name>/releases/<hash>/.taktwerk/  manifest.json, engine -> bin/taktwerk-<version>
<root>/bundles/<name>/current -> releases/<hash>
<root>/bundles/<name>/history                    activated releases, oldest first
<root>/bundles/<name>/records/                   the engine's file recorders
<root>/bundles/<name>/env                        selected project, http address, secrets (0600)

The first activation creates env; later deploys leave it alone, and the device owner adds secrets (for password_env) and RUST_LOG there:

TAKTWERK_PROJECT=sim.toml              relative to the release
TAKTWERK_HTTP=127.0.0.1:8480           a loopback port per bundle, from 8480 up
TAKTWERK_HTTP_TOKEN=<64 hex digits>    the http connector's write token

Units

agent install-unit writes one template unit, taktwerk@.service; the instance is the bundle’s name. It runs as the owner of the install root (or --user), reads env, and starts in current:

ExecStart=<root>/bundles/%i/current/.taktwerk/engine run ${TAKTWERK_PROJECT} --http ${TAKTWERK_HTTP} --http-writes --record-dir <root>/bundles/%i/records
Restart=on-failure
LimitRTPRIO=90
LimitMEMLOCK=infinity

The release’s engine link picks the taktwerk version, so the binary switches with current. The engine serves its http connector on loopback only (the binary needs the http feature); a host reaches it through an SSH port forward. A companion is its own unit, taktwerk-<bundle>.<id>.service, with PartOf= and After= the engine’s; a drop-in taktwerk@<bundle>.service.d/companions.conf makes the engine’s unit want it. Rerun install-unit after a release changes its companions.

Agent

taktwerk agent <command> --root <dir> [--yes]

Every command prints one JSON document on stdout:

{"agent_api":1,"command":"activate","ok":true,"bundle":"plant","release":"…","applied":false,"plan":["…"]}
{"agent_api":1,"command":"activate","ok":false,"error":{"code":"unit-running","message":"…"}}

A failure exits 1, a usage error 2. Error codes: usage, invalid, not-found, unit-running, verify-failed, arch-mismatch, ci-refused, no-systemd, systemd, io. Mutating commands print their plan and change nothing without --yes; --yes is refused when CI is set.

commandchangeswhat
infoarchitecture, glibc, os-release, systemd, free bytes under the root, engines in bin/, bundles
status [<bundle>]releases, staged uploads, active release, selected and available projects, http address, unit states
manifest <bundle> [<hash>]the active (or named) release’s manifest
activate <bundle> <hash>yesverify staging/<hash> against its manifest, move it to releases/<hash>, link its engine, create env if missing, switch current by one rename
rollback <bundle>yesswitch back to the release activated before the active one
start <bundle> [--project <file>]yesselect a project of the active release, then start the unit
stop, restart, enable, disable <bundle>yesthe engine unit; companions follow it
logs <bundle> [--lines N]journal lines of the engine and its companions
gc <bundle> [--keep N]yesremove releases but the active one and the N (2) activated last before it, and staged uploads
install-unit [--user U] [--unit-dir D]yeswrite the template, companion units and drop-ins, remove stale ones, reload systemd; needs root

activate and rollback refuse while the bundle’s unit runs. activate refuses a release for another architecture and reports, as problems, missing, changed or extra files, a missing bin/taktwerk-<version> and a running unit; a dry run says ready when there are none. Files an upload leaves out that the active release holds unchanged are taken from it, so a host sends only what changed.

Devices

The host keeps its devices in devices.toml in the user’s config dir (~/.config/taktwerk/ on Linux, %APPDATA%\taktwerk\ on Windows, TAKTWERK_CONFIG_DIR overrides): how to reach each one, its pinned host key and what the last verify found. No passwords.

[[device]]
name = "line-1"
host = "192.168.1.20"
port = 22
user = "taktwerk"          # logs in, owns the install root
privilege = "sudo"         # how unit changes get root: none, sudo or su
root = "/opt/taktwerk"     # the install root (default)
host_key = "SHA256:…"      # pinned by the first verify

[device.verified]          # the last verify: written by verify, read by the app
arch = "aarch64"
glibc = "2.36"
systemd = true
engines = ["0.8.1"]
# also: at, machine, free_bytes, root_exists, root_writable, taktwerk, bundles, problems, notes

Login. An SSH agent’s identities (SSH_AUTH_SOCK; on Windows the OpenSSH agent’s pipe), then key files (-i, else ~/.ssh/id_ed25519, id_ecdsa, id_rsa), then a password asked for on the terminal. Nothing is stored.

Host keys. The first verify shows the device’s host key fingerprint and pins it after a yes on the terminal, or when --accept-host-key <fingerprint> names it. Every later connection refuses any other key. When a device was reinstalled, check its new key and pin it with verify --accept-host-key.

Privilege. Only unit changes need root: start, stop, restart, enable, disable and install-unit with --yes run the agent through the device’s method, and so does creating a missing install root the login user cannot create. sudo runs with -S and asks for the login user’s password only when sudo does; su runs on a PTY and asks for root’s. Everything else runs as the login user, who should own the install root. Reading the journal (logs) needs the login user in the systemd-journal group.

Verify probes over one SSH exec: uname -m, the glibc version against the engines’ floor (2.25), systemd, whether the root exists and is writable, free space under it, installed engines and /etc/os-release; then agent info when an engine is installed. Problems (an unsupported architecture, no or too old glibc, a root the login user cannot use) stop a deploy; notes (no systemd, a root the deploy will create) do not.

Scan connects to the SSH port of every address of an IPv4 subnet (at most a /16, 64 at a time, 500 ms each) and lists the hosts that answer, with their banner. It never logs in.

Deploying a release

taktwerk deploy <bundle> --device <name> probes the device, checks the bundle for its architecture, builds the manifest for this taktwerk version, reads the active release’s manifest and the unit’s state, and prints the plan: the engine to install, the files to send (those the active release lacks or holds with other content), bytes against free space, and what stands in the way. A running unit is a problem: stop it first. With --yes:

  1. Create the install root if it is missing (through root when the login user cannot).
  2. If bin/taktwerk-<version> is missing: upload the engine under a temporary name, make it executable, run it with --version and refuse it unless it reports this host’s version, then rename it.
  3. Upload the changed files to bundles/<name>/staging/<hash>/ and the manifest’s canonical bytes to .taktwerk/manifest.json there.
  4. agent activate <bundle> <hash> --yes: the device takes the files the upload left out from the active release, verifies everything and switches current.

Then, on the first deploy and when companions change, device install-unit --yes, and device start <bundle> --yes, device enable <bundle> --yes to start at boot.

The engine comes from --engine <file>, else from a directory of per-architecture engines (TAKTWERK_ENGINES, which the desktop app sets to its bundled engines/), laid out as the release builds them: x86_64-linux-gnu/taktwerk, aarch64-linux-gnu/taktwerk, armv7-linux-gnueabihf/taktwerk. A Linux taktwerk deploying to its own architecture can send itself; it must have the http feature for the unit’s --http. The released device engines are built without the host side (feature host: SSH, SFTP, device, deploy), which the agent does not need.

Live view

taktwerk device tunnel <device> <bundle> reads the bundle’s http address from its env file (through agent status), listens on a local port (--local, default any free loopback port) and forwards each connection over SSH to that address on the device; it prints the URL and runs until Ctrl-C. The write token stays on the device unless --token puts it in the URL. The workbench forwards the same way and adds the token itself.
