taktwerk

taktwerk

taktwerk runs compiled models at a fixed step on Linux, beside or on a PLC, and exchanges their signals with PLCs, plant data systems and operators over OPC UA and HTTP.

  • Models are FMI 3 or FMI 2 co-simulation FMUs, or plain C libraries described by a small descriptor. A model is size-generic; an instance binds its sizes.
  • The engine owns a process image. A real-time thread steps every model on absolute deadlines and reads a snapshot of the image at each tick; connectors sync the image with the outside in the background.
  • An own OPC UA server exposes every signal, the engine status and a heartbeat, so any OPC UA client doubles as a UI. taktwerk tui is one.
  • One TOML project file per engine describes models, instances, wiring and connectors.

What it is not

  • Not hard real time: a fixed step on stock Linux, with optional SCHED_FIFO, CPU pinning and locked memory. Jitter is measured on the target, never assumed.
  • Not a safety controller: models run in the engine’s process. Whoever consumes the outputs, typically the PLC, owns the safe state once the heartbeat stops (see Concepts).

Architecture

taktwerk is a runtime: it loads compiled model packages, steps them at a fixed period, and exchanges their signals with the systems around them. It knows no equations and no plant; a model package brings the computation, a project file says where it runs and what it connects to.

Where it sits

  PI -- "recorder" --> REC[run records]
  • The PLC owns the plant’s I/O, its interlocks and the safe state. taktwerk runs beside it (on an edge PC) or on it (a Linux-based PLC) and hosts what a PLC program does not hold well: a model, an estimator, a controller compiled from C or exported as an FMU. The PLC reads the engine’s outputs, watches its heartbeat and falls back to its safe state when the heartbeat stops (see the safety contract).
  • A plant data system (a historian, a batch or lab system with a JSON API) holds measurements that do not come through the PLC and takes values back. The rest connector reads and writes it on fixed paths; what its API needs beyond that runs as a companion process next to the engine (Boundary).
  • Operators and tools see every signal on the engine’s own OPC UA server and, with the http connector, in the workbench and through taktwerk engine.

The engine

  PI <--> RS
  PI <--> SV
  PI --> HT

  RR --> PU[OPC UA pull: taktwerk record]
  • Process image. One typed, preallocated buffer per signal. Connectors write inputs and tunables and read outputs from their own threads; the cycle thread copies what it needs at its tick and stores outputs back. Nothing on the cycle path allocates, does I/O or waits for a connector. See Execution model.
  • Instances. A model package is size-generic; an instance binds its dimensions, sets its parameters, maps its variables to signals and picks its period. Instances exchange data only through the image: an input mapped to another instance’s output is wired to it.
  • Connectors sync part of the image with the outside: the engine’s own OPC UA server, an OPC UA client (to a PLC), a REST client (to a plant data system) and an HTTP API. Each is checked against the plan at init and fails closed. See Connectors.
  • Write gate. A client connector may hold its outputs while something is wrong: the engine not running, the heartbeat not advancing, a status bit set, a value out of range. The target keeps its last values; heartbeat and status still go out. See Write gate.
  • Recorder. The cycle thread copies selected values into a ring per recorder; a file sink writes run files from it, taktwerk record pulls it over OPC UA from another host. Nothing a sink does slows the cycle. See Recording and the run record format.
  • Event log. Start, stop, tunable changes, refused writes, stale inputs, gate changes and scenario events, with the cycle they apply at, in events.csv of every record.

Simulation and real time

The same engine runs a project in real time on a controller and as a simulation on a workstation: --speed max --no-connectors runs the same ticks unpaced, on engine time, so the same inputs give the same rows. Scenarios script events into a run, campaigns run a project many times with other parameters and seeds. See Simulation runs and Campaigns.

Execution model

Process image

The engine owns one value per signal, the process image. Every value lives in a typed buffer sized at init and never resized. Connectors write inputs and tunables and read outputs from their own threads; the cycle thread copies what it needs at its tick and stores outputs back. Each signal is locked only for one copy.

A signal has a direction:

directionwritten byread by
inputa connectorthe instances that consume it
outputthe instance that produces itconnectors, other instances
tunablea connector, while runningone instance, before its step
systemthe engineconnectors

Element types are f64, f32, i64, i32, i16, i8, u64, u32, u16, u8 and bool. A signal is a scalar or an array of any rank; matrices are stored row-major or column-major as the model declares.

Ticks and periods

One real-time thread wakes on an absolute deadline grid (clock_nanosleep with TIMER_ABSTIME) every engine.tick_ms. Each instance has a period of every ticks and is due at every tick whose number is a multiple of every, so all instances are due at tick 0.

Per tick:

  1. The external inputs and tunables of every due instance are copied from the image.
  2. If any of those inputs is stale, the tick is skipped (see stale inputs).
  3. Otherwise the due instances step in declared order. Each first copies its wired inputs, so it sees outputs stored earlier in the same tick.
  4. Outputs are stored, the heartbeat advances and the tick is published: connectors now see a complete, consistent set of outputs.

Model time is start_time + tick × tick_ms; an instance advances by its step size every × tick_ms per step. A tick that ends after the next deadline skips the missed slots and counts each in overruns; the tick counter stays contiguous, so after an overrun model time lags wall time by the skipped slots. Nothing on the tick path allocates.

taktwerk run --speed runs the same ticks faster than real time or unpaced, on engine time instead of the wall clock; see Simulation runs.

Instances and dimensions

A model is size-generic: its variables have symbolic shapes (u: f64[n], A: f64[nx, nx]) over named dimensions with an optional min, max and default. An instance references a model and binds every dimension, from the project file, from the model’s default, or "from-server" (the length a connector finds outside). The bound sizes are structural: they are fixed for the run, and a change needs a restart.

One model serves any number of instances. Whether one loaded library can host several is the model’s instances capability: multiple libraries keep their state per instance; for a single library (state in globals), each further instance loads a private copy of the file.

Parameters are set once before init. Tunables are set before init and change while running; a changed value is delivered before the instance’s next step. A tunable that no connector has written yet shows the model’s own start value after init, so writing one tunable never zeroes another.

Signals and wiring

An unmapped input, output or tunable v of instance i is the signal i.v. Mapping a variable in the project file names its signal:

  • An input mapped to a signal that some instance outputs is wired to it. It reads what the producer stored last: the same tick when the producer runs earlier in declared order, else the previous one. A wired input never goes stale.
  • An input nobody outputs is an external input, written by a connector.
  • Several instances may consume one signal.
  • A one-dimensional input may be composed element by element from scalar signals and elements of other instances’ outputs, each element wired or external as above; its value is the read-only signal i.v. A scalar input may take one element, x = "j.y[2]", the same way. See Project file.

Errors at init: two outputs on one signal, a tunable on an input or output signal, one signal used with two types, shapes or layouts, a mapping onto one of the engine’s own signals, or a signal name with [ or ] that is no element of another instance’s output.

Init

Before the first tick every instance is initialised once, in declared order. Its init sees its dimension lengths and parameters, its tunables as the image holds them (a connector’s write, else the start value), and its inputs as follows:

  • A wired input whose producer comes earlier in declared order holds the producer’s output as it stood after the producer’s init, so a library may seed its state from it.
  • A wired input whose producer comes later (a feedback loop) is zero.
  • An external input holds what a connector has written so far; if nothing yet, the model’s declared start, else zero. No first read is awaited and no age limit is checked at init.
  • The elements of a composed input follow the same rules, element by element.

Outputs written by an init are not stored in the image: connectors and other instances see outputs from tick 0 on, and every wired input is copied again before each step.

Stale inputs

Each external input may carry a maximum age, max_age_ms on the binding or engine.input_max_age_ms for all. Without one, an input never goes stale. With one, an input is stale when its last write is older than that at the tick, or when it was never written.

A stale input skips the whole tick: no instance steps, outputs and heartbeat are held, status becomes faulted and stale counts the tick. The fault is published at once. When inputs are fresh again the next tick runs normally and status returns to running.

Skipped ticks are not stepped later. The next step’s time is that tick’s engine time, so a model learns the gap from time (or from taktwerk.stale); one that counts its own steps instead of reading time falls behind by the skipped ticks. An FMU’s communication points stay contiguous: its next step starts where its last ended and covers the gap, as one longer step when it declares canHandleVariableCommunicationStepSize, else as steps of its step size, all with the inputs of the tick that resumes.

An OPC UA client connector that loses its server stops writing its inputs, so they age and the engine turns them stale.

Heartbeat, status and the safety contract

The engine publishes its own signals under engine.system_prefix (default taktwerk):

signaltypemeaning
taktwerk.heartbeatu64advances once per tick whose outputs were published
taktwerk.statusi320 init, 1 running, 2 faulted, 3 stopped, 4 degraded
taktwerk.cycleu64every tick, skipped ones included
taktwerk.overrunsu64deadline slots missed
taktwerk.staleu64ticks skipped for a stale input

Models run inside the engine’s process; there is no process isolation. Whoever consumes the outputs, typically the PLC, owns the safe state. It watches the heartbeat (map it to a PLC node with the OPC UA client) and falls back to its safe state when the heartbeat stops advancing or status is not 1. The heartbeat advances only on a tick whose outputs were published, so a held heartbeat means the outputs are not current.

Faults

By default a model error (a non-success return code, or a failed init) terminates every instance and ends the run with that error (fail-stop); taktwerk run exits non-zero. A connector that fails beyond its own reconnect logic stops the run the same way. Restart is the service manager’s job (see Running in production).

An instance may survive its own failed step instead (on_error in the project file):

  • hold: its last published outputs stay; safe: its declared safe values are published. The other instances keep stepping.
  • While an instance is down, status is 4 (degraded) and the heartbeat holds, so a consumer that watches it sees that not every output is its model’s. Recorded rows show the held or safe values.
  • Its health is published under taktwerk.instance.<id>.: state (i32: 0 running, 1 held, 2 safe, 3 re-initialising), faults (u64, failed steps and re-inits), code (i64, the last return code).
  • Re-init: after reinit_after_s of engine time (doubling after each failed attempt, up to 64 times), or when anything writes the tunable taktwerk.instance.<id>.reinit, the engine creates the instance again off the cycle thread and initialises it at the next tick it is due, with that tick’s inputs and the tunables in force; it steps from the tick after. Its outputs stay held or safe until that init succeeds. A re-init’s init runs on the cycle thread, as at the start, and may make that tick late.

Installing the CLI

taktwerk runs on Linux: x86_64, aarch64 and 32-bit hard-float ARM (armv7). One binary, taktwerk, is the engine, the CLI, the TUI, the device agent and, in a build with the http feature, the workbench backend.

From crates.io

With a Rust toolchain (1.89 or newer):

cargo install --locked taktwerk                  # engine, CLI, TUI, devices (SSH)
cargo install --locked taktwerk --features http  # also the rest and http connectors, `engine`, `serve`
cargo install --locked taktwerk --features ui    # also the web UI that `serve` and `--http` show

From a checkout: cargo install --locked --path crates/taktwerk with the same features. The examples need a C compiler.

Release archives

Each release carries the CLI per architecture and a SHA256SUMS file:

  • taktwerk-<version>-x86_64-linux-gnu.tar.gz
  • taktwerk-<version>-aarch64-linux-gnu.tar.gz
  • taktwerk-<version>-armv7-linux-gnueabihf.tar.gz

They hold the device engine: built with http and without host (no device, deploy), no web UI, linked against glibc 2.25 so one binary runs on older systems too. An archive holds taktwerk, the systemd unit taktwerk.service, the examples with their libraries built for that architecture (a bundle, examples/taktwerk-bundle.toml), the README and the licenses.

sha256sum -c --ignore-missing SHA256SUMS
tar xzf taktwerk-<version>-aarch64-linux-gnu.tar.gz
cd taktwerk-<version>-aarch64-linux-gnu
./taktwerk run examples/raw-pi/project.toml

The host side and the web UI come with the workbench or a build with host and ui.

Cross-building

Build on a development machine for the target with cargo-zigbuild, which links against an older glibc than the host’s so one binary runs on older target systems:

cargo install --locked cargo-zigbuild      # also needs `zig` on the PATH
rustup target add aarch64-unknown-linux-gnu x86_64-unknown-linux-gnu armv7-unknown-linux-gnueabihf

# The suffix after the target is the glibc version to link against: the oldest your targets run.
cargo zigbuild --release -p taktwerk --target aarch64-unknown-linux-gnu.<glibc>
cargo zigbuild --release -p taktwerk --target x86_64-unknown-linux-gnu.<glibc>
cargo zigbuild --release -p taktwerk --target armv7-unknown-linux-gnueabihf.<glibc>

The binaries land in target/<target>/release/taktwerk. taktwerk has no native dependencies beyond libc; its OPC UA security is pure Rust. The release archives are built this way with --no-default-features --features http and glibc 2.25 (.github/workflows/engine.yml).

Model libraries are separate files and must run on the target too: build raw libraries per architecture into lib/aarch64/, lib/x86_64/ and lib/arm/ (zig cc -target aarch64-linux-gnu.<glibc> or arm-linux-gnueabihf.<glibc> works for C), and ship FMUs with a binary for the target platform (see FMI 3). The examples’ build.sh take the compiler and the architecture from CC and ARCH:

CC="zig cc -target arm-linux-gnueabihf.<glibc>" ARCH=arm sh examples/raw-pi/build.sh

Installing the workbench

The workbench is the web UI of taktwerk serve over a project folder and its devices. It comes as a desktop app for Linux and Windows, or in a CLI build with the ui feature (cargo install --locked taktwerk --features ui, see Installing the CLI), opened in a browser. What it does: Workbench.

Desktop app

Each taktwerk release carries the installers, of the release’s version:

fileplatform
taktwerk-workbench_<v>_x64-setup.exeWindows x86_64, per-user installer (NSIS)
taktwerk-workbench_<v>_x64_en-US.msiWindows x86_64, machine-wide installer (MSI)

Each installer carries its own taktwerk and the Linux device engines of the same version (x86_64, aarch64, armv7), which serve deploys, so a device can be deployed to without internet. SHA256SUMS lists every file of the release.

The installers are not signed. On Windows, SmartScreen stops the first start of the installer with “Windows protected your PC”: check the file against SHA256SUMS (Get-FileHash <file> in PowerShell), then More info → Run anyway. The app needs WebView2, which Windows 10 and 11 include; the installers fetch it when it is missing.

On Linux the app runs projects locally and deploys to devices. On Windows taktwerk loads no models itself: local runs and checks go to a WSL2 distribution of the PC (Local runs on Windows), and engines run on Linux devices, which a WSL2 distribution can be too. Without WSL2 the app shows the folder’s files, records, campaign results and devices, a project’s plan lists each model as not loaded, and no local run starts.

Local runs on Windows

The app runs the folder’s projects in a WSL2 distribution with the Linux engine it carries, so nothing is ported and no admin rights, SSH server or password are needed. Once, in PowerShell:

wsl --install            # WSL2 and Ubuntu; skip when `wsl -l -v` lists a version 2 distribution

Start the distribution once from the Start menu to create its user, then (re)start the app. Runs names the distribution and starts runs there: the app copies its engine to ~/.cache/taktwerk/ in the distribution, runs it in the folder as WSL sees it (C:\… is /mnt/c/…), and the Live screen reaches the run’s API through wsl.exe. Records land in the Windows folder. The distribution is the default WSL2 one, or the first WSL device of the registry (TAKTWERK_WSL_DISTRO overrides). The folder must be on a local drive or inside the distribution (\\wsl.localhost\<distro>\…), not on a network share.

A device to try

Any Linux machine with SSH and glibc 2.25 or newer serves as a device: a single-board computer on the desk, a PC, or WSL2 on the Windows machine itself. systemd supervises the bundles where it runs, taktwerk’s own supervisor elsewhere (Without systemd). The release archive of the device’s architecture carries examples/ as a bundle with its libraries built:

# on the Windows PC, PowerShell
cd $HOME\Documents
mkdir taktwerk; cd taktwerk
tar -xzf $HOME\Downloads\taktwerk-<v>-aarch64-linux-gnu.tar.gz

On the device, once, as a user with sudo (the login user owns the install root):

sudo install -d -o "$USER" /opt/taktwerk

Then in the app: Devices → add the device (address, login user, privilege sudo) → Verify and compare the fingerprint with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the device → deploy the bundle examples → Install unit → Start → Live: write ctrl.sp and watch plant.level_m follow → Stop → Sync records → Records: the run from the device.

WSL2 as a device

On Windows, Devices lists the PC’s WSL2 distributions under This PC (WSL): Add as device → Verify (no host key: the distribution is this PC) → deploy, install the unit, start, Live and sync records as for any device. Take the x86_64-linux-gnu archive for the bundle. Commands run through wsl.exe, root through wsl -u root (WSL2 distributions). Units need systemd in the distribution ([boot] systemd=true in /etc/wsl.conf), else taktwerk’s own supervisor runs the bundle. The app keeps the distribution running while it is open; for engines that keep running after it closes, add to %UserProfile%\.wslconfig:

[general]
instanceIdleTimeout=-1

Getting started

Install taktwerk first: the CLI (cargo install --locked taktwerk, or a release archive) and, for the web UI, the workbench.

A project in four commands

taktwerk inspect plant.fmu --kind fmi           # dimensions, variables, shapes
taktwerk new plant.fmu --kind fmi -o plant.toml # scaffold a project file
taktwerk check plant.toml                       # load, resolve, check; print the plan
taktwerk run plant.toml                         # until SIGINT, SIGTERM or SIGHUP

new writes a project with one instance, every dimension at the model’s default, every input, output and tunable mapped to its default signal name, commented-out parameters, and an OPC UA server on opc.tcp://127.0.0.1:4840. Edit it, then check it: check loads every model, binds every dimension, resolves every signal and checks every connector’s mapping against the plan, contacting nothing; check --live also verifies every mapped node on the servers the project connects to. It prints the plan:

tick 10 ms

  instance  model    period  dims
  filt      lowpass  10 ms   n=3

  signal              direction  type  shape   max age
  taktwerk.heartbeat  system     u64   scalar  -
  taktwerk.status     system     i32   scalar  -
  taktwerk.cycle      system     u64   scalar  -
  taktwerk.overruns   system     u64   scalar  -
  taktwerk.stale      system     u64   scalar  -
  filt.y              output     f64   [3]     -
  filt.u              input      f64   [3]     -
  filt.gain           tunable    f64   scalar  -

ok: 1 instance(s), 8 signal(s), 1 connector(s) checked (nothing contacted; `--live` verifies the endpoints)

run logs to stderr (RUST_LOG filters, default info), stops on SIGINT, SIGTERM or SIGHUP, prints a run summary and exits non-zero when a model or connector failed.

Watch and edit with the TUI

taktwerk tui opc.tcp://127.0.0.1:4840

The TUI is an OPC UA client of the engine’s own server. It shows status, heartbeat and counters, and every signal with its value and age. Keys: ↑/↓ or j/k select, PgUp/PgDn, Home/End (g/G) jump, Enter edits the selected input or tunable and Enter again writes it, Esc cancels, q quits. If the project changes namespace or system_prefix, pass --namespace and --prefix.

Tutorial: from a package to a running device

A model package arrives, from a modelling tool or as an FMU from any FMI tool. This tutorial takes one through its whole life: inspected and simulated on a workstation, tested with a fault and a small campaign, bundled, deployed to an edge device, connected to a PLC and a plant data system, and operated there. Every step ends in commands to run and a result to check.

flowchart LR
  P[package] --> S[project, check]
  S --> W[workbench: run, scenario, campaign]
  W --> B[bundle]
  B --> D[edge device]
  D <--> PL[PLC, plant data system]

The example is examples/plant-loop, a level loop: a PI controller drives a tank’s pump through a plant data system’s JSON API, from the level that system measures; the set point and an interlock come from a PLC, which also mirrors the loop and lets an operator tune the gains. A supervisor model turns the interlock and an implausible level into status bits that hold the writes. For the steps before the plant, a tank model stands in for it; for the plant, the example carries stand-ins of the PLC and the plant data system.

What you need

  • A Linux shell on the workstation (on Windows, WSL2) with a C compiler, python3, curl and uv, and a checkout of the taktwerk repository.
  • taktwerk with the workbench: the desktop app’s own taktwerk on Linux (Installing the workbench), or a build from the checkout, cargo install --locked --path crates/taktwerk --features ui.
  • For steps 5 and 7, a device: any Linux machine with SSH and glibc 2.25 or newer, such as a single-board computer, a VM or WSL2; a login user with sudo, and python3 for the stand-in plant data system.

Every command on this page runs in CI: examples/plant-loop/tutorial.sh runs them in order, headless, and checks each result; the device steps run against the CI machine itself over SSH.

1. The package

A package is a C library with its descriptor (taktwerk-model.toml and lib/<arch>/), or an FMU. Here build.sh builds them from the repository’s C sources: the PI of raw-pi and a tank model into packages/, as a modelling tool releases a package, and in place the example’s supervisor and the stand-in PLC.

cd examples/plant-loop
sh build.sh
taktwerk inspect --kind raw packages/pi

  n          1    -    1

  variable  causality  type  shape   unit  description
  kp        tunable    f64   scalar  -     proportional gain

That is what a project binds: the dimension n, the tunables, the inputs and the output. An FMU is inspected the same way with --kind fmi; what makes a package is in Making a model taktwerk-compatible. new prints a project for one package to start from, one instance with a signal per variable and an OPC UA server:

taktwerk new --kind raw packages/pi
taktwerk inspect --kind raw packages/tank

sim.toml is such a project grown to the loop, with no connector: the PI as ctrl, the supervisor as sup and the tank as plant, the PI reading the tank’s measured level and driving its pump. The PLC’s set point and interlock are external inputs, zero until something sets them.

# The level loop of `project.toml` on a simulated plant, with no connector: the tank of
# `packages/tank` in place of the plant data system, so the PI reads the tank's measured level
# and drives its pump. The PLC's set point and interlock stay external inputs, zero until
# something sets them: an override, a scenario event, the workbench. Build first (`build.sh`),
# then from this folder:
#   taktwerk run sim.toml --speed max --until-time 600 --set plc.level_sp=1.0

[engine]
tick_ms = 100.0

[models.pi]
kind = "raw"
path = "packages/pi"

[models.supervisor]
kind = "raw"
path = "supervisor"

[models.tank]
kind = "raw"
path = "packages/tank"

# The tank runs first: the PI and the supervisor read the level it measured this tick, and it
# takes the pump flow the PI asked for at the previous one.
[[instance]]
id = "plant"
model = "tank"
parameters = { area = 10.0, k_out = 0.5, q_max = 1.5, level0 = 0.5, noise_sd = 0.002, seed = 1 }
inputs = { q_set = "ctrl.u[0]" }

[[instance]]
id = "ctrl"
model = "pi"
dims = { n = 1 }
parameters = { kp = 1.0, ki = 0.1 }
inputs = { sp = ["plc.level_sp"], pv = ["plant.level_m"] }

[[instance]]
id = "sup"
model = "supervisor"
parameters = { level_lo = 0.05, level_hi = 2.0 }
inputs = { interlock = "plc.interlock", level = "plant.level_m" }

[[recorder]]
id = "main"
signals = ["@io"]

taktwerk check sim.toml

check loads every model, resolves the wiring and prints the plan: the instances, every signal with its direction and type, the composed inputs (ctrl.pv from plant.level_m, plant.q_set from ctrl.u[0]) and the recorder. It ends in ok: 3 instance(s), 25 signal(s), 0 connector(s) checked.

taktwerk serve .

Open the URL it prints. In Runs, pick sim.toml, add the override plc.level_sp=1.0 and start it at speed 1. 4. The bundle

A device runs a bundle: this folder, with its projects and the packages they use.

# The level loop as a bundle for a device, three projects: the simulated plant (selected on the
# first activation), the loop on the plant as a dry run, and the closed loop.
#   taktwerk deploy . --device edge
name = "plant-loop"
projects = ["sim.toml", "project.toml", "closed-loop.toml"]
exclude = ["records", "out", "stand-in", "tutorial.sh"]
  • sim.toml, the simulated plant, comes first: a device’s first activation selects it.
  • project.toml is the loop on the plant with both connectors in dry run: they read and log what they would write.
  • closed-loop.toml is project.toml with writes on. A device runs a project as it is, with no --write, so the closed loop is a project of its own.
grep -n '^writes' project.toml closed-loop.toml

6. A PLC and a plant data system

project.toml replaces the tank with the plant: the rest connector lab reads the level from a plant data system and writes the pump set point and a watchdog; the opcua-client connector plc reads the set point and the interlock from a PLC and mirrors the loop into its program.

# A level loop on a plant, taktwerk alone: the PI of `packages/pi` drives the pump through a
# plant data system's REST API, from the level that system measures, with the set point and an
# interlock from a PLC, which also mirrors the loop and lets an operator tune it.
#
#   ctrl  PI: pump flow from the set point `plc.level_sp` and the measured level `lab.level`
#   sup   status bits for the write gates: 1 the PLC's interlock is set, 2 the level is
#         outside [level_lo, level_hi]
#
# `lab.level` goes stale 3 s after the last good read: the engine then skips its ticks and both
# gates close, so the plant data system and the PLC keep their last set points. Both connectors
# start as a dry run; `closed-loop.toml` is this file with writes on. Build the models first
# (`build.sh`). Then, from this folder, with the addresses below set to the plant's, or the
# stand-ins of `stand-in/` running:
#   taktwerk check --live project.toml
#   taktwerk run project.toml                         # reads, logs the writes
#   taktwerk run project.toml --write plc --write lab # closes the loop

[engine]
tick_ms = 100.0

[models.pi]
kind = "raw"
path = "packages/pi"

[models.supervisor]
kind = "raw"
path = "supervisor"

[[instance]]
id = "ctrl"
model = "pi"
dims = { n = 1 }
parameters = { kp = 1.0, ki = 0.1 }
inputs = { sp = ["plc.level_sp"], pv = [{ signal = "lab.level", max_age_ms = 3000.0 }] }

[[instance]]
id = "sup"
model = "supervisor"
parameters = { level_lo = 0.05, level_hi = 2.0 }
inputs = { interlock = "plc.interlock", level = "lab.level" }

# Every external input as written and every output each tick; tunable changes, gate changes
# and refused writes are events in events.csv.
[[recorder]]
id = "main"
signals = ["@io"]

# The plant data system: the measured level in, the pump set point and a watchdog out.
[[connector]]
id = "lab"
kind = "rest"
base_url = "http://127.0.0.1:8080/api/"
period_ms = 500
refresh_s = 10
writes = "dry-run"

[connector.gate]
open_after = 3
conditions = [{ signal = "sup.status", mask = 3 }]

[connector.map]
"lab.level" = { get = "values", pointer = "/level", min = 0, max = 5, max_unchanged_s = 60 }
"ctrl.u[0]" = { put = "setpoints/pump", pointer = "/value", min = 0, max = 1.5, clamp = true }
"taktwerk.heartbeat" = { put = "setpoints/watchdog", pointer = "/value" }

# The PLC: set point and interlock in; the engine's signals, the loop and the gains mirrored
# into its program, the gains synced both ways so an operator tunes them there. The map is what
#   taktwerk plc-mirror project.toml --node-prefix 'nsu=urn:example:plc;s=' \
#     --program mirror --from-plc 'plc.*' --all-tunables ctrl --sync-tunables
# generates (with the program `mirror`), edited: the set point and interlock read from the
# PLC's own `hmi` program, three engine signals left out, limits and an ungated status added.
[[connector]]
id = "plc"
kind = "opcua-client"
endpoint = "opc.tcp://127.0.0.1:4840"
sync_period_ms = 200
writes = "dry-run"
sync_epoch = "nsu=urn:example:plc;s=mirror.taktwerk_sync_epoch"

[connector.gate]
open_after = 3
conditions = [{ signal = "sup.status", mask = 3 }]

[connector.map]
"plc.level_sp" = { node = "nsu=urn:example:plc;s=hmi.level_sp", min = 0, max = 2 }
"plc.interlock" = "nsu=urn:example:plc;s=hmi.interlock"
"taktwerk.heartbeat" = "nsu=urn:example:plc;s=mirror.taktwerk_heartbeat"
"taktwerk.status" = "nsu=urn:example:plc;s=mirror.taktwerk_status"
"lab.level" = { node = "nsu=urn:example:plc;s=mirror.lab_level", mirror = true }
"ctrl.u" = { node = "nsu=urn:example:plc;s=mirror.ctrl_u", min = 0, max = 1.5, clamp = true }
"sup.status" = { node = "nsu=urn:example:plc;s=mirror.sup_status", gated = false }
"ctrl.kp" = { node = "nsu=urn:example:plc;s=mirror.ctrl_kp", min = 0, max = 10, sync = true }
"ctrl.ki" = { node = "nsu=urn:example:plc;s=mirror.ctrl_ki", min = 0, max = 1, sync = true }

The example carries stand-ins for both, on loopback:

  • stand-in/lab.py: the plant data system, a tank behind a JSON API, standard library only.
  • stand-in/plc.toml: the PLC, a taktwerk project whose OPC UA server offers the nodes project.toml maps; its model (stand-in/plc/plc.h) holds the operator’s set point and interlock as tunables, takes what the engine mirrors and watches the engine’s heartbeat.

Start them in two more terminals, from this folder, then verify the map against them; check --live writes nothing:

python3 stand-in/lab.py
taktwerk run stand-in/plc.toml --http 127.0.0.1:8490 --http-writes
taktwerk check --live project.toml

It lists every node with its role and type, ok per row, and ends in verified against the live endpoints, nothing written. Now the dry run: it reads, evaluates the gates and logs what it would write.

taktwerk run project.toml --http 127.0.0.1:8480

Its log shows dry run, not written: ctrl.u[0] (PUT setpoints/pump#/value) = … once a second. In another terminal:

curl -s 127.0.0.1:8080/api/setpoints
taktwerk engine read 'taktwerk.connector.*.gate_open' sup.status

The plant data system got nothing ({"writes": 0}), and both gates are open: a write would go out. Stop the run with Ctrl-C. Writes on, for one run: verify that every written node is writable, then run with --write:

taktwerk check --live --write plc --write lab project.toml
taktwerk run project.toml --write plc --write lab --http 127.0.0.1:8480

curl -s 127.0.0.1:8080/api/setpoints now shows the pump set point and the watchdog arriving; the stand-in’s tank follows the pump. Set the interlock on the PLC:

taktwerk engine --url 127.0.0.1:8490 set hmi.interlock 1 --yes

sup.status is 1 and both gates close: the pump set point holds where it was, the watchdog keeps coming, so both sides see the engine alive. Clear the interlock and the gates open after three good ticks. An operator tunes the PI on the PLC; the synced gain reaches the engine:

taktwerk engine --url 127.0.0.1:8490 set hmi.interlock 0 --yes
taktwerk engine --url 127.0.0.1:8490 set mirror.ctrl_kp 2 --yes
taktwerk engine read ctrl.kp

Stop the run and both stand-ins with Ctrl-C. The record holds each gate change and the gain:

uv run --with ../../python python report.py records/project/main

Check for gate lab closed: sup.status 1 has masked bits 1 and tunable ctrl.kp 1.0 -> 2.0 by plc. On a real plant the addresses and the map are the plant’s, generated with plc-mirror, credentials come from the environment, and the same order applies: Commissioning. The connectors are in Connectors (dry run, write gate, tunable sync), the setups in A controller beside a PLC and A closed loop with a plant data system.

report.py:

"""A run of the level loop in a few lines, or two runs compared.

    uv run --with ../../python python report.py <run> [<other run>]

A run is a run directory (with `run.json`) or any directory above runs: then its newest run.
Prints how the run ended, its events but the tunables' start values, and the range of every
recorded number; given two runs, the largest difference per column instead.
"""

import math
import sys
from pathlib import Path

import taktwerk


def newest(path: str) -> Path:
    root = Path(path)
    if (root / "run.json").is_file():
        return root
    runs = [p.parent for p in root.rglob("run.json")]
    if not runs:
        sys.exit(f"{path}: no run below it")
    return max(runs, key=lambda p: (p / "run.json").stat().st_mtime)


def numbers(run: taktwerk.Run, column: str) -> list[float]:
    return [float(v) for v in run[column] if isinstance(v, (int, float)) and math.isfinite(v)]


def summary(path: Path, details: bool = True) -> taktwerk.Run:
    run = taktwerk.read_run(path)
    t = run.t_engine
    print(f"{path}: {len(t)} rows, {t[0]:.1f} to {t[-1]:.1f} s, stop: {run.stop}")
    if not details:
        return run
    for e in run.events:
        if e.kind not in ("start", "stop") and not e.detail.startswith("start "):
            print(f"  {e.t_engine:8.1f} s  {e.kind:9} {e.source:28} {e.detail}")
    for column in run.columns:
        values = numbers(run, column)
        if values:
            print(f"  {column:28} {min(values):10.4g} .. {max(values):<10.4g}")
    return run


def compare(a: taktwerk.Run, b: taktwerk.Run) -> None:
    print("largest difference per column:")
    for column in a.columns:
        if column not in b.columns:
            continue
        pairs = list(zip(a.t_engine, a[column], b[column]))
        diffs = [
            (abs(float(x) - float(y)), t)
            for t, x, y in pairs
            if isinstance(x, (int, float)) and isinstance(y, (int, float))
        ]
        diffs = [d for d in diffs if math.isfinite(d[0]) and d[0] > 0]
        if diffs:
            d, t = max(diffs)
            print(f"  {column:28} {d:10.4g} at {t:.1f} s")
        else:
            print(f"  {column:28} {'equal':>10}")


def main() -> None:
    if len(sys.argv) not in (2, 3):
        sys.exit(__doc__)
    if len(sys.argv) == 2:
        summary(newest(sys.argv[1]))
    else:
        first = summary(newest(sys.argv[1]), details=False)
        compare(first, summary(newest(sys.argv[2]), details=False))


if __name__ == "__main__":
    main()

Simulation and digital twin

The engine that runs a project on a controller also runs it as a simulation: the same packages, the same fixed step, the same image, as fast as the models compute. A digital twin is the same project again, run in real time beside the plant and fed with its measurements.

Offline simulation

A plant model and the application under test in one project, wired in the image:

[engine]
tick_ms = 100.0

[models.plant]
kind = "fmi"
path = "packages/plant.fmu"

[models.ctrl]
kind = "raw"
path = "packages/ctrl"

[[instance]]                  # the controller reads the plant's output of the previous tick
id = "ctrl"
model = "ctrl"
inputs = { pv = "plant.y" }

[[instance]]
id = "plant"
model = "plant"
inputs = { u = "ctrl.u" }

[[recorder]]
id = "main"
signals = ["@io"]

taktwerk run sim.toml --speed max --no-connectors --until-time 86400 --seed 1
  • --speed max runs unpaced on engine time; input ages and every event count model time, so the rows are the same at any speed (Pace).
  • --set, --model and a scenario file change a run without editing the project: other parameters, another package version, a disturbance, a sensor fault. Each is recorded in run.json.
  • The record is the same format a plant run writes; the Python package and the workbench read both.

examples/closed-loop is an FMU and a C controller wired this way; examples/campaign adds a seeded noisy sensor and a disturbance scenario.

Digital twin

A twin runs a plant model in real time with the plant’s own inputs, so its outputs can be put next to the measurements, or stand in for what the plant does not measure:

    TW[plant model] --> PI[(image)]
  end
  E -- "OPC UA server" --> HMI[HMI, historian]
  E -- "recorder" --> R[records]
  • An opcua-client reads the manipulated values (and the measurements to compare with) into external inputs, with a max_age_ms, so the twin stops stepping when the data stops.
  • The model’s outputs are on the engine’s OPC UA server for any client; mapped in the opcua-client they go back to the PLC. A twin that only reads needs no writes.
  • A recorder with @io keeps every input as received and every output each tick, for a comparison afterwards: the same record can be replayed offline with the measured inputs set by a scenario, or compared run against run in the workbench.

An estimator that corrects the model from the measurements is an application package of its own; see A controller or estimator beside a PLC.

A study runs one project many times: other gains, other plants, other noise, the same disturbance. A campaign file plans the runs; taktwerk campaign --write runs them, one process each, and resumes where it stopped.

A controller or estimator beside a PLC

An estimator, a soft sensor or a model-based controller runs next to a PLC: it reads the PLC’s measurements, computes at a fixed period and writes estimates or set points back. The PLC keeps the I/O, the interlocks and the safe state.

flowchart LR
  subgraph tw[taktwerk, edge PC or Linux PLC]
    EST[estimator] --> CTL[controller] --> PI[(image)]
    EST --> PI
  end
  PLC[PLC] -- "measurements, set points" --> PI
  PI -- "estimates, manipulated values,<br/>status, heartbeat (gated)" --> PLC
  1. Package the application with an interface of inputs, outputs, tunables and a status output (Applications as packages, Status and the write gate).
  2. Map the PLC’s nodes in an opcua-client: measurements into inputs with a max_age_ms, outputs to the PLC’s variables, taktwerk.heartbeat and taktwerk.status to variables the PLC program watches. Per mapping scale, offset, min, max and max_unchanged_s check the values on the way (Conversion and checks).
  3. Gate the writes on the application’s status: [connector.gate] with { signal = "est.status", mask = 255 }. A closed gate writes none of the gated outputs; the PLC keeps their last values and sees the heartbeat and the status.
  4. Let operators tune on the PLC’s HMI: a tunable mapped with sync = true and a sync_epoch node is seeded from the engine, forwards an operator’s write into the image and follows other writers (Tunable sync).
  5. Generate the PLC side: taktwerk plc-mirror project.toml --node-prefix 'ns=4;s=' writes an IEC 61131-3 program with one variable per mirrored signal and the map entries that write it, from one walk over the plan, so the two cannot diverge (CLI).
  6. Commission in steps: check --live, a run with writes = "dry-run", then run --write plc (Commissioning).
  7. Deploy as a bundle to the edge PC or the Linux PLC, supervised by systemd or by taktwerk’s own supervisor (Deploying to devices).

The PLC program must treat a heartbeat that stops advancing, or taktwerk.status other than 1, as the engine being gone, and fall back to its own safe values (the safety contract).

On a PLC that runs Linux itself, the same binary runs on the PLC; keep the cycle thread’s priority below the PLC runtime’s own tasks, and record with sink = "buffer" pulled by taktwerk record from an edge PC (Two sinks).

Where the connector stops

The connector maps fixed paths to signals. Simulation runs

The engine that runs a project on a controller in real time also runs it as a simulation: the same project, the same model packages, the same fixed-step semantics, as fast as the models compute. taktwerk solves no equations itself. Each model advances itself by one step at every tick it is due, and the engine exchanges values at tick boundaries, as in real time.

Pace

--speed decides how ticks follow the wall clock:

taktwerk run project.toml                  # real time: one tick per tick_ms
taktwerk run project.toml --speed 120      # deadlines 120 times closer together
taktwerk run project.toml --speed max --no-connectors --cycles 100000
speedticksengine clockoverruns
1on absolute deadlines every tick_mswall clockcounted
<factor>on absolute deadlines every tick_ms / factorengine timecounted
maxeach as soon as the previous one is doneengine timenone

Model time is start_time + tick × tick_ms at every speed; a model sees the same step size and the same inputs. What changes is how long a tick takes on the wall clock.

Engine time. Off real time the engine’s clock is engine time: an input’s age is measured in model time, and a write by a connector (a tunable set from the TUI, say) is stamped with the engine time of the tick it lands in. So max_age_ms means the same at every speed.

Recorders lose no rows at max. In a paced run a file sink that falls a ring behind loses rows (see Recording); unpaced, nothing is late, so the cycle waits for its file sinks instead. A buffer sink is not waited for.

Connectors. --no-connectors starts none: the run serves nothing and binds no port, so many runs can share a machine. An opcua-client or rest connector exchanges values with a device in wall time and is refused off real time. The OPC UA server may stay; a client sees the run go by at its speed and can still set tunables, which are then stamped and logged at the engine’s tick.

Same project, same inputs: the same rows, at any speed. A run whose inputs only come from its models (no connector writes while it runs) records byte-identical parts at --speed 1, 120 and max, except for taktwerk.overruns, which counts the machine’s missed deadlines.

Stop conditions

A run ends on SIGINT, SIGTERM or SIGHUP, on a model error, or at the first of these:

taktwerk run project.toml --speed max --no-connectors \
  --cycles 1000000 --until-time 86400 \
  --stop-when 'tank.level > 2.0' --stop-when 'ctrl.alarm'
  • --cycles N: after N ticks.
  • --until-time S: before the first tick whose engine time is at or after S seconds, so the last tick is the last one before S; with start_time 0 and a 0.1 s tick, --until-time 60 runs 600 ticks.
  • --stop-when CONDITION: after the first tick at which the condition holds; that tick is the last recorded one. A condition is <signal> <op> <number> with >, >=, <, <=, == or !=, or a bare signal, which holds when the value is not zero (a flag set). name[i] takes element i of an array. true and false are 1 and 0. Any numeric signal works, read after the tick: outputs, inputs, tunables, system signals. NaN satisfies only !=. The option repeats; the first condition that holds ends the run.

Conditions are parsed against the plan at start, so a typo fails the run before the first tick. The stop event in events.csv names what ended the run: cycle limit reached, time limit reached, or condition tank.level > 2.0.

Overrides

One project serves many runs. --set, --model and --record-dir change a run without editing the project file:

taktwerk run project.toml --speed max --no-connectors --until-time 3600 \
  --set ctrl.kp=2.5 --set plant.tau='[0.2, 0.5]' --set plant.dims.n=2 \
  --set engine.start_time=0 --set plant.u=1.0 \
  --model plant=../packages/plant-v2 --record-dir out/run-7
keywhat it sets
<instance>.<parameter>the parameter’s value, like parameters in the project
<instance>.<tunable>the tunable’s start value
<instance>.<input>the initial value of the external signal the input reads
<instance>.dims.<dimension>the dimension’s length
<instance>.everythe instance’s period in ticks
engine.tick_ms, engine.start_time, engine.input_max_age_msthe engine setting
<signal>a tunable bound to that signal (its start value), or an external input (its initial value)
  • The value is a TOML value: 0.5, 3, true, [1.0, 2.0], "model2.txt". Text that is not valid TOML is taken as text, so --set ctrl.mode=fast works without quotes. A model’s data file, read by the library from a text parameter, is just such a parameter.
  • Overrides apply in order once the models are loaded, so a later one wins, and they are checked like the project file: an unknown instance, variable or signal, an output, a wired input, or a value of the wrong shape fails the run before it starts.
  • An initial value is written into the image before the first tick. Nothing writes the input again in a run without connectors, so it holds for the whole run unless a scenario event changes it.
  • --model ID=PATH points model ID at another package or FMU of the same kind. --record-dir DIR replaces the dir of every file recorder, so the run lands in DIR/<project>/<recorder>/<run-id>/. Both paths are relative to the working directory.

Every applied override is recorded in run.json under invocation, with the project’s value it replaced (was, absent when the project left it to the model), next to the speed, the stop conditions and whether connectors ran. With the project file’s hash, a record describes its run completely:

  "connectors": false,
  "until_time": 3600.0,
  "overrides": [
    { "key": "models.plant", "value": "/home/me/packages/plant-v2", "was": "plant" },
    { "key": "ctrl.kp", "value": 2.5, "was": 1.0 }

}

Seeds

--seed N gives a run one seed, and every instance that draws random numbers its own seed derived from it:

taktwerk run project.toml --speed max --no-connectors --until-time 600 --seed 7
  • Which variable. An instance takes its seed through a numeric scalar parameter or tunable named seed, when its model has one. A model that names it differently is pointed at it in the project, seed_var = "rng_seed" on the [[instance]]; seed_var = "" takes none. A model needs no change for this: it already reads its seed from a parameter, now the run sets it.
  • Which value. Instance id gets splitmix64(N xor fnv1a(id)), reduced to what the variable holds exactly: 31 bits for a signed 32-bit integer, 32 for an unsigned one, 24 for an f32, 53 for an f64, 63 for a 64-bit integer. Instances draw independent streams, and a renamed instance draws another.
  • What wins. The run seed replaces a seed the project file sets; --set <instance>.seed=… replaces the run seed. Without --seed nothing changes.
  • Recorded. run.json’s invocation holds seed and seeds, the value each instance got.

Same project, same overrides, same seed: byte-identical parts, at any speed.

Scenario events

A scenario file says what happens to a run while it runs: timed events, and the overrides, stops and seed that go with them. One project, many scenarios:

taktwerk run project.toml --speed max --no-connectors --scenario disturbance.toml

seed = 3

[set]                            # overrides, as --set takes them
"ctrl.sp" = [1.0]

[models]                         # model packages, relative to this file
# plant = "../packages/plant-v2"

[stop]                           # as --cycles, --until-time and --stop-when
time_s = 900.0
when = ["plant.level > 2.5"]

[[event]]                        # a step of the disturbance inflow at 300 s
at_s = 300.0
add = "plant.q_dist"
value = 0.2

[[event]]                        # the level sensor freezes for a minute
at_s = 400.0
fault = "plant.level_m"
hold = true
for_s = 60.0

[[event]]                        # a set-point ramp
at_s = 600.0
ramp = "ctrl.sp[0]"
to = 1.5
over_s = 100.0

[[event]]                        # from 800 s the sensor reads 0.1 m high, to the end
at_s = 800.0
fault = "plant.level_m"
offset = 0.1

An event applies at the first tick whose engine time is at or after at_s, or at tick cycle, before the models step; events of one tick apply in file order. Each has one action: set, add (a step) or ramp a tunable or external input, fault a signal (hold, value, offset, scale, noise_sd, drop, for for_s seconds or until a clear). Every key is in the scenario file reference.

  • A target of set, add and ramp is a tunable or an external input. A fault acts on an output or an external input, element name[i] or whole, for every model that reads it. A new fault on a signal replaces the one in force.
  • A set, add or ramp ends a ramp in progress on what it writes (the whole signal, or the same element), logging that ramp’s end; the ramp does not resume. A write to another element leaves it running. A new ramp starts from the value the signal holds at its tick.
  • Faults act where models read: a recorded output stays what its model produced. A recorded external input and a recorded composed input are what their model received. An input wired whole to an output has no signal of its own (its column would be the output), so to see what a model received there, compose it: inputs = { pv = ["plant.y"] } records as ctrl.pv.
  • Noise draws from a stream of the run seed and the event’s index, so a seeded run repeats its noise.
  • Every applied, started and ended event is a scenario event in events.csv, with the signal as its source: fault plant.level_m hold for 60 s, and later end: fault plant.level_m hold for 60 s.
  • Events are checked against the plan at start: an unknown signal, a target of the wrong kind, a missing or misplaced value fails the run before the first tick.

The file’s overrides apply before --set, its models before --model, and --seed, --cycles, --until-time win over the file’s; its stop conditions and those of the command line all apply. run.json’s invocation keeps the file whole: its path, hash and text.

Campaigns

A campaign is a set of simulation runs of one project, planned from one file: the product of named cases, a parameter grid, random samples and replicates, each run one scenario with its own seed. taktwerk campaign prints the plan; with --write it runs it, each run a taktwerk run process of its own, and picks up where it stopped when run again.

taktwerk campaign sweep.toml            # the plan, nothing run
taktwerk campaign sweep.toml --write    # run what is not done

The campaign file

project = "project.toml"         # relative to this file
out = "out/sweep"                # default: the file's stem, beside it
jobs = 2                         # runs at a time; --jobs overrides
speed = "max"                    # --speed of every run: max (default) or a factor
seed = 1                         # the campaign's seed
scenario = "disturbance.toml"    # a scenario every run starts from

[set]                            # overrides of every run
"ctrl.sp" = [1.0]

[stop]                           # stops of every run; every run needs cycles or time_s
time_s = 1200.0

[[event]]                        # events of every run, as in a scenario file
at_s = 300.0
add = "plant.q_dist"
value = 0.2

[[case]]                         # the list axis
name = "nominal"
[[case]]
name = "small-outlet"
scenario = "outlet.toml"         # merged over the common scenario
set = { "plant.k_out" = 0.4 }

[grid]                           # the grid axis: every combination
"ctrl.kp" = [0.5, 1.0, 2.0]
"ctrl.ki" = [0.01, 0.05]

[sample]                         # the random axis: n draws of every variable
n = 50
method = "lhs"                   # Latin hypercube (default) or "uniform"
"plant.gain" = { uniform = [0.8, 1.2] }
"plant.tau" = { log_uniform = [0.5, 2.0] }
"plant.bias" = { normal = [0.0, 0.01] }
"plant.mode" = { choice = [1, 2, 3] }

replicates = 1                   # repeats of every run with another seed
  • Runs. The product of the axes present, in the order case, grid point, sample, replicate. A run is named by its axes: small-outlet-g3-s07, or g03 for a grid alone, run for a campaign without axes.
  • What a run runs. The common scenario file, then the campaign’s [set], [stop] and events, then the case’s scenario file and set, then the grid point’s and the sample’s values: later values win, stop conditions and events add up. The result is the run’s run.toml, a scenario file that taktwerk run --scenario reruns on its own.
  • Seeds. Run seeds derive from the campaign’s seed and the run’s sample and replicate, 63 bits of splitmix64: runs that differ only in case or grid point share their seed, so a comparison of cases or gains sees the same noise (common random numbers). A grid or sample key seed sets the run seed instead.
  • Samples. A Latin hypercube puts one draw of each variable in each of n equal-probability strata, shuffled per variable; each variable draws from its own stream of the campaign’s seed, so adding a variable leaves the others’ draws as they were. normal maps through the inverse normal distribution, choice picks one of its values.
  • Every run is checked when the plan is made: a bad case name, an empty grid, a bad distribution or a run without a stop limit fails the plan before anything runs.

Running and resuming

Each run is taktwerk run <project> --speed <speed> --no-connectors --scenario run.toml --record-dir <run directory>, jobs at a time; a library with process-wide state is no problem, since every run is its own process.

out/sweep/
  campaign.json                   the plan: file and project hashes, every run's values, seed, spec hash
  runs.csv                        one row per run: axes, seed, status, stop, cycles, wall time, values
  runs/small-outlet-g3-s07/
    run.toml                      the run's scenario
    status.json                   status, exit code, stop, cycles, wall time, sha256 of every record file
    stderr.log                    the run's log
    project/main/<run-id>/        the run's records: run.json, parts, events.csv
  • Status. A run is ok when it exits cleanly on a limit or a condition, failed otherwise; a run stopped by SIGINT or SIGTERM is not ok.
  • Resume. --write again runs only what is not done: a run is done when its status.json says ok and its spec hash is the planned one. The spec hash covers the taktwerk version, the project file, the model packages the run uses (a scenario’s [models] in place of the project’s) and the run’s scenario, so a changed project or a rebuilt package runs every run that uses it again. A package is its descriptor and libraries (see run.json), so a campaign and its output may sit in the package directory. An interrupted or failed run’s directory is cleared and run again.
  • Another plan. When the output already holds a plan with other runs, --write refuses; --force clears the runs and starts over.

runs.csv and campaign.json are made to be read back: the Python reader loads a campaign into a table of runs and each run’s signals into arrays.

Recording

A [[recorder]] keeps a lossless, per-tick history of selected signals, taken by the engine itself. OPC UA subscriptions sample and can miss ticks; a recorder sees every tick it is asked for. The cycle thread only copies the selected values into a preallocated ring buffer: no allocation, lock, I/O or wait. Everything else (files, compression, counters, remote pulls) happens on other threads, and a sink that falls behind loses rows instead of slowing the cycle.

[[recorder]]
id = "main"
signals = ["plant.*", "ctrl.u[*]", "ctrl.qp_flag"]
every = 1
sink = "file"
dir = "records"

Every key is in the project file reference.

cycle thread --copy, never waits--> ring (buffer_s) --drain thread--> run files      (sink = "file")
                                         |
                                         +--read_rows over OPC UA--> taktwerk record --> run files

Two sinks

  • sink = "file" (the default): on an edge PC or a workstation. A drain thread per recorder writes gzipped CSV parts to the engine’s own disk (or a mounted stick). The ring is the drain’s slack.
  • sink = "buffer": on a PLC-class device with little RAM and flash. The engine keeps the last buffer_s seconds in RAM and writes nothing. taktwerk record on an edge PC beside it pulls the rows over OPC UA and writes the same files a file sink writes.

Both sinks serve their ring to pulls, so a file sink can be pulled as well.

What a row holds

One row every every ticks, at the ticks divisible by every: row n holds cycle n · every. Skipped ticks are recorded too (a stale input skips a tick; the row then holds the held outputs and taktwerk.status is 2). So consecutive rows always differ by exactly every cycles; any other jump is a loss.

A row is what the cycle holds after the tick is stored: outputs, composed inputs, system signals, and inputs and tunables bound whole to an instance, an input or tunable as the instance stepping most often holds it. A recorder with @io or @inputs takes every external input from the image instead, as its writer left it at the start of the tick.

Selecting signals

signals lists patterns over signal names, in column order; a signal matched twice is recorded once.

  • * matches any run of characters, dots included; ? matches one character.
  • A trailing [*] takes every element of a one-dimensional signal, [i] element i (from 0). Without a selector an array is recorded whole.
  • An empty list (the default) records every output.
  • Each array element is one column, name[i], or name[i,j] with logical indices for a matrix. A text signal is one column.
  • "@io" takes the engine’s I/O interface in its place, "@inputs" and "@outputs" one half of it each.
  • A pattern that matches nothing recordable is an error. An external signal read only element by element (a source of a composed input) is not held whole: a pattern skips it and its exact name is refused, unless the recorder has @io or @inputs. Without either, record the composed input <instance>.<input> instead.

The I/O interface

"@io" in signals records every signal the engine exchanges with the outside, in its place in the column order:

  • "@inputs": every external input, as its writer (a connector, or a scenario’s set or ramp) left it in the image at the start of the tick, whatever its age: also one the instances read only element by element, and one an instance with a longer period holds between its steps;
  • then "@outputs": every model output, then <prefix>.heartbeat and <prefix>.status.

Every output can be read by an OPC UA or HTTP client, so @io takes them all; a model with many outputs (matrices, diagnostics, text) makes wide rows. @inputs with the outputs a consumer actually reads keeps a per-tick recorder narrow.

Each group is in signal order, the order in which the project’s instances (and their models’ variables) first use the signals, so the columns stay the same from run to run of a project. Connectors play no part: --no-connectors and --http record the same columns. Composed inputs are left out, since their sources are recorded; tunables are no columns, events.csv holds their values.

In a recorder with @io or @inputs, every external input is taken as written, also one another pattern names. A scenario fault applies where a reader copies the input, so it shows in the composed input and the outputs, not in the input’s own column.

A per-tick recorder in RAM, pulled by taktwerk record on an edge PC, pairs well with a decimated copy of everything on the device’s own disk, for when the edge PC is away longer than buffer_s:

[[recorder]]
id = "io"                      # every tick, pulled: taktwerk record ... --recorder io
signals = ["@inputs", "ctrl.u[*]", "ctrl.status", "taktwerk.heartbeat", "taktwerk.status"]
sink = "buffer"
buffer_s = 3600                # the edge PC may be away an hour without a gap

[[recorder]]
id = "local"                   # every 10th tick on the device's disk
signals = ["@io"]
every = 10
rotate = { size_mb = 4, hours = 24 }
retain = { max_gb = 0.03 }     # 30 MB of the device's flash

Run files

Every run of a recorder is a directory <dir>/<project>/<recorder>/<run-id>/ with run.json, gzipped CSV parts, events.csv, SHA256SUMS and, once closed, CLOSED. A run opens when the engine starts and closes when it stops; every start is a new run. A local sink and taktwerk record write the same files. The layout and every field are specified in Run record format.

Rotation and retention

A part closes, and the next one opens, when its compressed size reaches rotate.size_mb or it covers rotate.hours of engine time, whichever comes first. Rotation counts engine time, not wall time, so the same rows always split into the same parts.

Retention runs when a run opens and at every rotation, over all runs of one recorder (<dir>/<project>/<recorder>/). It deletes closed parts, oldest first, while the recorder’s parts together exceed retain.max_gb, and every closed part older than retain.days (by its modification time). The open part is never deleted, an .open part another run left behind is; run.json, events.csv and SHA256SUMS are kept, so a deleted part’s line stays in SHA256SUMS (check with sha256sum -c --ignore-missing).

Decimation and several recorders

every = 10 keeps one row per 10 ticks. A project may have several recorders, each with its own signals, every, sink and ring, for example a per-tick one for a few signals and a decimated one for everything. Their ids keep their directories, counters and pull nodes apart.

Counters

Each recorder publishes system signals under <prefix>.recorder.<id>. (<prefix> is engine.system_prefix, default taktwerk), about once a second, on the OPC UA server and in the TUI:

signaltypemeaning
rows_writtenu64rows written to parts; for a buffer sink, rows captured
rows_droppedu64rows the cycle overwrote before the file sink wrote them
gapsu64pulls that asked for rows already overwritten
bytesu64compressed bytes written to parts
partu64number of the open part; 0 for a buffer sink
buffer_fillf64rows not yet written (file) or held (buffer), as a fraction of the ring

A recorder may list counters in signals, its own or another’s (e.g. "taktwerk.recorder.*.buffer_fill"); a row holds the value last published, so it changes about once a second.

Sizing the ring

The ring holds buffer_s seconds of engine time: ceil(buffer_s / (tick_s · every)) rows, at least 2. A row takes one 8-byte word per numeric column, one per byte of a text column’s capacity, and two words of its own. taktwerk check prints both per recorder:

  recorder  sink    every  columns  ring rows  ring     dir
  main      file    1      8        60000      4.8 MB   records
  slow      buffer  10     3        600        24.0 kB  -

A ring larger than 4 GiB is refused. For a buffer sink, buffer_s is how long a puller may be away without a gap; for a file sink, how long the disk may stall without a drop.

A per-tick I/O recorder of 60 columns at a 1 s tick takes 3600 rows an hour, (60 + 2) · 8 = 496 bytes each in the ring, so buffer_s = 3600 holds an hour in 1.8 MB. A part takes far less per row, since gzip packs values that change little; how much depends on the signals. In one 42-hour simulated run of a closed loop with noisy plant readings, 44 numeric columns took 106 bytes a row, and 298 columns, most of them constant, 174 bytes. Measure it on a simulated run of the project (taktwerk run --speed max --cycles 86400, then the size of its parts) before sizing rotate and retain for a device’s flash.

Gaps and drops

Both show as a jump in the cycle numbers of a run, larger than every. They differ in where the rows were lost:

  • Dropped: the engine’s own file sink fell more than a ring behind the cycle (a stalled or slow disk). Counted in rows_dropped, logged as a dropped event with the cycles lost. Raise buffer_s, record fewer signals or a larger every, or use a faster disk.
  • Gap: a puller asked for rows the ring had already overwritten (the puller stopped or the network was down for longer than buffer_s). Counted in the engine’s gaps, logged as a gap event in the puller’s events.csv. Raise buffer_s on the engine.

A skipped tick is neither: its row is there, with taktwerk.status 2.

Reading a run

The standard library is enough: gzip and csv over every part in order, json for run.json. Every value arrives as a string; float() reads the float columns, NaN and inf included. This script is examples/recording/read_run.py:

"""Read one recorded run with the Python standard library alone.

Usage: python3 read_run.py <run-dir>
"""

import csv
import gzip
import json
import sys
from pathlib import Path


def rows(run: Path):
    """Yield every row of the run as a dict, parts in order, header lines skipped."""
    # Closed parts, then the open one of a running engine (`.open`, renamed when closed).
    parts = [*run.glob("part-*.csv.gz"), *run.glob("part-*.csv.gz.open")]
    for part in sorted(parts):
        with gzip.open(part, "rt", newline="") as f:
            try:
                yield from csv.DictReader(f)
            except EOFError:
                pass  # the open part of a running engine ends at its last flush


def main() -> None:
    run = Path(sys.argv[1])
    meta = json.loads((run / "run.json").read_text())
    every = meta["every"]
    n, gaps, last, prev = 0, 0, None, None
    for row in rows(run):
        cycle = int(row["cycle"])
        if prev is not None and cycle != prev + every:
            gaps += 1  # rows lost between prev and cycle
        prev, last, n = cycle, row, n + 1
    print(
        f"{meta['project']}/{meta['recorder']}: {n} rows, tick {meta['tick_s']} s, "
        f"every {every}, {gaps} gaps"
    )
    print("last row:", last)
    with open(run / "events.csv", newline="") as f:
        for e in csv.DictReader(f):
            print(f"event {e['cycle']} {e['kind']} {e['source']}: {e['detail']}")


if __name__ == "__main__":
    main()

A run still recording, or one cut off by SIGKILL or a crash, has an open part (part-NNNN.csv.gz.open) that ends at its last flush, without the gzip trailer, and an events.csv that may end in half a line. The Python package and taktwerk serve read such a run up to its last complete line; they ignore temporary files (*.tmp).

Syncing to an object store

taktwerk uploads nothing; any sync tool copies a record directory to an S3-compatible store. Closed parts never change, so a tool that compares size and modification time uploads each once. While a run records, exclude the open part and temporary files; events.csv, run.json and SHA256SUMS still change and are uploaded again until the run is closed.

# rclone, a remote `store` from `rclone config`
rclone copy /data/records store:records --exclude '*.open' --exclude '*.tmp'

# the AWS CLI, or any S3-compatible endpoint with --endpoint-url
aws s3 sync /data/records s3://records --exclude '*.open' --exclude '*.tmp'
  • Copy, do not mirror deletions (rclone copy, aws s3 sync without --delete): retention deletes closed parts locally, and the store keeps them.
  • Run it from cron or a timer; a run is complete in the store once its CLOSED is there and sha256sum -c --ignore-missing SHA256SUMS passes in a copy of it.
  • A run cut off by a kill never gets CLOSED; its .open part stays local, the rows up to the last closed part are in the store.

Reproducible runs

taktwerk run --cycles N stops the engine after N ticks with a stop event cycle limit reached, at any speed; --speed max runs it unpaced and loses no row. Two runs of a deterministic project (no external inputs, no edits while it runs) give byte-identical parts and the same events.csv; run.json differs in run_id, engine_run and the UTC fields. taktwerk.overruns counts missed deadlines, which depend on the machine’s load; leave it out of signals when parts must match.

taktwerk run examples/recording/project.toml --cycles 200 --speed max --no-connectors

Remote recording

taktwerk record pulls the recorders of a running engine over OPC UA, over one connection, and writes the run files on the host it runs on, until SIGINT, SIGTERM or SIGHUP. Run it on an edge PC beside a PLC-class device that records with sink = "buffer":

taktwerk record opc.tcp://10.0.0.2:4840 --dir /data/records --recorder main
  • Without --recorder it pulls every recorder of the engine, each into its own <dir>/<project>/<recorder>/ runs; --recorder (repeatable) picks some. --namespace and --prefix match the server’s namespace and the engine’s system_prefix when they are not the defaults.
  • It starts with the oldest row the engine still holds and opens the run at the first row it gets: source in run.json is the endpoint, start.utc the puller host’s clock.
  • It pulls a recorder again at once while its batches come back full, else after a tenth of the smallest buffer_s pulled (at most 1 s). It stays lossless while it is never away longer than buffer_s.
  • A jump in the cycle numbers is written as a gap event, and so are engine events that left the engine’s log before they were pulled.
  • Events are pulled from the oldest the engine’s log (its newest 65 536) still holds, so a run opened after the engine started still gets the tunables’ start lines.
  • When the engine stops, its server stays up (at most 5 s) until every recorder pulled during the run has its last rows and events; the puller writes the stop event, the rows up to the last tick, and closes the run.
  • A lost connection is retried. When the engine restarted (engine_run changed), the run is closed and the next one opened. If its end had not been pulled (no stop event, or rows after it), a gap event cycles from <n> not pulled: … is its last event and run.json’s end says truncated: true: the rows from cycle n to the engine’s last tick are lost.
  • Its parts are written the same way as a local sink’s, so the same rows give the same bytes.

An integrator writing a puller of their own uses the pull interface.

Workbench

The workbench is a web UI over a project folder and the devices it deploys to, and the same UI over one running engine. A build with the ui feature carries it (cargo install taktwerk --features ui); the desktop app in desktop/ wraps it.

A project folder

taktwerk serve examples/campaign
# taktwerk workbench: http://127.0.0.1:8470/#token=…

Open the printed URL. The token in it lets the page check projects, start and stop runs and write values; serve listens on loopback only and refuses a request whose Host is not 127.0.0.1, [::1] or localhost, or that the browser marks as cross-site, so another web page can neither read the folder (DNS rebinding) nor trigger a check.

  • Project: the folder’s project, scenario, campaign and model files; a project’s plan as check resolves it (instances, signals with units, recorders, connectors) or its problems.
  • Runs: start a project with a scenario, speed, stop, seed, overrides and a record directory. A run starts without the project’s own connectors unless asked, so it talks to no PLC by accident. Each run serves an HTTP API on a free loopback port that serve proxies; stop ends it as SIGTERM would. On Windows runs and checks go to a WSL2 distribution (Local runs on Windows).
  • Live: status, cycle, heartbeat and counters; every signal with its value, unit and age; trends of the signals picked, one chart per unit; inputs and tunables written in place; the event log.
  • Records: every run recorded below the folder; a run’s metadata, overrides, events and columns plotted (long runs thinned to a minimum and maximum per bucket); a second run overlaid dashed, with the largest difference per column.
  • Campaigns: each campaign’s runs with their values, status, stop and wall time; up to eight runs plotted together; two runs compared in the records view.
  • Devices: see below.
  • Add-ons: workspaces another program serves, on this machine or on a device, each in an isolated frame (Extending the workbench).

Devices

The Devices page works on the device registry the CLI uses: add a device (or scan a subnet for SSH hosts, or on Windows add a WSL2 distribution of the PC in one click), verify it, deploy the folder’s bundles (every taktwerk-bundle.toml below it) and drive their units.

  • Verify shows the device’s host key fingerprint first and pins it only after it was checked on the device; a changed key refuses every connection until it is pinned again.
  • A device lists its facts (architecture, glibc against the floor, systemd, install root, free space, engines), and per bundle the active release, the selected project, the unit’s state, whether the folder’s bundle of that name is the active release (or which files differ), and the journal.
  • Deploy: pick a bundle, read the plan (files to send, bytes against free space, the engine to install, what stands in the way), confirm, watch the files go. The apply sends exactly the plan shown; a plan older than 30 minutes is planned again.
  • Start, stop, restart, boot start, roll back, clean up and install unit show the agent’s plan first; start, stop and restart name the device, bundle and project and need a confirmation, as they drive the equipment the engine is connected to.
  • Live of a deployed bundle is the same Live screen, through an SSH port forward to the engine’s loopback http connector (on a WSL distribution a pipe through wsl.exe); serve reads the engine’s write token from the device.
  • Add-ons lists the add-on workspaces whose backends run on the device for its login user; Open shows one through a port forward, and it stays in the sidebar while serve runs.
  • Sync records copies the bundle’s records from the device into records/<device>/<bundle>/ of the folder, where the Records screens list them: only files missing or different there, a run still recording as far as it is written. It only reads on the device and needs the page’s token; run it again for what was recorded since (Records).

serve keeps one SSH session per device and opens it again when it drops. Logins use an SSH agent, key files (serve -i <file>, else ~/.ssh/id_ed25519, id_ecdsa, id_rsa) or a password the page asks for; a password for the login, sudo or su stays in serve’s memory until it exits or the device’s session is forgotten, never on disk. Every request that changes a device needs the page’s token and is refused when CI is set.

Isolation

  • The frame loads the backend’s page from a loopback port of its own: on this machine the backend’s, on a device a port forward over the device’s SSH connection (or wsl.exe). A different port is a different origin, so the page cannot read the workbench’s page, its storage or its token.
  • The frame is sandboxed without top navigation, popups or modals (allow-scripts allow-same-origin allow-forms allow-downloads).
  • In the desktop app the frame gets no app commands: Tauri gives its IPC to the top frame only.
  • The page talks to its own backend with its own token, never to serve, the device keys or the file system. What it asks of the workbench goes through the messages below, and a folder it asks to open is copied only after the person confirms.

The backend

A backend listens on 127.0.0.1 and announces itself on its host with a file in ${XDG_STATE_HOME:-$HOME/.local/state}/taktwerk/addons/ (any name ending in .json, mode 600), removed when it exits:

{ "taktwerk_addon": 1, "url": "http://127.0.0.1:8480/", "token": "<a fresh token>" }

serve reads these files on its own machine (TAKTWERK_ADDONS_DIR overrides the folder), and on a device when its page Add-ons looks, over SSH as the device’s login user. It then asks GET /api/info with Authorization: Bearer <token>; the answer lists the workspaces:

{ "workspaces": [{ "id": "lab", "label": "Lab", "entry": "/", "api": 1 }] }

id is [a-z0-9_-], at most 40 characters, unique on its host; entry is the page’s path; api the frame protocol it speaks. A backend that does not answer is not listed. When two backends on one host offer the same id, the one whose announcement file name sorts first is listed.

The page loads as http://127.0.0.1:<port><entry>#token=<token> and reads its token from the fragment. Its document is requested by the workbench’s page, which a browser marks Sec-Fetch-Site: same-site: the backend accepts that for its pages and refuses requests whose Host is not loopback. It must not forbid framing (no X-Frame-Options).

Deploying to devices

A bundle goes to a Linux device as a release named by its manifest’s hash. On the device, taktwerk agent verifies and activates releases under an install root and drives their systemd units, or its own built-in supervisor where systemd does not run; the host (taktwerk device, taktwerk deploy, the desktop app) calls it over SSH and copies files by SFTP.

taktwerk device add line-1 --host 192.168.1.20 --user taktwerk --privilege sudo
taktwerk device verify line-1                  # pins the host key, probes the device
taktwerk deploy plant --device line-1          # the plan
taktwerk deploy plant --device line-1 --yes
taktwerk device install-unit line-1 --yes      # once, through sudo
taktwerk device start line-1 plant --yes      # or --at 11:15 --yes: once, later
taktwerk device engine line-1 plant status     # JSON, exit 1 unless it runs (see Operating a running engine)
taktwerk device tunnel line-1 plant            # http://127.0.0.1:<port>/ to the engine

The desktop app and taktwerk serve do the same from the workbench’s Devices page, on the same registry. The bundle file, the manifest, the device layout, the units and the agent’s commands are specified in Devices and bundles; a running engine is operated with the commands of Operating a running engine.

Login. An SSH agent’s identities (SSH_AUTH_SOCK; on Windows the OpenSSH agent’s pipe), then key files (-i, else ~/.ssh/id_ed25519, id_ecdsa, id_rsa), then a password asked for on the terminal. Nothing is stored.

Host keys. The first verify shows the device’s host key fingerprint and pins it after a yes on the terminal, or when --accept-host-key <fingerprint> names it. Every later connection refuses any other key. When a device was reinstalled, check its new key and pin it with verify --accept-host-key.

Privilege. Only unit changes need root: start, stop, restart, enable, disable and install-unit with --yes run the agent through the device’s method, and so does creating a missing install root the login user cannot create. sudo runs with -S and asks for the login user’s password only when sudo does; su runs on a PTY and asks for root’s. Everything else runs as the login user, who should own the install root. Reading the journal (logs) needs the login user in the systemd-journal group.

Verify probes over one SSH exec: uname -m, the glibc version against the engines’ floor (2.25), systemd, whether the root exists and is writable, free space under it, installed engines and /etc/os-release; then agent info when an engine is installed. Problems (an unsupported architecture, no or too old glibc, a root the login user cannot use) stop a deploy; notes (no systemd, so the built-in supervisor runs the bundles; a root the deploy will create) do not.

WSL2 distributions

On Windows a WSL2 distribution of the PC is a device without SSH: every command is a wsl.exe -d <distro> -u <user> --exec sh -c …, every file the stdin or stdout of one, and root is wsl -u root, which needs neither a password nor Windows admin rights. There is no host key to pin; verify probes at once. taktwerk device add wsl-ubuntu --wsl Ubuntu (the user defaults to the distribution’s default user) or Add as device on the Devices page writes:

[[device]]
name = "wsl-ubuntu"
transport = "wsl"
distro = "Ubuntu"
user = "fabian"

WSL stops a distribution shortly after its last wsl.exe ends. The workbench keeps each WSL device’s distribution running while it is open; a deployed engine stops with it unless instanceIdleTimeout=-1 is set under [general] in %UserProfile%\.wslconfig. With systemd in the distribution ([boot] systemd=true in /etc/wsl.conf) enabled bundles start when the distribution does; without it the built-in supervisor runs them.

Scan connects to the SSH port of every address of an IPv4 subnet (at most a /16, 64 at a time, 500 ms each) and lists the hosts that answer, with their banner. It never logs in.

Deploying a release

taktwerk deploy <bundle> --device <name> probes the device, checks the bundle for its architecture, builds the manifest for this taktwerk version, reads the active release’s manifest and the unit’s state, and prints the plan: the engine to install, the files to send (those the active release lacks or holds with other content), bytes against free space, and what stands in the way. A running unit is a problem: stop it first. With --yes:

  1. Create the install root if it is missing (through root when the login user cannot).
  2. If bin/taktwerk-<version> is missing: upload the engine under a temporary name, make it executable, run it with --version and refuse it unless it reports this host’s version, then rename it.
  3. Upload the changed files to bundles/<name>/staging/<hash>/ and the manifest’s canonical bytes to .taktwerk/manifest.json there.
  4. agent activate <bundle> <hash> --yes: the device takes the files the upload left out from the active release, verifies everything and switches current.

Then, on the first deploy and when companions change, device install-unit --yes, and device start <bundle> --yes, device enable <bundle> --yes to start at boot.

The engine comes from --engine <file>, else from a directory of per-architecture engines (TAKTWERK_ENGINES, which the desktop app sets to its bundled engines/), laid out as the release builds them: x86_64-linux-gnu/taktwerk, aarch64-linux-gnu/taktwerk, armv7-linux-gnueabihf/taktwerk. A Linux taktwerk deploying to its own architecture can send itself; it must have the http feature for the unit’s --http. The released device engines are built without the host side (feature host: SSH, SFTP, device, deploy), which the agent does not need.

Live view

taktwerk device tunnel <device> <bundle> reads the bundle’s http address from its env file (through agent status), listens on a local port (--local, default any free loopback port) and forwards each connection over SSH to that address on the device; it prints the URL and runs until Ctrl-C. The write token stays on the device unless --token puts it in the URL. The workbench forwards the same way and adds the token itself. On a WSL distribution each connection is a wsl.exe running agent connect <address>, which pipes it to the engine, so neither WSL’s localhost forwarding nor a Windows process on the same port is involved.

Records

The unit records with --record-dir <root>/bundles/<bundle>/records, so every file recorder of the project writes there. taktwerk device records <device> <bundle> copies that directory by SFTP into records/<device>/<bundle>/ of the current directory (--dir for another), where taktwerk serve and its Records screens list the runs:

taktwerk device records line-1 plant          # 12 copied (48211 bytes), 3 unchanged, in ./records/line-1/plant
  • A file is copied when the local one is missing or differs: by size, then modification time, then, for a closed file, the SHA-256 its run’s SHA256SUMS lists. A copy is checked against that sum, written under a hidden .tmp name, given the device’s modification time and renamed into place.
  • Run it again at any time: it copies only what is new or grew, and continues a closed file a cut-off sync left half copied.
  • A run still recording is copied as far as it is written; the readers stop at its last complete line. Its open part is copied again while it grows, and the local .open copy goes once the device has closed the part. Per run the parts come first, CLOSED last.
  • Nothing on the device changes and nothing local is deleted but such an .open copy: parts the device’s retention removed stay.
  • --json prints the report (copied, unchanged, bytes, removed). The device’s engine must have agent records (deploy with this version).

pi.c:

#include <stdlib.h>
#include "pi.h"

typedef struct {
    int n;
    double dt;
    double integral[];
} pi_state;

int pi_init(void **handle, int n, double dt) {
    pi_state *s;
    int i;
    if (n < 1 || dt <= 0.0) return -1;
    s = malloc(sizeof *s + sizeof(double) * (size_t)n);
    if (!s) return -2;
    s->n = n;
    s->dt = dt;
    for (i = 0; i < n; i++) s->integral[i] = 0.0;
    *handle = s;
    return 0;
}

int pi_step(void *handle, const pi_gains *gains, const double *sp, const double *pv, double *u) {
    pi_state *s = handle;
    int i;
    if (!s) return -1;
    for (i = 0; i < s->n; i++) {
        double e = sp[i] - pv[i];
        s->integral[i] += gains->ki * e * s->dt;
        u[i] = gains->kp * e + s->integral[i];
    }
    return 0;
}

void pi_terminate(void *handle) {
    free(handle);
}

lowpass.c:

#include <stdlib.h>
#include "lowpass.h"

typedef struct {
    int n;
    double *alpha; /* [n], dt / (tau + dt) */
    double *x;     /* [n], filter state */
} lowpass_state;

int lowpass_init(void **h, const lowpass_dims *dims, const lowpass_params *params,
                 double step_size) {
    lowpass_state *s;
    int i;
    if (dims->n < 1 || step_size <= 0.0) return 1;
    s = calloc(1, sizeof *s);
    if (!s) return 2;
    s->n = dims->n;
    s->alpha = calloc((size_t)s->n, sizeof *s->alpha);
    s->x = calloc((size_t)s->n, sizeof *s->x);
    if (!s->alpha || !s->x) {
        lowpass_terminate(s);
        return 2;
    }
    for (i = 0; i < s->n; i++) {
        if (params->tau[i] < 0.0) {
            lowpass_terminate(s);
            return 3;
        }
        s->alpha[i] = step_size / (params->tau[i] + step_size);
        s->x[i] = params->y0[i];
    }
    *h = s;
    return 0;
}

int lowpass_step(void *h, double time, const lowpass_inputs *in,
                 const lowpass_tunables *tun, lowpass_outputs *out) {
    lowpass_state *s = h;
    int i;
    (void)time;
    for (i = 0; i < s->n; i++) {
        s->x[i] += s->alpha[i] * (in->u[i] - s->x[i]);
        out->y[i] = tun->gain * s->x[i];
    }
    return 0;
}

int lowpass_terminate(void *h) {
    lowpass_state *s = h;
    if (s) {
        free(s->alpha);
        free(s->x);
        free(s);
    }
    return 0;
}

io_model.h:

/* A model behind a single entry point: one function for init and step, called with an id and
 * two opaque byte pointers that the library casts to its input and output structs. The library
 * keeps no state; every call re-reads the sizes it reported from the caller's output struct. */
#ifndef IO_MODEL_H
#define IO_MODEL_H

#include <stdint.h>

#define IO_ID 7

#define IO_OK 0
#define IO_NULL_ARGUMENT (-1)
#define IO_UNKNOWN_VARIANT (-2)
#define IO_UNKNOWN_ID (-3)
#define IO_NOT_INITIALISED (-4)
#define IO_BAD_FLAG (-5)

/* What a successful call writes into `ready`: a true byte that is not 1. */
#define IO_TRUE_BYTE 2

typedef struct {
    int32_t *init_flag; /* 1 on the first call (init), 0 on every step */
    int32_t variant;    /* by value between two pointers: which size set to report */
    double *k;          /* scalar gain */
    double *u;          /* nu inputs */
    int32_t *counter;   /* step counter, written back by the library */
    char *title;        /* text the caller supplies, NUL-terminated */
} io_input;

typedef struct {
    char *label;      /* the title echoed back, or the library's own name if empty */
    double *y;        /* ny outputs: y = k * gain * u */
    double *gain;     /* ny x nu, row-major, filled at init */
    double *p;        /* np parameters, filled at init */
    char *names;      /* names written at init */
    int32_t *dim_nu;  /* reported at init */
    int32_t *dim_ny;  /* reported at init */
    int32_t *dim_np;  /* reported at init */
    uint8_t *ready;   /* IO_TRUE_BYTE after every successful call */
} io_output;

int io_call(int id, char *in, char *out);

#endif

io_model.c:

#include "io_model.h"

#include <stddef.h>
#include <string.h>

static int sizes(int32_t variant, int32_t *nu, int32_t *ny, int32_t *np) {
    switch (variant) {
    case 1: *nu = 2; *ny = 3; *np = 4; return 0;
    case 2: *nu = 1; *ny = 1; *np = 2; return 0;
    default: return -1;
    }
}

static void copy_text(char *dst, size_t cap, const char *src) {
    size_t n = strlen(src);
    if (n >= cap) n = cap - 1;
    memcpy(dst, src, n);
    dst[n] = '\0';
}

int io_call(int id, char *in_bytes, char *out_bytes) {
    if (id != IO_ID) return IO_UNKNOWN_ID;
    if (in_bytes == NULL || out_bytes == NULL) return IO_NULL_ARGUMENT;
    io_input *in = (io_input *)in_bytes;
    io_output *out = (io_output *)out_bytes;
    if (in->init_flag == NULL || in->k == NULL || in->u == NULL || in->counter == NULL ||
        out->y == NULL || out->gain == NULL || out->p == NULL || out->dim_nu == NULL ||
        out->dim_ny == NULL || out->dim_np == NULL || out->ready == NULL)
        return IO_NULL_ARGUMENT;
    int32_t nu, ny, np;
    if (sizes(in->variant, &nu, &ny, &np) != 0) return IO_UNKNOWN_VARIANT;

    if (*in->init_flag == 1) {
        *out->dim_nu = nu;
        *out->dim_ny = ny;
        *out->dim_np = np;
        for (int i = 0; i < ny; i++) {
            out->y[i] = 0.0;
            for (int j = 0; j < nu; j++) out->gain[i * nu + j] = (i + 1) + 0.1 * j;
        }
        for (int i = 0; i < np; i++) out->p[i] = 0.5 * i;
        if (out->label != NULL)
            copy_text(out->label, 32, (in->title != NULL && in->title[0] != '\0') ? in->title
                                                                                   : "io");
        if (out->names != NULL) copy_text(out->names, 24, "k;u;y;p");
        *in->counter = 0;
        *out->ready = IO_TRUE_BYTE;
        return IO_OK;
    }
    if (*in->init_flag != 0) return IO_BAD_FLAG;
    if (*out->dim_nu != nu || *out->dim_ny != ny || *out->dim_np != np) return IO_NOT_INITIALISED;
    for (int i = 0; i < ny; i++) {
        double acc = 0.0;
        for (int j = 0; j < nu; j++) acc += out->gain[i * nu + j] * in->u[j];
        out->y[i] = *in->k * acc;
    }
    *in->counter += 1;
    *out->ready = IO_TRUE_BYTE;
    return IO_OK;
}

read_run.py:

"""Read one recorded run with the Python standard library alone.

Usage: python3 read_run.py <run-dir>
"""

import csv
import gzip
import json
import sys
from pathlib import Path


def rows(run: Path):
    """Yield every row of the run as a dict, parts in order, header lines skipped."""
    # Closed parts, then the open one of a running engine (`.open`, renamed when closed).
    parts = [*run.glob("part-*.csv.gz"), *run.glob("part-*.csv.gz.open")]
    for part in sorted(parts):
        with gzip.open(part, "rt", newline="") as f:
            try:
                yield from csv.DictReader(f)
            except EOFError:
                pass  # the open part of a running engine ends at its last flush


def main() -> None:
    run = Path(sys.argv[1])
    meta = json.loads((run / "run.json").read_text())
    every = meta["every"]
    n, gaps, last, prev = 0, 0, None, None
    for row in rows(run):
        cycle = int(row["cycle"])
        if prev is not None and cycle != prev + every:
            gaps += 1  # rows lost between prev and cycle
        prev, last, n = cycle, row, n + 1
    print(
        f"{meta['project']}/{meta['recorder']}: {n} rows, tick {meta['tick_s']} s, "
        f"every {every}, {gaps} gaps"
    )
    print("last row:", last)
    with open(run / "events.csv", newline="") as f:
        for e in csv.DictReader(f):
            print(f"event {e['cycle']} {e['kind']} {e['source']}: {e['detail']}")


if __name__ == "__main__":
    main()

analyze.py:

"""Rank the gains of the level-loop campaign by how well each run rejects the disturbance.

    uv run --with taktwerk python examples/campaign/analyze.py examples/campaign/out/gains

For every run: the integral of the absolute level error after the disturbance step (300 s to
700 s, before the sensor freezes), the largest error in that window, and the largest error while
the sensor is frozen (700 s to 760 s) and the minute after. Per case, the runs best first.
"""

from __future__ import annotations

import sys

import taktwerk


def window(run: taktwerk.Run, start: float, end: float) -> list[int]:
    """Row indices with start <= t_engine < end."""
    return [i for i, t in enumerate(run.t_engine) if start <= t < end]


def metrics(run: taktwerk.Run) -> dict[str, float]:
    level, sp = run["plant.level"], run["ctrl.sp[0]"]
    dt = run.manifest["tick_s"]
    after = window(run, 300.0, 700.0)
    frozen = window(run, 700.0, 820.0)
    return {
        "iae": sum(abs(level[i] - sp[i]) for i in after) * dt,
        "max_err": max(abs(level[i] - sp[i]) for i in after),
        "max_err_frozen": max(abs(level[i] - sp[i]) for i in frozen),
    }


def main(out: str) -> None:
    campaign = taktwerk.read_campaign(out)
    rows = []
    for r in campaign:
        if not r.ok:
            print(f"{r.name}: {r.status}, skipped", file=sys.stderr)
            continue
        rows.append((r, metrics(r.read())))
    for case in dict.fromkeys(r.case for r, _ in rows):
        print(f"\n{case}")
        print(f"  {'run':<18} {'kp':>5} {'ki':>6} {'IAE [m s]':>10} {'max err [m]':>12} {'frozen [m]':>11}")
        for r, m in sorted((x for x in rows if x[0].case == case), key=lambda x: x[1]["iae"]):
            print(
                f"  {r.name:<18} {r.values['ctrl.kp']:>5} {r.values['ctrl.ki']:>6} "
                f"{m['iae']:>10.3f} {m['max_err']:>12.4f} {m['max_err_frozen']:>11.4f}"
            )


if __name__ == "__main__":
    if len(sys.argv) != 2:
        sys.exit(f"usage: {sys.argv[0]} <campaign output directory>")
    main(sys.argv[1])

plant-loop

A level loop on a plant with no process beside the engine: the PI of raw-pi drives the pump through a plant data system’s REST API (lab) from the level it measures, with the set point and an interlock from a PLC (plc), which also mirrors the loop and lets an operator tune the gains. A small supervisor model (supervisor/) turns the interlock and an implausible level into status bits.

  • In: the level from GET values (stale 3 s after the last good read), the set point and the interlock from the PLC.
  • Out: the pump set point, one element of ctrl.u, to PUT setpoints/pump and a watchdog (the heartbeat) to PUT setpoints/watchdog; the engine’s signals, the level, ctrl.u and the status bits mirrored into the PLC’s program.
  • Gates: both connectors hold their outputs while sup.status & 3 is set and while the engine is not running, so a stale level, which skips the ticks, holds them too. The heartbeat goes out either way.
  • Tunable sync: an operator’s change of ctrl.kp or ctrl.ki on the PLC reaches the engine and is an event in events.csv; one outside the mapping’s range is refused and overwritten with the value in force.
  • Dry run: both connectors start with writes = "dry-run"; run --write plc --write lab writes.

The folder is also a bundle with a simulated plant and stand-ins for both systems, walked through in the tutorial from the package to the device:

  • build.sh: builds the supervisor and the stand-in PLC in place, and the PI of raw-pi and the tank of campaign/tank as packages into packages/.
  • sim.toml: the loop on the tank, no connector; fault.toml, a scenario with a sensor fault and the interlock; gains.toml, a campaign of three gains over it.
  • closed-loop.toml: project.toml with writes on, as a device runs it; taktwerk-bundle.toml lists the three projects.
  • stand-in/: a bundle of its own, the PLC as a taktwerk project (plc.toml, its model in plc/) and the plant data system as a standard-library Python server (lab.py).
  • report.py: a run’s events and ranges, or two runs’ differences, with the Python package.
  • tutorial.sh: every command of the tutorial, checked; CI runs it (tutorial.yml).

Checkpoints and resume

With [engine.checkpoint] the engine saves every instance at a tick boundary every every_s of engine time and when it stops cleanly; run --resume continues from there.

[engine.checkpoint]
every_s = 60.0        # engine time between checkpoints
dir = "records"       # <dir>/<project>/checkpoints/<instance>.state; --record-dir replaces it

A checkpoint holds the model’s state (an FMU with canSerializeFMUState; a raw C model keeps none), the instance’s tunables and the external inputs it reads, with the hashes of the project file, the run’s overrides and seed and the model package, the tick, the engine time and the host’s UTC. Each file is replaced whole (temporary file, sync, rename). Saving an FMU’s state allocates in the library, so the tick before a checkpoint may run long: watch taktwerk.overruns with a short tick and a large model.

taktwerk run project.toml --resume [--max-age 1h] restores each instance whose checkpoint matches all three hashes, is younger than --max-age and is of the newest tick among them: cycle numbers and engine time go on from that tick, the tunables in force become start values and the inputs are preset (one with an age limit still waits for a fresh write). Every other instance starts from init at that time and the log says why; a raw model gets its tunables and inputs back and starts from init. Each instance gets a resume event in events.csv, and run.json records the resume in its invocation. A library that refuses a matching state fails the start; delete its file to start that instance fresh. A scenario run does not resume.

Commissioning

A project goes onto a plant in steps, each one changing one thing: first the engine checks what it would connect to, then it reads the plant and writes nothing, then it writes. No step needs another binary or another project format; a bundle may carry one project file per step (Applications as packages).

flowchart LR
  A["check<br/>nothing contacted"] --> B["check --live<br/>every item verified"]
  B --> C["run, writes = dry-run<br/>reads, logs writes"]
  C --> D["check --live --write<br/>writability"]
  D --> E["run --write<br/>or writes = on"]

1. Offline

taktwerk check project.toml

Loads every model, binds every dimension, resolves every signal and checks every connector’s settings and map against the plan; contacts nothing. A project whose opcua-client or rest map writes and that does not say writes = "on" or "dry-run" is refused here, so no project starts writing to a plant, or stops, without saying so.

Run the project as a simulation first: the plant connectors replaced by a plant model in the image, or the project with --no-connectors and a scenario.

2. The endpoints

taktwerk check project.toml --live

Runs the verification every opcua-client session runs at its start against the live server, for every connector: each mapped node exists, has the signal’s type and shape, is readable, and is writable where the connector writes with writes on. It writes nothing. The report has a row per node and the connector’s own problems (an unreachable endpoint, a missing writes); --json gives the same as one object. A from-server dimension is resolved only here.

3. Reading, not writing

With writes = "dry-run" in the connector:

taktwerk run project.toml

Inputs and plain tunables are read as usual, the models step on plant data, the write gate is evaluated, and at most once a second the connector logs what it would write:

dry run, not written: plant.u (ns=4;s=Plant.u) = 0.25, …

Compare the logged values with what the plant runs today. Synced tunables stay idle in a dry run. Watch the engine meanwhile:

taktwerk engine status --url 127.0.0.1:8480 --expect 'taktwerk.overruns == 0' \
  --expect 'est.status & 255 == 0'
taktwerk engine read 'plant.*' --for 300          # mean, sd, min, max per signal over 5 min

(--http 127.0.0.1:8480 on the run, or an http connector; on a device the bundle’s unit has one, see Operating a running engine.)

A rest connector takes the same writes: a dry run reads, evaluates the gate and sends nothing, the heartbeat included, logging what it would send.

4. Writing

taktwerk check project.toml --live --write plc     # writability, as that run would write
taktwerk run project.toml --write plc              # writes on for this run

--write <id> turns a dry-run connector’s writes on for one run and is recorded in run.json’s invocation; it is refused while CI is set. Once the loop is accepted, set writes = "on" in the project (or deploy the bundle’s next project file).

A set point written to the engine and read back with its event:

taktwerk engine set ctl.sp 1.2                     # the plan, with the current value
taktwerk engine set ctl.sp 1.2 --yes               # write, wait for the tick, read back

Records of commissioning

Each step’s run is a run record when the project has a recorder: the project’s hash, every override, --write, the tunables’ values at every cycle and every gate change. @io records exactly what the engine exchanged with the plant.

Operating a running engine

The engine commands operate a running engine through its http connector and print JSON, so a checklist or a plant-side agent needs no scripts of its own. Three ways to the same operations:

taktwerk engine status --url 127.0.0.1:8480                        # any engine with --http
taktwerk agent engine plant status --root /opt/taktwerk             # on the device: the bundle's env
taktwerk device engine line-1 plant status                          # from a computer, over SSH

agent engine reads the bundle’s address and token from its env file; device engine runs it over SSH, so neither needs a port forward or the token on the computer. taktwerk engine takes --url and, for writes, --token-file, TAKTWERK_HTTP_TOKEN or the token file the engine wrote. Reads need no token.

Status for a checklist. status reads every signal once and watches the heartbeat for up to --heartbeat-timeout seconds. It passes when the status is running (1), the heartbeat advances and every --expect holds; it exits 1 otherwise, and the report’s failed says why.

Start at a set time. device start <device> <bundle> --at 11:15 --yes (or --in 15m) arms taktwerk-start@<bundle>.timer on the device, a transient systemd timer that starts the engine unit once. On the device the same is agent start-at <bundle> --in 15m --yes (or --at, by the device’s clock), through root.

Security model

taktwerk has four surfaces a network can reach: the OPC UA server, the http connector, taktwerk serve and SSH to devices. Client connectors reach out to a PLC or a plant data system with credentials from the environment or a file. The project file holds no secret: inline passwords are refused; a rest login body takes them as ${NAME} from the environment.

OPC UA server

Open by default: anonymous, writable, no encryption, all interfaces, so any client on a closed machine network is a UI. On any other network:

  • bind endpoint to one interface;
  • anonymous = false, or anonymous_write = false for read-only anonymous sessions;
  • users with passwords from password_env or password_file, write = false for viewers;
  • security = ["sign-encrypt"] and the policies to offer; client certificates are trusted only from <pki_dir>/trusted/ unless trust_client_certs.

A user’s password on a "none" endpoint is encrypted with the server certificate, the values are not. Inputs and tunables are writable to identities with write access, through UserAccessLevel; outputs and system signals are read-only for everyone. Every write passes the image’s type, length and range checks; a refused tunable write is logged in events.csv. Keys in OPC UA server.

http connector

  • Reading needs no credentials. Writes and stop need writes = true and Authorization: Bearer <token>: TAKTWERK_HTTP_TOKEN, else a fresh token written to token_file (default $XDG_RUNTIME_DIR/taktwerk/http-<port>.token, mode 0600) and removed at shutdown.
  • No TLS. It listens on loopback by default; keep it there or on a network you trust.
  • On loopback a request is refused (403) unless its Host is a loopback address or localhost and no browser marks it cross-site (Sec-Fetch-Site), so a web page the operator opens cannot reach the engine through DNS rebinding.

On a device the bundle’s unit serves it on a loopback port with the token in the bundle’s env file; a host reaches it through an SSH port forward and reads the token over SSH.

taktwerk serve

  • Listens on loopback only; another address is refused.
  • A token (TAKTWERK_SERVE_TOKEN, else generated and printed in the URL’s fragment) is needed to check a project (it loads model libraries), start and stop runs, write values, shut down, and for every request that changes a device. Requests that change a device are refused when CI is set.
  • The same Host and Sec-Fetch-Site checks as the http connector.
  • Runs start without the project’s connectors unless asked, so the workbench talks to no plant by accident.
  • Passwords for SSH logins, sudo or su stay in memory until serve exits or the device’s session is forgotten; nothing is written to disk.

Devices

  • Every control call is an SSH exec, every file an SFTP transfer, the live view an SSH port forward: SSH authenticates and encrypts.
  • Host keys are pinned at the first verify and checked on every connection; a changed key is refused until it is pinned again (device verify --accept-host-key).
  • Logins use an SSH agent, key files, or a password asked for and never stored. devices.toml holds no secret.
  • The login user owns the install root; only unit changes and creating a missing root run as root, through the device’s privilege (none, sudo, su).
  • Secrets for the engine (password_env, token_env, TAKTWERK_HTTP_TOKEN) live in the bundle’s env file on the device, mode 600, which a deploy never rewrites.
  • Every mutating command is a dry run without --yes, and --yes is refused when CI is set.

See Deploying to devices.

Client connectors

  • opcua-client: security = "sign" or "sign-encrypt" (Basic256Sha256), credentials from password_env or password_file, server certificates trusted only from <pki_dir>/trusted/ unless trust_server_certs.
  • rest: plain HTTP only; https:// is refused. For a server that requires TLS, put a TLS proxy beside the engine. Credentials from the environment (Auth).
  • Both write to a plant only when the project says writes = "on", or for one run run --write <id>; "dry-run" logs what they would write (Dry run).

What taktwerk does not do

  • Models run in the engine’s process, with its privileges; a package is trusted code.
  • The engine is not a safety controller: the PLC owns the safe state (the safety contract).
  • No TLS on the http connector, serve or rest.

Versioning and compatibility

One version

Every crate, the taktwerk binary, the desktop app and the Python package carry one version number, and a release tag vX.Y.Z (SemVer) releases them together: the CLI archives, the workbench installers and a SHA256SUMS of every file, with the release’s section of CHANGELOG.md as its notes. The release refuses a tag that differs from the crates’ or the app’s version. taktwerk --version prints it; run.json, campaign.json, a bundle manifest and GET /api/info record it.

The workbench deploys the engine of its own version, which its installer carries for every device architecture, so the app and the engines it deploys never disagree on a format.

Every key in dims, parameters, inputs, outputs and tunables must name a dimension or a variable of that causality in the model.

dims

  • n = 3: a fixed length, checked against the dimension’s min and max.
  • n = "from-server": the length is discovered at init. The model needs a one-dimensional variable of shape [n]; the engine asks each connector for the length of the external item mapped to that variable’s signal. The OPC UA client answers for nodes in its map, the REST client for arrays its reads point at.
  • Unbound: the model’s default; without one, init fails.

parameters

Start values of parameters and tunables. Unset ones keep the model’s value: the FMU’s start value, or a raw descriptor’s start, zero without one.

  • A scalar takes a number or a boolean. Integers convert to floats; floats never convert to integers.
  • An array takes nested arrays, one level per dimension, first index outermost: A = [[1.0, 0.0], [0.0, 1.0]]. The engine stores it in the variable’s layout.
  • An array also takes one flat array of the full length, taken as already stored in the variable’s layout: A = [1.0, 0.0, 0.0, 1.0].

Ranges

A numeric tunable may admit only a range of values: the model declares it (an FMU’s min and max, its own or its declared type’s; a raw descriptor’s range), and ranges replaces it for one instance.

ranges = { kp = [0.0, 10.0], sp = [[0, 1], [0, 2]] }  # sp: one range per element
  • Bounds are inclusive; -inf or inf leaves a side open.
  • check refuses a start value outside the range (from parameters, --set or the model).
  • A write outside the range is refused like a type mismatch: the value in force stays, the writer gets an error (OPC UA BadOutOfRange), and events.csv gets refused <value> by <writer>: outside the range [lo, hi] (element i outside … for an array). A NaN is outside every range. A scenario event writing outside it fails the run.
  • Instances sharing one tunable signal admit what all their ranges admit.

Faults

on_error = "safe"          # or "hold"
safe = { u = 0.0 }         # every output, typed like `parameters`
reinit_after_s = 10.0      # optional; writing taktwerk.instance.<id>.reinit also re-inits

A failed step of such an instance holds its outputs or publishes safe, sets status to degraded and holds the heartbeat until it runs again; see Faults.

inputs, outputs, tunables

Each maps a variable to a signal name. Unmapped variables get <instance>.<variable>. An input binding is either a signal name or a table:

inputs = { y = "plant.y" }                                   # signal only
inputs = { y = { signal = "plant.y", max_age_ms = 50.0 } }   # with an age limit

max_age_ms overrides engine.input_max_age_ms for that input. It is refused on a wired input (one some instance outputs). When several instances consume one external signal, the explicit limits they set must agree; one explicit limit wins over the default. See Concepts for wiring rules.

A one-dimensional input may instead be composed element by element from a list with one source per element, in element order:

inputs = { y = ["plc.p", "est.mu", { signal = "plc.t", max_age_ms = 50.0 }, "est.v[1]"] }
  • name is a scalar signal of the input’s type: another instance’s scalar output (wired) or an external input, created when no one else uses it.
  • name[i] is element i, counted from 0, of another instance’s one-dimensional output of the input’s type.
  • { signal, max_age_ms } sets an age limit on one external element, as above.
  • The list’s length must equal the input’s bound length. Multi-dimensional and text inputs, outputs and tunables cannot be composed.
  • The composed value is the signal <instance>.<input>, read-only, stored each time the instance is about to step (and before its init), so a connector shows what the model received. taktwerk check lists every composed input with its element sources.

A scalar input takes one element the same way, without a list:

inputs = { n_st = "mpc.u[0]" }

It is a composed input of one element, with the same rules and the same read-only signal <instance>.<input>. A name with [ or ] that is not an element of another instance’s one-dimensional output is refused: no signal name contains brackets, so it never becomes an external input or a connector’s node mapping.

Connectors

A connector syncs part of the process image with the outside. At init the engine builds each connector from its [[connector]] table, asks it for "from-server" lengths, builds the image and lets each connector verify its mapping (fail-closed).   • Certificates: the server certificate and key (own/cert.der, private/private.pem) are generated in pki_dir when a secure endpoint or a user needs them. A client certificate is refused into <pki_dir>/rejected/ until moved to <pki_dir>/trusted/, unless trust_client_certs is set.
  • Passwords come from an environment variable (password_env) or a file (password_file, one trailing line break dropped; relative to the working directory like pki_dir), never from the project file. They are read at start. On a "none" endpoint the client encrypts the password with the server certificate (Basic256Sha256), so it never travels in clear; the values themselves do.
  • Write access: a user with write = false, or an anonymous session with anonymous_write = false, sees inputs and tunables read-only (their UserAccessLevel) and a write is refused with BadUserAccessDenied. Reads and recorder pulls are open to every accepted identity. Outputs and system signals are read-only for everyone.

The server is open by default: anonymous, writable, no encryption, all interfaces. On any network other than a closed machine network, bind it to one interface, turn off anonymous (or anonymous_write), add users and offer only secure endpoints. taktwerk tui and taktwerk record connect to such a server with --security, --policy, --user and the password in TAKTWERK_UA_PASSWORD.

Nodes

  • Every signal is a variable node with NodeId ns=<index of namespace>;s=<signal name>, for example ns=2;s=plant.y (the index is assigned by the server; read it from the server’s namespace array, or address the node by URI as nsu=urn:taktwerk;s=plant.y).
  • The browse path splits the name on . into folders under Objects: plant.y is Objects/plant/y, taktwerk.heartbeat is Objects/taktwerk/heartbeat.
  • Data types: f64 Double, f32 Float, i64 Int64, i32 Int32, i16 Int16, i8 SByte, u64 UInt64, u32 UInt32, u16 UInt16, u8 Byte, bool Boolean.
  • A scalar has ValueRank −1. An array has its rank and ArrayDimensions; matrix elements are sent in row-major order whatever the model’s storage layout.
  • A text signal is a scalar String node. A read gives the bytes up to the first NUL, decoded as UTF-8 (invalid sequences are replaced, not refused). A write takes a String of at most capacity − 1 UTF-8 bytes, copies it and zero-fills the rest; a longer one is refused with BadOutOfRange and one containing NUL with BadInvalidArgument, never truncated.
  • Outputs and system signals are read-only. Inputs and tunables are writable; a write goes to the image and is picked up at the next tick.
  • Every node follows each published tick, with the time the value was written into the image as its source timestamp. A value never written has status UncertainInitialValue.

Map

Each key is a signal of the image; each value a NodeId: ns=<index>;s=<id>, nsu=<uri>;s=<id> (the namespace is resolved by URI on every session), or the i=, g=, b= forms. Unmapped signals are not synced.

  • Inputs and tunables are read from their nodes, one bulk Read every sync_period_ms.
  • Tunables with sync = true are synced both ways in the same period.
  • Outputs and system signals are written to theirs, one bulk Write per published tick.
  • An entry with mirror = true is written whatever the signal’s direction and never read: an input another connector writes, or a tunable, shown on the peer (taktwerk plc-mirror generates such a map).

Every Read and Write, the verification reads included, is split into requests of at most max_nodes_per_request nodes and at most the server’s advertised MaxNodesPerRead and MaxNodesPerWrite (read at every session; 0 or unreadable means none). Set the key for a server that refuses large requests without advertising its limit.

Conversion and checks

A map entry may be a table instead of a NodeId string:

[connector.map]
"plant.y" = { node = "ns=4;s=Plant.y", scale = 0.01, offset = 0.0, min = 0.0, max = 1.0, max_unchanged_s = 60 }

"mpc.cost" = { node = "ns=4;s=Plant.cost", gated = false }
keydefaultmeaning

  • An input is converted after the read, element by element: value = raw · scale + offset. An output is converted back before the write: raw = (value − offset) / scale. min and max bound the signal value, in the engine’s units, on both sides.
  • An array is converted and checked element by element; one invalid element makes the whole value invalid.
  • With a range, NaN and infinities are invalid.
  • An invalid input (out of range, or unchanged for longer than max_unchanged_s, compared bit for bit) is not written to the image: it ages and turns stale by its max_age_ms, as after a bad read. The problem is logged once until it clears.
  • An invalid gated output closes the gate. An invalid output without a gate, or with gated = false, is not written: the node holds its last value, the problem is logged once. Nothing is clamped unless the entry says clamp = true: then a finite value outside the range goes out as the nearer bound (a round-off below 0 as 0), and NaN and infinities stay invalid.

Verification

Every session is verified before it syncs: the first at init, every reconnect again. For each mapped node the client reads DataType, ValueRank, ArrayDimensions, AccessLevel and the value, and refuses the session listing every mismatch:

  • the node exists and its DataType is the signal’s type (String for a text signal); a vendor-defined DataType (a PLC’s STRING(n), say) counts as the built-in type it subtypes, followed along HasSubtype up to 8 levels, once per type and session;
  • a scalar signal maps to a scalar node, an array signal to an array node with the same element count (from ArrayDimensions, or the current value when the server reports none);
  • the node is readable, and writable when the engine writes it (outputs, system signals, mirrored and synced signals) and writes = "on";
  • the sync_epoch node is a UInt32 scalar, readable and writable.

A text signal maps to a scalar String node, typically a PLC STRING(n), and follows the server’s rules: a remote string longer than capacity − 1 bytes is not read into the image (the input ages, the problem is logged), and the PLC refuses an output longer than its own n. Array elements travel in the signal’s storage order. At init a refusal, or an unreachable server, stops the engine before the first tick. After a reconnect a refusal is logged and retried with backoff.

Dry run

A client whose map writes any node (an output, a system signal, a mirrored or synced signal) needs writes: without it check and run refuse the project, so no connector starts writing to a plant, or stops, without the project saying so.

  • writes = "on" writes.
  • writes = "dry-run" writes nothing: inputs and plain tunables are read as usual, the gate is evaluated, and at most once a second the client logs what it would write (dry run, not written: plant.u (ns=4;s=Plant.u) = 0.25, …). Synced tunables are idle, so no peer value is forwarded that the engine never seeded. Writability is not verified.

taktwerk run --write plc turns a dry-run connector’s writes on for one run (recorded in run.json); taktwerk check --live --write plc verifies writability as that run would. The workflow on a plant: check --live, run with writes = "dry-run" and read the log, then check --live --write plc and run --write plc, or set writes = "on".

Tunable sync

A tunable an operator edits on the server, typically a PLC program’s variable, with the engine’s value in force always shown there:

[[connector]]
id = "plc"
kind = "opcua-client"
endpoint = "opc.tcp://192.168.0.10:4840"
sync_epoch = "ns=4;s=Plant.sync_epoch"   # UInt32, the program leaves it alone

[connector.map]
"pi.r" = { node = "ns=4;s=Plant.r", min = 0, max = 80, sync = true }

Each sync_period_ms the client reads every synced node and the epoch, compares each node with the value it last synced (L, bit for bit, before scale and offset) and with the tunable in the image:

  • Seed: no L yet: the node gets the tunable’s value.
  • Forward: the node changed: an operator wrote it. The value is converted and checked like a read input and written into the image as a tunable write by the connector (events.csv: <old> -> <new> by plc). A value out of min/max, or not finite with a range, is refused (refused <value> by plc: <reason>) and the node is overwritten with the value in force in the next period.
  • Follow: the tunable changed elsewhere (another connector, a scenario): the node gets it. Both changed: the operator wins.

Every new session, and every period the epoch reads back other than the one last written, seeds every synced node instead of forwarding it, and writes a new nonzero epoch in the same Write; the epoch counts once that write succeeded. So a program that restarted or was re-initialised (its variables back at their initial values) is seeded with the values in force, never read back into the engine. An unreadable epoch, or a node that cannot be read, holds the routes. Syncing starts once the engine published its first tick, when every tunable holds its start value. The write gate does not apply: tunables stay editable while outputs are held. max_unchanged_s does not apply to a synced tunable.

Write gate

A gate table holds the connector’s outputs while something is wrong, so the PLC keeps its last values instead of taking bad ones:

[connector.gate]
open_after = 5                                  # good ticks in a row before writes resume
conditions = [
  { signal = "mpc.status", mask = 13 },         # closed while mpc.status & 13 != 0
  { signal = "plant.mode", min = 1, max = 1 },  # closed while not finite or outside [1, 1]
]

The gate is evaluated once per published tick the connector writes. It is good when

  • the engine status is running and the heartbeat advanced since the last tick (a skipped tick, a stopped engine or a repeated tick is bad);
  • no condition holds: mask on an integer or bool scalar, min/max on a numeric scalar;
  • every gated output is finite and within its mapping’s min and max.

One bad tick closes it; it opens after open_after (default 1) good ticks in a row. It starts closed and closes when the session is lost. While it is closed no gated output is written, so the PLC holds their last values; system signals (taktwerk.heartbeat, taktwerk.status) are always written, so the PLC sees the engine and owns the safe state.

With a gate, every output is gated unless its map entry says gated = false: an output added to the map later is safe by default. Without a gate nothing is held.

Each change is an event (gate: open or closed: <reason>), and the gate publishes system signals under <prefix>.connector.<id>.:

signaltypemeaning

gate_opensu64times the gate opened
gate_closesu64times the gate closed

Reconnect and staleness

A lost session is closed and reconnected with exponential backoff. While disconnected, inputs are not written, so they age; with a max_age_ms the engine turns them stale and skips ticks until reads resume. An input read with a bad status, or a value that does not fit the signal, leaves that signal aging as well; the problem is logged once until it clears.

Stamp

stamp = "receive" stamps an input with the time the read response arrived: an input is as fresh as the last successful read. stamp = "source" uses the server’s source timestamp (or the receive time when it sends none). Servers that stamp a value only when it changes make a constant input look old under "source".

from-server

For an instance dimension bound "from-server", the client answers with the length of the node mapped to the dimension’s signal (its ArrayDimensions, else its current value’s length). taktwerk check contacts no server, so a project with such a dimension checks with check --live.

Writes cannot be checked without writing: only their direction and settings are. An unreachable server stops the engine before the first tick. Auth

Secrets come from the environment:

auth = { scheme = "basic", user = "op", password_env = "LAB_PASSWORD" }
auth = { scheme = "bearer", token_env = "LAB_TOKEN" }
auth = { scheme = "header", name = "X-Api-Key", value_env = "LAB_KEY" }
auth = { scheme = "login", path = "auth/login", body = { user = "op", password = "${LAB_PASSWORD}" }, token = "/access_token" }

basic takes the password from password_env or password_file (exactly one; an inline password is refused). login sends POST <path> with the JSON body (${NAME} in a string is replaced by the variable) and uses the string at the token pointer of the answer as a bearer token; a request answered 401 logs in again and is sent once more. A failed login is retried after period_ms. On a device the variables go into the bundle’s env file.

Transport

Plain HTTP/1.1 on one keep-alive connection; https:// is refused (put a TLS proxy beside the engine for a server that requires it). A request the connection gave back unsent is sent again on a new connection; a GET that broke on a reused connection is sent once more; a write that went out is never repeated. A request that gets no answer within its timeout marks the server lost: the gate closes, inputs age, and the connector retries with backoff. Answers over 4 MiB are refused. The connector works in wall time and is refused off real time.

Boundary

The connector maps fixed paths to signals. What a plant data system’s API needs beyond that stays a companion process of the bundle: ids looked up at run time (a variable’s id by its name, the running batch or process), paths that change during a run, reads that need several dependent requests, sessions other than a token from one login, set point ramps, rate limits and deadbands, TLS. The companion talks to the plant system on one side and to the engine on the other, through the OPC UA server or a rest connector pointed at itself.

Per run: the common scenario, then the campaign’s set, stop and events, then the case’s scenario and set, then the grid point’s and the sample’s values. Later values win; stop conditions and events add up. The result is the run’s run.toml, a scenario file that taktwerk run --scenario reruns alone.

CLI reference

taktwerk logs to stderr. RUST_LOG sets the filter; the default is info for run and warn otherwise. Exit status is non-zero when a command fails, when check finds a problem, and when run ends on a model or connector failure.

On Windows taktwerk is a remote client: models are not loaded, so inspect and new refuse and check reports each model as a problem; run, campaign --write and agent refuse; serve offers files, records, campaign results and devices, and runs and checks projects in a WSL2 distribution when one is installed. device, deploy, tui, record, import-header and a campaign’s plan work as on Linux.

The help blocks below are the program’s own --help output, kept so by a test (TAKTWERK_BLESS=1 cargo test -p taktwerk --test cli_doc rewrites them).

  <PROJECT>
          Project file

Options:

          The program that declares the variables

          Write the files; without it, only say which would change

      --check
          Write nothing; exit non-zero when a file is missing or differs

  -h, --help
          Print help (see a summary with '-h')

taktwerk plc-mirror line.toml --node-prefix 'ns=4;s=' --all-tunables ctrl --write writes, beside the project:

  • line.plc-prg.st: the declaration of an IEC 61131-3 program with one variable per mirrored signal: the engine’s own (taktwerk.heartbeat, status, cycle, overruns, stale), every external input (also an element source of a composed input), every instance output, and the tunables named by --tunable or --all-tunables. a.b is a_b unless --rename a.b=NAME; a reserved word or a case-insensitive collision (ctrl.k and ctrl.K) is refused, naming the signal. Types keep the node’s data type (f64 LREAL, u64 ULINT, …), an array has one ARRAY dimension per dimension, and a text signal of capacity n (NUL included) is a STRING(n-1).
  • line.routes.toml: the [connector.map] of an opcua-client connector, one entry per variable, NodeId <node-prefix><program>.<variable>. Outputs and the engine’s signals are plain entries, inputs and tunables mirror = true (written, never read). Append the file to the connector’s table.

--from-plc 'plc.*' names external inputs the PLC itself provides (a set point, an interlock word), by glob as a recorder’s patterns: each is a plain entry the connector reads, declared in its own section as the PLC’s to write. A pattern that matches no external input, or matches any other signal, is refused.

With --sync-tunables every mirrored tunable is a sync = true entry instead: an operator may change it on the PLC. The program then declares taktwerk_sync_epoch : UDINT, which the connector names as sync_epoch (the line is in the map’s header).

--dialect attributes puts {attribute 'symbol' := 'readwrite'} before the program, for runtimes that serve a program’s variables on their OPC UA server through that attribute; plain (the default) is IEC 61131-3 alone. A raw package is read, not loaded (its descriptor alone, so no library is needed); an FMU is opened as inspect opens it. Both files name the project’s and every model file’s SHA-256; --check fails when either is stale.

Model package

A model package is what taktwerk runs: compiled code and a declaration of its interface. It comes in one of two forms, both read by the same engine with the same semantics:

formkindwhat it isdetail
FMU"fmi"an FMI 3 (or FMI 2) co-simulation FMU, as an .fmu archive or an extracted directoryFMI 3
raw"raw"a directory with a C shared library per architecture and a descriptor, taktwerk-model.tomlHand-written C, the descriptor

taktwerk defines no ABI of its own: an FMU follows the FMI standard, a raw library keeps its C interface and the descriptor says how to call it. New C code follows the recommended shape, which the importer reads without review.

Files and identity

<package>/                        a raw package
  taktwerk-model.toml             the descriptor
  lib/x86_64/<name>.so            one library per architecture: x86_64, aarch64, arm
  lib/aarch64/<name>.so
  lib/arm/<name>.so               32-bit hard-float ARM

<model>.fmu                       an FMU: modelDescription.xml, binaries/<platform>/, resources/

A package is identified by its content: the SHA-256 over the files that make it (a raw package’s descriptor and lib/; an FMU archive; an extracted FMU’s modelDescription.xml, binaries/ and resources/), as run.json records it (see run.json) and a campaign’s spec hash covers it. Other files in the directory (sources, build scripts, records, campaigns) are not part of the package. taktwerk reads no version number of a package and the descriptor carries no format number; a descriptor key taktwerk does not know is refused, not ignored.

What a package declares

  • A name, informational.

  • Dimensions: named sizes with an optional min, max and default. An FMU declares them as structural parameters, a descriptor as [[dimensions]]. Every instance binds each one; a dimension without a default must be bound by the project.

  • Variables, each with a name (unique in the model), a causality, an element type, a shape and a layout, and optionally a unit and a description:

    causalitythe enginethe model
    inputwrites it before every stepreads it
    outputreads it after every stepwrites it every step
    parametersets it once, before initreads it; never changes for the instance
    tunablesets it before init, and again before the next step after a changereads it every step

  • Element types: f64, f32, i64, i32, i16, i8, u64, u32, u16, u8, bool, and text (below).

  • Shape: empty for a scalar, else one entry per axis: a dimension name or a literal length ([n], [nx, nx], [3]). Layout: row-major or column-major for more than one axis; FMI 3 arrays are row-major.

  • Instances: multiple when every instance keeps its own state (behind a handle, or in structs the engine owns per instance); single when the library keeps state in globals, so each further instance loads a private copy of the library. An FMU declares single with canBeInstantiatedOnlyOncePerProcess.

Conventions

  • Text is a u8 variable of one literal length, the capacity with the terminating NUL included. The image holds bytes; connectors, check, inspect and the TUI show a string, and a connector refuses text that does not fit. An FMU’s String is text of 256 bytes or the capacity a taktwerk annotation gives; a raw char * member of literal length is text.
  • Start values: an input, parameter or tunable starts at its declared start when nothing else sets it: an FMU’s start, a descriptor’s start, zero for a raw variable without one. The project’s parameters win over it, a scenario’s overrides over those, --set over everything. After init the image holds every tunable’s value from the model.
  • Ranges: a numeric tunable may declare the values it admits (an FMU’s min and max, a descriptor’s range); the image refuses a write outside it and logs the refusal. A project may replace it per instance.
  • Seeds: a model that draws random numbers takes its seed through a numeric scalar parameter or tunable named seed. A run with --seed N gives instance id the value splitmix64(N xor fnv1a(id)), reduced to what the variable holds exactly; a project names another variable with seed_var. No annotation is needed. See Seeds.
  • Time: a step receives the engine time it advances from and advances by the instance’s step size, every × tick_ms. After skipped ticks the next step’s time jumps; a model that integrates reads the gap from time (see Stale inputs).
  • Status: the engine does not interpret a model’s outputs. A package that can produce outputs a consumer must not use should say so in an integer status output, one bit per reason, so a connector’s write gate can hold them. See Status and the write gate for the recommended bits.

Calling contract

  • Lifecycle per instance: load (the library, or the FMU’s binary for the running platform), instantiate with the bound dimensions and parameters, init once with the instance’s inputs and tunables, one step per period, terminate once, also after an error. Instances init and step in the project’s declared order.
  • Threads: a raw library’s init, steps and terminate, and an FMU’s initialization, steps and termination, are called on the engine’s cycle thread, after its real-time settings apply. Loading and an FMU’s instantiation happen before.
  • Memory: the engine owns every buffer the model exchanges, sizes it at init from the bound dimensions and keeps its address for the instance’s lifetime, so init may keep pointers. A library may allocate at init, never per step; no blocking I/O in a step.
  • Errors: a raw call that returns a code outside ok_codes (default 0), or an FMU status other than OK and Warning (or a step that asks to terminate), fails the call. By default that stops the engine (fail-stop) and the service manager restarts it; an instance with on_error = "hold" or "safe" is held instead while the others step, and may be re-initialised (Faults). A step that cannot continue fails; a step that can continue but whose outputs are not valid succeeds and says so in its status.
  • Sizes: the project is the size authority. A raw library that reports its own lengths has them checked after init and every step, never adopted (reported lengths).

Checking a package

taktwerk inspect <package> --kind raw     # or <model>.fmu --kind fmi
taktwerk new <package> --kind raw -o try.toml
taktwerk check try.toml

inspect prints the interface exactly as the engine reads it. Testing a package goes on from there.

Run record format

A run record is what one recorder writes for one run of an engine: a directory of plain files that any tool can read with gzip, CSV and JSON. The engine’s own file sink and taktwerk record write the same files; taktwerk serve, the Python package and taktwerk-record read them. This page specifies format 1, the format in run.json. How a recorder chooses what to record is in Recording.

Layout

<dir>/<project>/<recorder>/<run-id>/
  run.json                   what was recorded and how the run was started
  part-0001.csv.gz           closed parts: never change again
  part-0002.csv.gz.open      the part being written; renamed without .open once closed
  events.csv                 the run's events
  SHA256SUMS                 one line per closed file
  CLOSED                     empty; written last, once the run is closed
  • <dir> is the recorder’s dir (or --record-dir), or --dir of taktwerk record.
  • <project> is the project file’s name without extension; <recorder> the recorder’s id (ASCII letters, digits, _, -).
  • <run-id> is YYYYMMDDTHHMMSSZ-<hash>: the recorder host’s UTC when the run opened and the first 8 hex digits of the project file’s SHA-256. A second run of the same second gets -2, then -3, and so on.
  • Parts are numbered from 0001, four digits at least; the order of the numbers is the order of the rows.

Life of a run

  1. The run opens: the directory, run.json (without end), events.csv with its header and part-0001.csv.gz.open.
  2. Rows go into the open part. When it closes (rotation or the end of the run) it is finished, synced to disk and renamed to part-NNNN.csv.gz, and <sha256> part-NNNN.csv.gz is appended to SHA256SUMS; the next part opens.
  3. The run closes: the last part closes, run.json is replaced with end, the lines for events.csv and run.json are appended to SHA256SUMS, and CLOSED is created.
  • run.json is written as run.json.tmp and renamed, never rewritten in place.
  • SHA256SUMS lines are <64 lowercase hex> <file name>, the format sha256sum -c checks.
  • A run without CLOSED is still recording, or was cut off (SIGKILL, a crash, power). Its last part keeps the .open name and ends at its last flush.
  • Retention deletes closed parts of a recorder’s runs, oldest first; their lines stay in SHA256SUMS (sha256sum -c --ignore-missing). run.json, events.csv and SHA256SUMS are never deleted.
  • Files ending in .tmp are temporary: readers and sync tools ignore them.

Parts

A part is a gzip file of CSV text (RFC 4180 quoting, \n line ends): a header line, then one line per row. The gzip header carries no file name and modification time 0.

cycle,t_engine,filt.y[0],filt.y[1],filt.y[2],filt.gain,taktwerk.status
0,0.0,0.9090909090909091,1.9607843137254901,2.9702970297029703,1.0,1
1,0.01,0.8264462809917356,1.9223375624759707,2.9408881482207625,1.0,1
  • Header: cycle, t_engine, then each column’s name from run.json, in that order. Every part repeats it. A scalar’s name is its signal; an array element is <signal>[i], a matrix element <signal>[i,j] with logical indices, quoted since it holds a comma; a text signal is one column named like its signal.
  • cycle: the tick, an unsigned integer. Consecutive rows differ by every; a larger step is a loss (see Gaps and drops). Skipped ticks have rows.
  • t_engine: start_time + cycle · tick_s, seconds.
  • Floats (f64, f32): the shortest text that reads back to the same value: 0.1, 1e-7, 1.0, NaN, inf, -inf.
  • Integers: decimal. Booleans: 0 or 1.
  • Text: the bytes up to the first NUL, as UTF-8 (invalid sequences replaced), quoted when they hold a comma, a quote, CR or LF.
  • The stream is flushed every 10 s of engine time and at close, never on wall time, so the same rows give the same bytes.
  • A part still being written, or cut off, ends at its last flush without the gzip trailer: a reader decodes until the stream ends and keeps the complete lines.

events.csv

A puller’s gap line is written when the gap is found, so it may follow an event of a later cycle. source and detail are quoted when they need it. Flushed about once a second on wall time, so a run still recording may end in half a line.

Tunables

events.csv holds the value of every tunable at every cycle:

  • At init, before the first tick, one start <value> per tunable, in signal order.
  • Every change: <old> -> <new> by <writer>, the writer the id of the connector that wrote it. A write of the value in force logs nothing.
  • Every refused write: refused <value> by <writer>: <reason> (wrong type, length or text capacity, outside the tunable’s range, or rejected by a client’s mapping). The value in force stays.
  • A scenario’s set, add or ramp of a tunable is a scenario event; the scenario is in run.json.

The cycle of a start or a change is the first tick that fetches the value: an instance stepping at that cycle or later steps with it. The value of a tunable at cycle c is that of its last start or change line with a cycle of at most c; the lines of one tunable are in the order of its values.

Reading a record

  1. Read run.json; check format.
  2. List part-*.csv.gz and part-*.csv.gz.open, sort by name, and decode each as far as its gzip stream goes, keeping complete lines. Check each header against columns.
  3. Read events.csv up to its last line break.
  4. A run is complete when CLOSED exists; its closed files check with sha256sum -c --ignore-missing SHA256SUMS.

examples/recording/read_run.py does steps 1 and 2 with the Python standard library.

Pull interface

taktwerk record reads a running engine’s recorders through its OPC UA server; another puller can do the same. Per recorder, next to its counters, in the signal namespace (s= NodeIds):

  • <prefix>.recorder.<id>.manifest, a String variable: run.json without the run’s own fields (run_id, host, source, start, end), as JSON.
  • <prefix>.recorder.<id>.read_rows(from_cycle: UInt64, max_rows: UInt32) returns engine_run (String), oldest_cycle, next_cycle (UInt64) and rows (ByteString). Rows start at the first row at or after from_cycle still held, 0 meaning the oldest. Each row is its cycle and then one word per column word (words in the manifest), all little-endian u64: a float’s bits (f32 in the low 32), an integer sign- or zero-extended, a bool 0 or 1, a text byte per word. A reply holds at most 8 MiB. Ask again from next_cycle; a jump in the cycles is a gap.
  • <prefix>.recorder.<id>.read_events(from_seq: UInt64, max: UInt32) returns engine_run, oldest_seq, next_seq, then cycles (UInt64[]), kinds, sources and details (String[]), one entry per event, at most 4096 per call.

<prefix> is the engine’s system_prefix. The methods are called on the recorder’s folder object, NodeId s=<prefix>.recorder.<id>/. A changed engine_run means the engine restarted and its cycles count from 0 again.

Devices and bundles

What a deploy puts on a device and how it runs there: the bundle file, the release manifest, the layout under the install root, the units, the supervisor where systemd does not run, and the agent’s commands. The workflow is in Deploying to devices.

Bundle

A bundle is a folder with one or more project files, the model packages they use and optional companion processes, described by taktwerk-bundle.toml at its top:

name = "plant"                          # lowercase letters, digits, `_`, `-`; at most 64
projects = ["sim.toml", "closed-loop.toml"]  # the first is selected on a device's first activation
exclude = ["records", "campaigns"]      # left out, with everything below

[[companion]]                           # a process of its own, started and stopped with the engine
id = "bridge"
command = "bin/bridge"                  # relative to the bundle
args = ["--port", "9000"]
env = { LOG = "info" }

Every regular file below the folder belongs to the bundle, except hidden entries (a name starting with .) and what exclude names. A link to a file inside the folder is carried as that file; a link out of the folder, or to a directory, is refused. Project and command paths use letters, digits and ._/+- only.

A bundle is checked per target architecture (aarch64, x86_64, arm): every project file parses, every model package it references lies inside the bundle (no path escapes it) and has a library for the architecture (lib/<arch>/ of a raw package, binaries/<platform>/ of an FMU, packed or extracted), and every companion’s command is in the bundle.

Manifest

The manifest lists the bundle, the taktwerk version that runs it, the architecture and every file with its size and sha256. Its canonical form is one line of JSON, keys in this order, files sorted by path:

{"format":1,"bundle":"plant","taktwerk":"0.8.1","arch":"aarch64","files":[{"path":"bin/bridge","size":1024,"sha256":"…","exec":true}]}

exec marks a companion’s command, installed executable. The sha256 of these bytes, in lowercase hex, names the release. The agent refuses a manifest that is not canonical, whose hash is not the release’s name, or whose paths leave the bundle.

Device layout

<root>/bin/taktwerk-<version>                    engine binaries
<root>/bundles/<name>/staging/<hash>/            an upload: the files, and .taktwerk/manifest.json
<root>/bundles/<name>/releases/<hash>/           activated releases
<root>/bundles/<name>/releases/<hash>/.taktwerk/  manifest.json, engine -> bin/taktwerk-<version>
<root>/bundles/<name>/current -> releases/<hash>
<root>/bundles/<name>/history                    activated releases, oldest first
<root>/bundles/<name>/records/                   the engine's file recorders
<root>/bundles/<name>/env                        selected project, http address, secrets (0600)
<root>/bundles/<name>/enabled                    without systemd: started at boot

<root>/bundles/<name>/supervise.lock, .json      without systemd: the supervisor's lock, state

The first activation creates env; later deploys leave it alone, and the device owner adds secrets (for password_env) and RUST_LOG there:

TAKTWERK_HTTP_TOKEN=<64 hex digits>    the http connector's write token

Units

agent install-unit writes one template unit, taktwerk@.service; the instance is the bundle’s name. It runs as the owner of the install root (or --user), reads env, and starts in current:

ExecStart=<root>/bundles/%i/current/.taktwerk/engine run ${TAKTWERK_PROJECT} --http ${TAKTWERK_HTTP} --http-writes --record-dir <root>/bundles/%i/records
Restart=on-failure
RestartSec=2
RestartSteps=5
RestartMaxDelaySec=60
LimitRTPRIO=90
LimitMEMLOCK=infinity

A failed engine restarts after 2 s, the delay growing to 60 s (RestartSteps needs systemd 254; an older one restarts every 2 s), and is never given up (StartLimitIntervalSec=0): an engine that fails at init because its PLC is not up yet comes back once it is.

The release’s engine link picks the taktwerk version, so the binary switches with current. The engine serves its http connector on loopback only (the binary needs the http feature); a host reaches it through an SSH port forward. A companion is its own unit, taktwerk-<bundle>.<id>.service, with PartOf= and After= the engine’s; a drop-in taktwerk@<bundle>.service.d/companions.conf makes the engine’s unit want it. Rerun install-unit after a release changes its companions.

Without systemd

On a device without systemd (a BusyBox userland with init scripts, perhaps a read-only root and a persistent data partition for the install root) the agent drives its built-in supervisor instead, through the same commands, JSON and unit names, so the host and the workbench work unchanged. It is picked when /run/systemd/system is missing; --supervisor systemd|builtin overrides. agent info reports "supervisor": "builtin".

  • start runs taktwerk agent supervise <bundle> detached: one process per bundle, holding supervise.lock and writing its state to supervise.json in the bundle dir. It runs the engine with the same command line as the unit, in current, with PATH, RUST_LOG=info and the env file, then every companion.
  • A unit that fails (non-zero exit, a signal other than SIGHUP, SIGINT, SIGTERM, SIGPIPE) restarts after 2 s, doubling to 60 s, back to 2 s after a run of 60 s, and is never given up. A cleanly ended engine stops the companions and the supervisor.
  • stop sends the supervisor SIGTERM; it stops the companions, then the engine, each with SIGTERM and SIGKILL after 30 s. A killed supervisor takes its units with it.
  • Started as root (the boot script, or a sudo or su privilege), it raises RLIMIT_RTPRIO to 90 and RLIMIT_MEMLOCK to unlimited, then runs as the owner of the install root; install-unit --user is refused. Started as that owner, the real-time limits stay as they are.
  • The units’ output goes to bundles/<bundle>/log, a line each with the time and the unit, rotated at 1 MiB to log.1 .. log.3; logs reads it.
  • enable and disable create and remove bundles/<bundle>/enabled. install-unit writes <root>/boot.sh, which starts the enabled bundles in the order of their names (stop stops all), each through its release’s engine, and an init entry S99taktwerk that calls it in the first of /etc/rc.d, /etc/init.d that exists (--unit-dir picks another). On a read-only root the report’s notes say so: have the device’s own boot hook run <root>/boot.sh start as root.
  • start-at runs a supervisor that sleeps for the delay on the monotonic clock, then starts the units; --cancel stops it, start starts at once instead. Like the transient timer, it does not survive a reboot.

Making a model taktwerk-compatible

taktwerk has no ABI of its own. It hosts two kinds of model:

  1. FMI co-simulation FMUs (FMI 3, also FMI 2). FMI 3 is the recommended format: any tool that exports FMI 3 co-simulation works, and structural parameters carry the sizes.
  2. Plain C shared libraries, described by a descriptor (taktwerk-model.toml) next to the library. New C models follow the recommended shape; existing other C interfaces are hosted through a hand-confirmed descriptor.

The model convention

Whatever the format, a taktwerk model is:

  • Size-generic and plant-agnostic. Variables have symbolic shapes over named dimensions (y: f64[ny], A: f64[nx, nx]) with optional min, max and default. The model learns each size at init. A fixed-size model is one whose dimensions are literals.
  • Explicit about roles. Each variable is an input (read every step), an output (written every step), a parameter (set once before init) or a tunable (set before init, changeable while running, delivered before the next step).
  • Allocation-free in its step. The engine owns every buffer the model exchanges: it sizes them at init and passes pointers that stay valid for the instance’s lifetime. A library may allocate its own state at init, never per step.
  • Honest about instances. A library that keeps state per instance (behind a handle, or in structs the engine owns per instance) declares multiple. A library with state in globals declares single; taktwerk then loads a private copy of the file for each further instance.
  • Explicit about matrix layout: row-major (C order) or column-major.
  • Fail-loud. A step that cannot continue returns an error code; the engine stops (fail-stop) and the service manager restarts it, unless the project holds that instance (Faults). Never return success with garbage outputs; a step whose outputs are not valid says so in a status output.

The project file then binds every dimension, sets parameters and maps signals per instance; one model serves many instances. See Concepts.

Checking a model

taktwerk inspect model.fmu --kind fmi      # or: taktwerk inspect path/to/package --kind raw
taktwerk new model.fmu --kind fmi -o try.toml
taktwerk check try.toml

Wrapping a raw model as an FMU

A confirmed package can also leave taktwerk as a standard FMI 3 co-simulation FMU, for any importer:

taktwerk fmu-wrap path/to/package                       # dry run: variables, structural parameters, targets
taktwerk fmu-wrap path/to/package --write -o model.fmu  # build for the host
taktwerk fmu-wrap path/to/package --target aarch64 --target x86_64 --write   # cross-build with zig

fmu-wrap builds for aarch64 and x86_64.

The generated C wrapper does what the raw adapter does, in C: it allocates the buffers from the bound structural parameters (one UInt64 per dimension, with the descriptor’s min, max and default as start), starts every input, parameter and tunable at the descriptor’s start (zero without one), fills the struct members per call, loads the library itself (a single library as a private copy per instance), checks ok_codes and reported lengths. The structs are emitted for the target compiler and checked against taktwerk’s layout at compile time. Text buffers appear as String variables; a library told its step size (builtin = "step_size") is initialised on the first fmi3DoStep, which fixes the communication step. The FMU carries the library and any --bundled dependency under binaries/<arch>-linux/ and the wrapper source under sources/.

FMI 3 (recommended)

taktwerk runs FMI 3 and FMI 2 co-simulation FMUs. Export from any tool that writes FMI 3 co-simulation for Linux; the FMU then runs unchanged in taktwerk and in every other FMI importer. A kind = "fmi" model path is an .fmu archive (extracted to a private temporary directory at load) or an already extracted FMU directory. An archive that holds a symlink, an encrypted entry, a duplicate name or a name outside the archive (absolute, ..) is refused before anything is extracted, and deploy refuses a bundle that ships one.

Sizes: structural parameters

A size-generic FMI 3 model declares each size as a structural parameter and sizes its arrays with <Dimension valueReference="…"/>. Each structural parameter becomes a taktwerk dimension: its name is the dimension’s name, start its default, min and max its bounds.

Calling sequence

Per instance: instantiate (co-simulation, no event mode, the FMU’s resources/ directory as resource path), configuration mode for structural parameters, parameters set, initialization mode at engine.start_time (no tolerance, no stop time) with the inputs described under Init, outputs read back, then one DoStep per period of every × tick_ms. Inputs are set before every step, changed tunables before the next step; outputs are read after it. OK and Warning are success; any other status, or a step that requests termination, stops the engine. Logging goes to the engine log at debug level.

Single vs multiple instances

canBeInstantiatedOnlyOncePerProcess="true" marks a single-instance FMU. taktwerk still runs several instances of it: each further instance loads a private copy of the shared library, since one loaded file shares its globals. Without the flag, all instances share one loaded library. Prefer FMUs that keep all state in the instance.

Checklist

  • FMI 3 (or FMI 2), with a CoSimulation element; model exchange alone is refused.
  • Every size is a structural parameter with an integer type, a start, and min/max where the model has limits.
  • Exposed variables use numeric or Boolean types only.
  • Parameters that may change while running are variability="tunable".
  • A Linux binary for every target architecture, in the platform folder above.
  • No allocation and no blocking I/O in DoStep.
  • taktwerk inspect model.fmu --kind fmi shows the dimensions and variables you expect.

Hand-written C

A C model is a shared library plus a descriptor, taktwerk-model.toml, in a package directory:

lowpass/
  taktwerk-model.toml      the descriptor
  lib/aarch64/liblowpass.so
  lib/x86_64/liblowpass.so

lib/<arch>/ is named by the running architecture: aarch64, x86_64, or arm for 32-bit hard-float ARM. It holds one .so, or set abi.library in the descriptor to pick one by file name.

The recommended shape

New C models use this shape, for a model <m>:

typedef struct { int nx; /* 1..64 = 4 */ int nu; } <m>_dims;   /* one int per dimension */
typedef struct { const double *A; /* [nx][nx] */ double k; } <m>_params;
typedef struct { const double *u; /* [nu] m/s: inflow */ } <m>_inputs;
typedef struct { double gain; } <m>_tunables;
typedef struct { double *x; /* [nx] */ double y; } <m>_outputs;

int <m>_init(void **h, const <m>_dims *dims, const <m>_params *params, double step_size);
int <m>_step(void *h, double time, const <m>_inputs *in, const <m>_tunables *tun,
             <m>_outputs *out);
int <m>_terminate(void *h);   /* or void */

taktwerk import-header reads a header in this shape completely and writes a descriptor that is already confirmed: nothing is guessed, so there is nothing to review. The rules:

  • Return codes. init and step return int; 0 is success, anything else an error. A failed init or step stops the engine (fail-stop) unless the instance’s on_error holds it (Faults); the code is logged. terminate returns int or void.
  • Roles by struct name. The suffix of the type name says what a struct holds: _dims, _params, _inputs, _tunables, _outputs. Every member is a variable of its struct’s role. <m>_params and <m>_tunables may be left out, and with them their argument; so may <m>_dims when no shape names a dimension. The struct arguments may come in any order; the handle, time and step_size are where the shape puts them.
  • Sizes in <m>_dims, one int per dimension, named like the dimension. A trailing comment may bound it and give a default: /* 1..64 */, /* 1.. */, /* 1..64 = 4 */.
  • Arrays are pointers whose memory the engine owns. Every pointer member carries its shape in a trailing comment on its line, in dimension names or literal lengths: /* [n] */, /* [nx][nu] */, /* [3] */. Matrices are row-major. Pointers stay valid for the instance’s lifetime, so init may keep them.
  • Scalars by value inside the structs: a scalar parameter, input, tunable or output is a plain double (or another admitted type) member without a shape.
  • Units and descriptions may follow the shape in the same comment: /* [n] s: time constant */ is unit s and description time constant; /* [n]: input */ only a description. Without a colon, one word is a unit (/* m */) and more words a description.
  • const marks what the model reads: dims, params, inputs and tunables are const; outputs are not.
  • State behind the handle. init allocates the instance’s state and stores it through h; step and terminate receive it. No globals, so any number of instances share one loaded library (instances = "multiple").
  • No allocation in step, no blocking I/O, no printing. Allocate everything at init and free it in terminate.
  • Admitted C types: double, float, bool, char, and the fixed-width and plain integer types at their 64-bit Linux widths, each optionally const and optionally followed by one *. A char * with a literal length (/* [32] */) carries text, NUL included.

step advances from time by step_size. The engine fills in and tun before each step and reads out after it; a changed tunable is in tun from the next step on.

Example: a low-pass filter bank

A first-order low-pass filter per channel over n channels, y = gain · x, with x ← x + α (u − x) and α = dt / (tau + dt).

This is examples/raw-filter-bank. lowpass.h:

/* A bank of first-order low-pass filters over n channels, in the recommended shape. */
#ifndef LOWPASS_H
#define LOWPASS_H

typedef struct {
    int n;              /* 1..64 = 3 */
} lowpass_dims;

typedef struct {
    const double *tau;  /* [n] s: time constant */
    const double *y0;   /* [n]: initial state */
} lowpass_params;

typedef struct {
    const double *u;    /* [n]: filter input */
} lowpass_inputs;

typedef struct {
    double gain;        /* output gain */
} lowpass_tunables;

typedef struct {
    double *y;          /* [n]: gain times the filter state */
} lowpass_outputs;

int lowpass_init(void **h, const lowpass_dims *dims, const lowpass_params *params,
                 double step_size);
int lowpass_step(void *h, double time, const lowpass_inputs *in,
                 const lowpass_tunables *tun, lowpass_outputs *out);
int lowpass_terminate(void *h);

#endif

lowpass.c:

#include <stdlib.h>
#include "lowpass.h"

typedef struct {
    int n;
    double *alpha; /* [n], dt / (tau + dt) */
    double *x;     /* [n], filter state */
} lowpass_state;

int lowpass_init(void **h, const lowpass_dims *dims, const lowpass_params *params,
                 double step_size) {
    lowpass_state *s;
    int i;
    if (dims->n < 1 || step_size <= 0.0) return 1;
    s = calloc(1, sizeof *s);
    if (!s) return 2;
    s->n = dims->n;
    s->alpha = calloc((size_t)s->n, sizeof *s->alpha);
    s->x = calloc((size_t)s->n, sizeof *s->x);
    if (!s->alpha || !s->x) {
        lowpass_terminate(s);
        return 2;
    }
    for (i = 0; i < s->n; i++) {
        if (params->tau[i] < 0.0) {
            lowpass_terminate(s);
            return 3;
        }
        s->alpha[i] = step_size / (params->tau[i] + step_size);
        s->x[i] = params->y0[i];
    }
    *h = s;
    return 0;
}

int lowpass_step(void *h, double time, const lowpass_inputs *in,
                 const lowpass_tunables *tun, lowpass_outputs *out) {
    lowpass_state *s = h;
    int i;
    (void)time;
    for (i = 0; i < s->n; i++) {
        s->x[i] += s->alpha[i] * (in->u[i] - s->x[i]);
        out->y[i] = tun->gain * s->x[i];
    }
    return 0;
}

int lowpass_terminate(void *h) {
    lowpass_state *s = h;
    if (s) {
        free(s->alpha);
        free(s->x);
        free(s);
    }
    return 0;
}

When the header deviates

A header that is not completely in the shape gets the heuristic proposal of other C interfaces, written with abi.confirmed = false, which the engine refuses to load. Its leading comment lists every deviation from the shape first, then every guess. Leave out the shape comment of tau, for example:

# - not the recommended shape: lowpass_params: tau is a pointer without a shape comment such as `/* [n] */`

Either fix the header and import again, or review the proposal, fix causalities and shapes by hand and set confirmed = true. That flag states that you checked which pointer takes which dimension: lengths are never inferred at run time, and a wrong shape means the library reads or writes out of bounds.

Other C interfaces: the descriptor

An existing C library that does not follow the recommended shape is hosted as it is, through a descriptor that says how to call it. The engine owns every buffer, lays structs out by C’s rules for the running target, fills pointers once per call and copies inputs in and outputs out around each step.

Workflow

  1. taktwerk import-header model.h -o taktwerk-model.toml proposes a descriptor. The importer reads flat typedef struct { … } Name; blocks and function prototypes over the admitted types; it is not a C parser (no macro expansion) and skips, with a note, anything it does not cover. A header in the recommended shape comes out confirmed; any other gets a proposal whose notes start with what deviates from that shape.
  2. Read the notes at the top of the proposal. Function roles (init, step, terminate), dimension members and pointer→length relations are guessed by name; every guess is listed. Pointers are inputs when const and outputs otherwise; scalars by value are parameters unless the struct name hints otherwise.
  3. Fix causalities (which values are parameters, which tunables), shapes, matrix layouts (the importer proposes one dimension per pointer), dimension bounds and defaults.
  4. Set abi.confirmed = true. An unconfirmed descriptor is refused at load.
  5. Put the library at lib/<arch>/ next to the descriptor and run taktwerk inspect <dir> --kind raw.

Calls

A library is called through at most three functions, or one function serving as both init and step (see single entry point):

  • [abi.init] once per instance, in declared order, after the engine has allocated and filled the buffers (dimension lengths, parameters, tunables, inputs as described under Init);
  • [abi.step] once per step, after inputs and changed tunables were copied in; outputs are copied out afterwards;
  • [abi.terminate] (optional) once when the instance is released, also after an error.

Each function returns int (returns = "int", the default), where any value in ok_codes (default [0]) is success and anything else fails the call, or void (returns = "void"). Arguments are listed in C order; each is exactly one of:

Structs

A struct in [abi.structs.<s>] lists its members with their C type in declaration order; each member maps to at most one of:

  • A scalar member mapped to a variable carries the value: inputs, parameters and tunables are written before each call, outputs read after it. A shaped variable needs a pointer member.
  • A pointer member may point at a scalar variable of any causality. One the library writes back (a counter in an input struct) is mapped to an output variable, whose buffer the engine never overwrites.
  • A pointer member carrying a dim, const or phase points at engine-owned storage.
  • Unmapped pointer members are NULL, unmapped scalars zero.

A variable member’s C type must match the variable’s type, with one exception: a uint8_t or uint8_t * member may carry a bool variable; the engine keeps the bytes and reads any non-zero byte as true.

Reported lengths. A dim member with reported = true is a length the library knows and writes itself. It is zeroed before init, then compared with the bound length after init and after every step; a difference fails the call with both values. The check runs after the call returned, so a library loaded with the wrong sizes may already have written at its own size: every reported dimension therefore needs a max, and the engine allocates each buffer shaped by it at that max while exchanging only the bound length (text and byte buffers keep their literal capacity). The project file stays the size authority.

Library-owned outputs. Some libraries allocate their output buffers themselves at init and store the addresses into the output struct’s pointer members (out->y = y_buf;), then write only their own buffers. Mark such a member owner = "library":

{ name = "y", type = "double *", variable = "y", owner = "library" }

The engine writes NULL into the member before init and never writes it again. After init and after every step it reads the address from the struct and copies the variable’s bound length (text and byte buffers: their literal capacity) from there into its own buffer, byte-wise, so the address needs no alignment. A member still NULL after init, or set back to NULL by a step, fails that call with the library left <struct>.<member> NULL. Only a pointer member mapped to an output variable can be library-owned, and no other member or argument may carry that variable. The engine trusts the address: the library must keep at least the bound length readable there for the instance’s lifetime, the same contract as every pointer the engine hands it. The default, owner = "engine", is the engine’s buffer as above.

Text is a char * member mapped to a u8 variable with a literal shape, its capacity with the terminating NUL included (shape = [32]). Such a variable is marked text: the image and the library see its bytes, while connectors, check, inspect and the TUI present a string (the OPC UA server a String node, see Connectors). A uint8_t * or unsigned char * member stays a byte buffer. The caller supplies text through a parameter (a TOML string in the project file) or an input; the library writes it into an output. Each instance owns one image per struct, the same in every call, so a library may keep a struct pointer it got at init.

C types

Admitted are double, float, bool, char and the fixed-width and plain integer types at their 64-bit Linux widths (int is i32, long and size_t are 64-bit, char is a byte that marks text), each optionally const and optionally followed by one *. Pointers to pointers are refused, except the void ** of handle = "out".

Start values

An input, parameter or tunable may declare the value it starts at, as FMI’s start does:

[[variables]]
name = "k"
causality = "tunable"
type = "f64"
start = 2.0

[[variables]]
name = "b"
causality = "parameter"
type = "f64"
shape = ["nx"]
start = 1.0              # every element

[[variables]]
name = "c"
causality = "parameter"
type = "f64"
shape = ["nx"]
start = [0.1, 0.2, 0.3]  # one per element: nx must be bound to 3
  • A scalar takes one number, a bool variable true or false. Integers convert to floats, floats never to integers.
  • An array takes one value for every element, or a flat list of the bound length, in the variable’s layout. A literal shape is checked at load, a symbolic one by check and at init.
  • Outputs and text variables take no start.
  • What sets a value wins over start: --set, then a scenario’s overrides, then the project’s parameters. Without any of them a value starts at start, without one at zero.
  • A tunable shows its start in the image from the beginning and keeps it until written. An external input holds its start until a connector writes it; that is not a write, so an input with an age limit stays stale until then. A wired input takes its producer’s output.
  • fmu-wrap writes start as the FMI start (a list must fit the dimensions’ defaults) and fills the wrapper’s buffers with it, so an FMU importer starts where the raw adapter does.
  • import-header proposes none; a header carries no start values.

Ranges

A numeric tunable may declare the values it admits; a write outside is refused (see Ranges):

[[variables]]
name = "k"
causality = "tunable"
type = "f64"
range = [0.0, 10.0]           # every element; -inf or inf leaves a side open
# range = [[0, 1], [0, 2]]    # or one per element: the bound length

Only tunables take a range; not bool or text. fmu-wrap writes a range of one [lo, hi] as the FMI min and max.

abi.libraryfile name in lib/<arch>/; default: the only .so there
abi.ok_codessuccess return values of int calls; default [0]
abi.init, abi.step, abi.terminatesymbol, returns (int or void), args; init and step may share a symbol
abi.structs.<s>.membersname, type (C spelling), at most one of variable (with optional owner: engine default, or library), dim (with optional reported), builtin, const, phase

A single library keeps its state in globals, so each further instance loads a private copy of the file; a multiple library carries its state behind a handle or inside a struct the engine owns per instance.

Any other key, at the top level or in any table, is refused at load: the error names the key, its line and the keys admitted there.

Single entry point

A common legacy style exports one function for every call, taking an integer id and two opaque pointers the library casts to its input and output structs. Which call runs is a flag the caller sets, and the library reports its own sizes at init:

typedef struct { double *y; char *label; int32_t *n_u; int32_t *n_y; } io_out;
int model_call(int id, char *in, char *out);  /* 0 on success */

taktwerk import-header model.h --entry model_call --arg-struct in=io_in --arg-struct out=io_out imports such a header when told the entry point and the struct behind each opaque parameter; it then also guesses a flag-like integer as a phase, size-like integer pointers in an output struct as reported lengths, and a leading integer argument as a const whose value is left to the developer. Set each reported dimension’s max before confirming. A header does not say who sets an output pointer: if the library points them at its own buffers at init, add owner = "library" to those members.

A runnable package in this style, with its header, source and confirmed descriptor: examples/raw-single-entry.

Calling convention

Supported targets are aarch64, x86_64 and 32-bit hard-float ARM Linux, with the platform’s standard C calling convention. On 32-bit ARM a float or a 64-bit integer by value is refused (pass a double, or go through a pointer or struct), and long and size_t are 32 bits.

Applications as packages

An estimator, a soft sensor, a controller or a plant model reaches taktwerk the same way: as a model package, an FMU or a raw C library with its descriptor. The package carries the computation; a project file per plant binds it. This page is about designing that interface so one package serves many plants and is safe to put in a loop.

Format

  • FMI 3 is the recommended format: any tool that exports FMI 3 co-simulation for Linux works, the sizes are structural parameters, and the same FMU runs in other importers. See FMI 3.
  • C in the recommended shape: taktwerk import-header --shape writes a confirmed descriptor from the header, nothing to review. taktwerk fmu-wrap turns the package into an FMI 3 FMU for other importers.
  • An existing C interface stays as it is behind a hand-confirmed descriptor.

The interface

  • Size-generic. A dimension instead of a literal length lets one package serve a plant with three measurements and one with twelve; the project binds the length per instance.
  • Units and descriptions on every variable (an FMU’s unit and description, a comment in the recommended C shape) show in inspect, check, on the OPC UA server and in the workbench.
  • Start values for inputs and tunables make a fresh instance sensible before anything writes them: an FMU’s start, a descriptor’s start.
  • Inputs carry no validity of their own. An input is a value; whether it is fresh is the engine’s job (max_age_ms: a stale input skips the tick), whether it is plausible is the package’s: check it and report it in the status.
  • A failed step is for bugs. A non-success return stops the engine and every instance in it (or, with the instance’s on_error = "hold" or "safe", takes the instance down until a re-init, the status degraded and the heartbeat held; see Faults). A step that can go on (a bad measurement, a solver that did not converge this step) returns success, holds or flags its outputs and sets a status bit.
  • No allocation and no blocking I/O in a step. Read files and allocate at init.

Files the application reads

A data file named by a text parameter is opened by the library itself, relative to the engine’s working directory: on a device the release directory of the bundle (Units), so a path relative to the bundle’s top works there. Such a file is not part of the package’s hash: run.json and a campaign’s spec hash cover the descriptor and lib/ of a raw package, and an FMU’s description, binaries and resources/. Data that belongs to the model goes into an FMU’s resources/; data that belongs to a plant goes into the bundle, whose manifest hashes every file.

Status and the write gate

The engine knows whether it runs: taktwerk.status, the heartbeat, stale inputs. It does not know whether a model’s outputs make sense. A package says so in a status output, and the project’s write gate holds the outputs a PLC or a plant data system would otherwise take.

A status output

One integer scalar output, conventionally status: 0 when every output is valid, else one bit per reason. An integer output of any width works for a gate; u32 maps to an OPC UA UInt32 and a PLC’s UDINT. The engine interprets none of the bits; the project picks the ones that hold writes.

The recommended layout keeps the bits that make outputs unusable apart from the ones that only inform:

bitsvaluemeaningoutputs
01not ready: initialising, too few measurements so farnot valid
12an input not plausible: out of the model’s range, not finitenot valid
24the computation failed this step (no convergence, singular data); outputs heldnot valid
3 to 78 to 128further reasons of the package’s own why outputs are not validnot valid
8256an output limited to its boundsvalid
9512degraded: running on a fallback, a reduced model, fewer measurementsvalid
10 to 151024 to 32768further warnings of the package’s ownvalid

So status & 255 is zero when the outputs may be written, and a gate closes on mask = 255; a project that also refuses degraded results adds 512. Document every bit the package uses in its variable’s description or the package’s own documentation.

A step that sets a bit returns success. A non-success return is a fault: it stops the engine, or with on_error = "hold" or "safe" takes the instance down and holds the heartbeat (Faults), which is right for a bug and wrong for a bad measurement.

The gate

[[connector]]
id = "plc"
kind = "opcua-client"
endpoint = "opc.tcp://10.0.0.10:4840"
writes = "on"

[connector.gate]
open_after = 5                               # good ticks in a row before writes resume
conditions = [{ signal = "est.status", mask = 255 }]

[connector.map]
"est.x_hat" = { node = "ns=4;s=Line.x_hat", min = 0.0, max = 50.0 }
"est.status" = { node = "ns=4;s=Line.est_status", gated = false }
"taktwerk.heartbeat" = "ns=4;s=Line.heartbeat"
"taktwerk.status" = "ns=4;s=Line.taktwerk_status"
  • The gate is closed while the engine is not running or the heartbeat did not advance, while a condition holds, or while a gated output is not finite or outside its mapping’s min and max. It opens after open_after good ticks in a row.
  • A closed gate writes none of the gated outputs, so the target keeps their last values. The heartbeat and taktwerk.status are always written; map the status output with gated = false too, so the PLC sees why.
  • Every change is a gate event (open, closed: <reason>) in events.csv, and <prefix>.connector.<id>.gate_open, gate_opens, gate_closes and gate_held count it.
  • The rest connector takes the same gate table.

The PLC still owns the safe state: it watches the heartbeat and taktwerk.status, and decides what a held value means for the plant (see the safety contract).

Checks from outside

taktwerk engine status --expect 'est.status & 255 == 0' passes only while the outputs are valid, so a checklist or a monitoring job can test the same bits (Operating a running engine).

Testing a package

A package is tested with the engine that will run it: the same adapter, the same fixed step, the same image. Runs off real time need no plant, no port and no privileges, so they fit a workstation and a CI job.

The interface

taktwerk inspect <package> --kind raw          # dimensions, variables, types, units, ranges
taktwerk new <package> --kind raw -o try.toml  # a project with one instance
taktwerk check try.toml                        # binds, resolves, prints the plan

inspect shows the interface exactly as the engine reads it: a wrong shape, causality or unit shows here before anything runs.

One run

taktwerk run try.toml --speed max --no-connectors --cycles 10000 \
  --set est.dims.n=4 --set est.q='[0.1, 0.1, 0.1, 0.1]' --seed 1
  • --speed max --no-connectors runs unpaced on engine time; a file recorder loses no row. With no recorder in the project, add one ([[recorder]] with signals = ["@io", "est.*"]).
  • --set binds dimensions and sets parameters, tunables and initial inputs without editing the project; --seed seeds every instance with a seed variable.
  • --stop-when 'est.status != 0' ends the run at the first tick that sets a status bit; the stop event names the condition.
  • A deterministic package gives the same bytes twice: run it again with the same seed and compare the parts’ lines in the two SHA256SUMS files.

Scenarios

A scenario file is a test of the package in a project: inputs driven, faults injected, a stop limit, a seed.

seed = 1

[stop]
time_s = 3600.0

[[event]]                 # a measurement steps
at_s = 600.0

[[event]]                 # the sensor freezes for 5 minutes

[[event]]                 # the reading is lost
at_s = 2000.0

[[event]]                 # the sensor drifts from here on
at_s = 2400.0

A fault changes what the package reads, not what the producer wrote: the producer’s output keeps its column. To record what the package received through a wired input, compose it (inputs = { y = ["plant.y"] } records as est.y). drop = true on an external input with a max_age_ms tests the stale path: the engine skips ticks, holds the outputs and publishes taktwerk.status faulted until the input is fresh again.

What to look for: the status bits set and cleared at the right ticks, outputs held or flagged while they are, no fail-stop for a bad measurement, and recovery after the fault ends.

In Python

import taktwerk

run = taktwerk.run("try.toml", scenario="scenarios/frozen-sensor.toml", seed=1)
status = run["est.status"]
frozen = [s for t, s in zip(run.t_engine, status) if 1200 <= t < 1500]
assert all(s & 255 for s in frozen[100:])          # flagged while frozen
assert status[-1] & 255 == 0                       # valid again at the end
print(run.events_of("scenario"))

taktwerk.run starts taktwerk run unpaced without connectors and returns the record of the project’s file recorder; it fits a pytest suite. See Python.

Campaigns

A campaign runs the scenarios over many parameter sets: a grid over tuning values, random samples of plant parameters ([sample]), replicates for other noise draws, [[case]] for the scenarios. Runs that differ only in case or grid point share their seed, so a comparison sees the same noise. taktwerk.read_campaign loads the results into one table.

In the loop

The write gate and the connectors run only in real time. Before a plant: a project with the plant connector and writes = "dry-run" evaluates the gate and logs what it would write (Commissioning).

Other importers

A raw package wrapped with taktwerk fmu-wrap runs in any FMI 3 importer; testing the FMU there checks that the interface is what other tools expect.

Tutorial: a single-entry library on a controller

You have a model compiled as a C shared library that exports one function for init and step, and you want it running on a Linux controller next to a PLC, stepping at a fixed period and reachable over OPC UA. This tutorial takes it there with taktwerk, from your workstation over ssh.

The library looks like this; names differ, the shape is what matters:

typedef struct { int32_t *init_flag; int32_t variant; double *k; double *u; char *title; } my_in;
typedef struct { double *y; char *label; int32_t *n_u; int32_t *n_y; } my_out;
int my_entry(int id, char *in, char *out);   /* 0 on success */

One function, an integer id, and two opaque pointers the library casts to its input and output structs. A flag in the input struct tells init from step, and the library may report its own sizes at init. examples/raw-single-entry is a complete library of this kind to practise on.

Placeholders used below:

placeholdermeaningexample
<host>the controller’s address192.168.1.10
<user>your login on the controlleradmin
<dir>a writable directory on the controller for everything here/opt/custom/taktwerk
<port>a free TCP port for taktwerk’s OPC UA server4841

1. Look at the controller

ssh <user>@<host> 'uname -m; ldd --version | head -1; ss -ltn'

Note three things: the architecture (x86_64 or aarch64), the glibc version, and which ports are taken. A controller with its own OPC UA server usually holds 4840; pick another <port>.

2. Install taktwerk on your workstation

On a Linux workstation with Rust 1.89 or newer:

cargo install --locked taktwerk
taktwerk --version

This gives you import-header, new, inspect, check and tui locally.

3. Build taktwerk for the controller

If the workstation has the controller’s architecture and a glibc no newer than the controller’s, the binary you just installed runs there too: use ~/.cargo/bin/taktwerk.

Otherwise cross-build it from the published crate with cargo-zigbuild, which links against an older glibc than the workstation’s. Name a glibc version at or below the controller’s:

cargo install --locked cargo-zigbuild        # also needs `zig` on the PATH
rustup target add x86_64-unknown-linux-gnu   # or aarch64-unknown-linux-gnu, armv7-unknown-linux-gnueabihf

curl -sSfL https://static.crates.io/crates/taktwerk/taktwerk-0.13.1.crate | tar xz
cd taktwerk-0.13.1
cargo zigbuild --release --locked --target x86_64-unknown-linux-gnu.2.35
cd ..
cp taktwerk-0.13.1/target/x86_64-unknown-linux-gnu/release/taktwerk ./taktwerk-target

Your library has the same constraint: build it for the controller’s architecture and against a glibc at or below the controller’s (zig cc -target x86_64-linux-gnu.2.35 -shared -fPIC ... works for C).

4. Make a model package

A package is a directory with the library under lib/<arch>/ and a descriptor that tells taktwerk how to call it. The header produces the descriptor:

mkdir -p mymodel/lib/x86_64
cp libmymodel.so mymodel/lib/x86_64/
taktwerk import-header my_model.h --entry my_entry \
  --arg-struct in=my_in --arg-struct out=my_out -o mymodel/taktwerk-model.toml

--entry names the one function; each --arg-struct says which struct an opaque parameter carries, by the parameter’s name in the header. The result is a proposal: it starts with notes, one per guess, and abi.confirmed = false. Go through the notes and fix the descriptor:

  • The id. The leading integer argument is a const; set the value the library expects.
  • The init flag. A flag-like member is guessed as phase = { init = 1, step = 0 }; check the values.
  • By-value members such as variant become inputs; a fixed selection is a const member instead.
  • Roles. Pointer members become inputs or outputs by their struct. A value you want to change while running without it being an input is a tunable; a member of the input struct the library writes back is an output.
  • Sizes. Give every array its shape in dimension names or literal lengths. A size the library reports at init is a reported = true dimension member; give that dimension a max, because buffers are allocated at it.
  • Output pointers the library sets. If the library allocates its own output buffers at init and stores their addresses into the output struct’s members, the header cannot show it: add owner = "library" to those members, or the outputs stay zero. A pointer left NULL after init then fails init with a message naming the member.
  • Text. A char * member is text: give its variable a literal capacity with the NUL included, shape = [32]. Text shows as a string in check, on OPC UA and in the TUI.
  • Matrices need two shape entries and their layout.

Then set abi.confirmed = true. The descriptor has every key; the example’s taktwerk-model.toml shows a confirmed one and the command that proposed it.

5. Write the project

The project file says which models run, at which period, with which sizes, and where the OPC UA server listens:

taktwerk new mymodel --kind raw --port <port> -o project.toml --write

Open project.toml and:

  • bind every dimension under [instance.dims];
  • set start values under [instance.parameters] (text as a TOML string: title = "tank 3");
  • set the server’s endpoint to opc.tcp://<host>:<port> so it listens on the controller’s network address instead of only on 127.0.0.1.

inspect, new and check load the library of the machine they run on (lib/<uname -m>/). On a workstation of another architecture, run them on the controller in step 6 instead.

taktwerk inspect mymodel --kind raw   # the interface as taktwerk reads it
taktwerk check project.toml           # load, resolve, check; prints the signal table

6. Ship to the controller

ssh <user>@<host> mkdir -p <dir>
scp -r taktwerk-target <user>@<host>:<dir>/taktwerk
scp -r mymodel project.toml <user>@<host>:<dir>/

The model path in project.toml is relative to the project file, so keep the two side by side as they are on the workstation.

7. Run and test

On the controller:

ssh <user>@<host>
cd <dir>
./taktwerk check project.toml
./taktwerk run project.toml

check loads the library and verifies the plan without calling the model. run calls the entry once with the init phase, checks the sizes the library reported against the project, then calls it once per tick with the step phase. A non-zero return stops the engine with the code in the log.

From the workstation, in a second terminal:

taktwerk tui opc.tcp://<host>:<port>
  • The header shows status Running and a rising heartbeat; overruns should stay 0.
  • Select an input or a tunable and set a value; the outputs follow from the next tick.
  • Text signals show as strings and are edited as strings.

Any OPC UA client works the same way: every signal is a node under the namespace urn:taktwerk.

Stop the engine with Ctrl+C. It prints a summary:

cycles <n>  published <n>  overruns 0  stale 0  cycle mean <ms> ms  max <ms> ms  late mean <ms> ms  max <ms> ms  stop requested

The max after cycle mean, the longest cycle, against the tick is your margin; the late pair is how long after its deadline a tick started; stop names why the run ended. A process started from an ssh session usually ends when that session closes; for anything longer than a test, run it as a service.

8. Keep it running

Running in production has the systemd unit, the real-time settings (SCHED_FIFO, a CPU, locked memory) and what each needs. On a controller that also runs a PLC runtime, keep the cycle thread’s priority below the runtime’s own tasks.

To connect the model to the PLC’s variables instead of driving it by hand, add an opcua-client connector that maps signals to the PLC’s OPC UA nodes; taktwerk new writes a commented one into the project. See Connectors.

Tutorial: a gain sweep as a campaign

A controller is tuned by running its loop many times: other gains, other plants, the same disturbance. This tutorial takes the level loop of examples/campaign from one simulated hour to a campaign of 24 runs and a ranking of the gains, with the engine that would run the same loop on a controller. Everything runs on a workstation, from the repository root, with a C compiler, taktwerk and uv.

1. The loop

The plant is a tank drained through an outlet, filled by a pump and by a disturbance inflow; its level sensor adds noise from a seed. The controller is the PI of raw-pi, reading the measured level and driving the pump. Both are raw C packages; build them:

sh examples/raw-pi/build.sh
sh examples/campaign/tank/build.sh

tank.h is in the recommended shape: taktwerk import-header tank.h --shape wrote its descriptor, confirmed. Its parameter seed makes it a seeded model, nothing more is needed for seeds.

2. One run

The set point ctrl.sp is an external input; nothing writes it unless something sets it. Run an hour of engine time as fast as the models compute, without OPC UA, with a set point of 1 m:

taktwerk run examples/campaign/project.toml --speed max --no-connectors \
  --until-time 3600 --set 'ctrl.sp=[1.0]' --seed 5

36 000 ticks of 0.1 s took about half a second with a release build on a four-core aarch64 board. The recorder main wrote the run to examples/campaign/records/project/main/<run-id>/; run.json records under invocation the speed, the time limit, the override and the seed each instance got. Read it in Python:

import taktwerk

run = taktwerk.read_run("examples/campaign/records/project/main")
print(run.stop, run.seed, run["plant.level"][-1])

Run it again with --seed 5: the parts are the same bytes.

3. A disturbance

disturbance.toml is a scenario: the set point, a time limit of 20 minutes, a step of 0.2 m³/s in the disturbance inflow at 300 s, and the level sensor frozen for a minute at 700 s.

taktwerk run examples/campaign/project.toml --speed max --no-connectors \
  --scenario examples/campaign/disturbance.toml

4. The campaign

gains.toml sweeps ctrl.kp over 0.5 to 4 and ctrl.ki over 0.01 to 0.2, for the tank as built and for one with a smaller outlet (plant.k_out = 0.4), all over the disturbance scenario. Look at the plan first:

taktwerk campaign examples/campaign/gains.toml

runs     24 (0 done), 2 at a time, speed max

run               seed                ctrl.ki  ctrl.kp  plant.k_out  done
nominal-g00       627405149472732430  0.01     0.5      -            no
nominal-g01       627405149472732430  0.01     1.0      -            no
...

Every run has the same seed: they differ only in case and grid point, so they all see the same sensor noise and the comparison is between the gains, not between noise draws. Run it:

taktwerk campaign examples/campaign/gains.toml --write

Each run is a taktwerk run process of its own, two at a time, and lands in examples/campaign/out/gains/runs/<name>/: its run.toml (the scenario it ran), status.json (status, stop, wall time, the hash of every record file), its log and its records. runs.csv lists them all. Stop it halfway with Ctrl-C and run the same command again: what is done is skipped. Any run reruns alone:

taktwerk run examples/campaign/project.toml --speed max --no-connectors \
  --scenario examples/campaign/out/gains/runs/nominal-g08/run.toml

5. The analysis

analyze.py reads the campaign with the Python package and ranks the runs of each case by the integral of the absolute level error after the disturbance step, next to the largest error after the step and around the frozen sensor:

uv run --with taktwerk python examples/campaign/analyze.py examples/campaign/out/gains

The strongest integral action rejects the step best and is worst while the sensor is frozen: it integrates an error that no longer changes. The sweep shows the trade-off in one table; a [sample] axis would add plant uncertainty to it, replicates other noise draws.
