taktwerk

Recording

A [[recorder]] keeps a lossless, per-tick history of selected signals, taken by the engine itself. OPC UA subscriptions sample and can miss ticks; a recorder sees every tick it is asked for. The cycle thread only copies the selected values into a preallocated ring buffer: no allocation, lock, I/O or wait. Everything else (files, compression, counters, remote pulls) happens on other threads, and a sink that falls behind loses rows instead of slowing the cycle.

[[recorder]]
id = "main"
signals = ["plant.*", "ctrl.u[*]", "ctrl.qp_flag"]
every = 1
sink = "file"
dir = "records"

Every key is in the project file reference.

cycle thread --copy, never waits--> ring (buffer_s) --drain thread--> run files      (sink = "file")
                                         |
                                         +--read_rows over OPC UA--> taktwerk record --> run files

Two sinks

  • sink = "file" (the default): on an edge PC or a workstation. A drain thread per recorder writes gzipped CSV parts to the engine’s own disk (or a mounted stick). The ring is the drain’s slack.
  • sink = "buffer": on a PLC-class device with little RAM and flash. The engine keeps the last buffer_s seconds in RAM and writes nothing. taktwerk record on an edge PC beside it pulls the rows over OPC UA and writes the same files a file sink writes.

Both sinks serve their ring to pulls, so a file sink can be pulled as well.

What a row holds

One row every every ticks, at the ticks divisible by every: row n holds cycle n · every. Skipped ticks are recorded too (a stale input skips a tick; the row then holds the held outputs and taktwerk.status is 2). So consecutive rows always differ by exactly every cycles; any other jump is a loss.

A row is what the cycle holds after the tick is stored: outputs, composed inputs, system signals, and inputs and tunables bound whole to an instance, an input or tunable as the instance stepping most often holds it. A recorder with @io or @inputs takes every external input from the image instead, as its writer left it at the start of the tick.

Selecting signals

signals lists patterns over signal names, in column order; a signal matched twice is recorded once.

  • * matches any run of characters, dots included; ? matches one character.
  • A trailing [*] takes every element of a one-dimensional signal, [i] element i (from 0). Without a selector an array is recorded whole.
  • An empty list (the default) records every output.
  • Each array element is one column, name[i], or name[i,j] with logical indices for a matrix. A text signal is one column.
  • "@io" takes the engine’s I/O interface in its place, "@inputs" and "@outputs" one half of it each.
  • A pattern that matches nothing recordable is an error. An external signal read only element by element (a source of a composed input) is not held whole: a pattern skips it and its exact name is refused, unless the recorder has @io or @inputs. Without either, record the composed input <instance>.<input> instead.

The I/O interface

"@io" in signals records every signal the engine exchanges with the outside, in its place in the column order:

  • "@inputs": every external input, as its writer (a connector, or a scenario’s set or ramp) left it in the image at the start of the tick, whatever its age: also one the instances read only element by element, and one an instance with a longer period holds between its steps;
  • then "@outputs": every model output, then <prefix>.heartbeat and <prefix>.status.

Every output can be read by an OPC UA or HTTP client, so @io takes them all; a model with many outputs (matrices, diagnostics, text) makes wide rows. @inputs with the outputs a consumer actually reads keeps a per-tick recorder narrow.

Each group is in signal order, the order in which the project’s instances (and their models’ variables) first use the signals, so the columns stay the same from run to run of a project. Connectors play no part: --no-connectors and --http record the same columns. Composed inputs are left out, since their sources are recorded; tunables are no columns, events.csv holds their values.

In a recorder with @io or @inputs, every external input is taken as written, also one another pattern names. A scenario fault applies where a reader copies the input, so it shows in the composed input and the outputs, not in the input’s own column.

A per-tick recorder in RAM, pulled by taktwerk record on an edge PC, pairs well with a decimated copy of everything on the device’s own disk, for when the edge PC is away longer than buffer_s:

[[recorder]]
id = "io"                      # every tick, pulled: taktwerk record ... --recorder io
signals = ["@inputs", "ctrl.u[*]", "ctrl.status", "taktwerk.heartbeat", "taktwerk.status"]
sink = "buffer"
buffer_s = 3600                # the edge PC may be away an hour without a gap

[[recorder]]
id = "local"                   # every 10th tick on the device's disk
signals = ["@io"]
every = 10
rotate = { size_mb = 4, hours = 24 }
retain = { max_gb = 0.03 }     # 30 MB of the device's flash

Run files

Every run of a recorder is a directory <dir>/<project>/<recorder>/<run-id>/ with run.json, gzipped CSV parts, events.csv, SHA256SUMS and, once closed, CLOSED. A run opens when the engine starts and closes when it stops; every start is a new run. A local sink and taktwerk record write the same files. The layout and every field are specified in Run record format.

Rotation and retention

A part closes, and the next one opens, when its compressed size reaches rotate.size_mb or it covers rotate.hours of engine time, whichever comes first. Rotation counts engine time, not wall time, so the same rows always split into the same parts.

Retention runs when a run opens and at every rotation, over all runs of one recorder (<dir>/<project>/<recorder>/). It deletes closed parts, oldest first, while the recorder’s parts together exceed retain.max_gb, and every closed part older than retain.days (by its modification time). The open part is never deleted, an .open part another run left behind is; run.json, events.csv and SHA256SUMS are kept, so a deleted part’s line stays in SHA256SUMS (check with sha256sum -c --ignore-missing).

Decimation and several recorders

every = 10 keeps one row per 10 ticks. A project may have several recorders, each with its own signals, every, sink and ring, for example a per-tick one for a few signals and a decimated one for everything. Their ids keep their directories, counters and pull nodes apart.

Counters

Each recorder publishes system signals under <prefix>.recorder.<id>. (<prefix> is engine.system_prefix, default taktwerk), about once a second, on the OPC UA server and in the TUI:

signaltypemeaning
rows_writtenu64rows written to parts; for a buffer sink, rows captured
rows_droppedu64rows the cycle overwrote before the file sink wrote them
gapsu64pulls that asked for rows already overwritten
bytesu64compressed bytes written to parts
partu64number of the open part; 0 for a buffer sink
buffer_fillf64rows not yet written (file) or held (buffer), as a fraction of the ring
oldest_cycleu64cycle of the oldest row in the ring

A recorder may list counters in signals, its own or another’s (e.g. "taktwerk.recorder.*.buffer_fill"); a row holds the value last published, so it changes about once a second.

Sizing the ring

The ring holds buffer_s seconds of engine time: ceil(buffer_s / (tick_s · every)) rows, at least 2. A row takes one 8-byte word per numeric column, one per byte of a text column’s capacity, and two words of its own. taktwerk check prints both per recorder:

  recorder  sink    every  columns  ring rows  ring     dir
  main      file    1      8        60000      4.8 MB   records
  slow      buffer  10     3        600        24.0 kB  -

A ring larger than 4 GiB is refused. For a buffer sink, buffer_s is how long a puller may be away without a gap; for a file sink, how long the disk may stall without a drop.

A per-tick I/O recorder of 60 columns at a 1 s tick takes 3600 rows an hour, (60 + 2) · 8 = 496 bytes each in the ring, so buffer_s = 3600 holds an hour in 1.8 MB. A part takes far less per row, since gzip packs values that change little; how much depends on the signals. In one 42-hour simulated run of a closed loop with noisy plant readings, 44 numeric columns took 106 bytes a row, and 298 columns, most of them constant, 174 bytes. Measure it on a simulated run of the project (taktwerk run --speed max --cycles 86400, then the size of its parts) before sizing rotate and retain for a device’s flash.

Gaps and drops

Both show as a jump in the cycle numbers of a run, larger than every. They differ in where the rows were lost:

  • Dropped: the engine’s own file sink fell more than a ring behind the cycle (a stalled or slow disk). Counted in rows_dropped, logged as a dropped event with the cycles lost. Raise buffer_s, record fewer signals or a larger every, or use a faster disk.
  • Gap: a puller asked for rows the ring had already overwritten (the puller stopped or the network was down for longer than buffer_s). Counted in the engine’s gaps, logged as a gap event in the puller’s events.csv. Raise buffer_s on the engine.

A skipped tick is neither: its row is there, with taktwerk.status 2.

Reading a run

The standard library is enough: gzip and csv over every part in order, json for run.json. Every value arrives as a string; float() reads the float columns, NaN and inf included. This script is examples/recording/read_run.py:

"""Read one recorded run with the Python standard library alone.

Usage: python3 read_run.py <run-dir>
"""

import csv
import gzip
import json
import sys
from pathlib import Path


def rows(run: Path):
    """Yield every row of the run as a dict, parts in order, header lines skipped."""
    # Closed parts, then the open one of a running engine (`.open`, renamed when closed).
    parts = [*run.glob("part-*.csv.gz"), *run.glob("part-*.csv.gz.open")]
    for part in sorted(parts):
        with gzip.open(part, "rt", newline="") as f:
            try:
                yield from csv.DictReader(f)
            except EOFError:
                pass  # the open part of a running engine ends at its last flush


def main() -> None:
    run = Path(sys.argv[1])
    meta = json.loads((run / "run.json").read_text())
    every = meta["every"]
    n, gaps, last, prev = 0, 0, None, None
    for row in rows(run):
        cycle = int(row["cycle"])
        if prev is not None and cycle != prev + every:
            gaps += 1  # rows lost between prev and cycle
        prev, last, n = cycle, row, n + 1
    print(
        f"{meta['project']}/{meta['recorder']}: {n} rows, tick {meta['tick_s']} s, "
        f"every {every}, {gaps} gaps"
    )
    print("last row:", last)
    with open(run / "events.csv", newline="") as f:
        for e in csv.DictReader(f):
            print(f"event {e['cycle']} {e['kind']} {e['source']}: {e['detail']}")


if __name__ == "__main__":
    main()

A run still recording, or one cut off by SIGKILL or a crash, has an open part (part-NNNN.csv.gz.open) that ends at its last flush, without the gzip trailer, and an events.csv that may end in half a line. The Python package and taktwerk serve read such a run up to its last complete line; they ignore temporary files (*.tmp).

Syncing to an object store

taktwerk uploads nothing; any sync tool copies a record directory to an S3-compatible store. Closed parts never change, so a tool that compares size and modification time uploads each once. While a run records, exclude the open part and temporary files; events.csv, run.json and SHA256SUMS still change and are uploaded again until the run is closed.

# rclone, a remote `store` from `rclone config`
rclone copy /data/records store:records --exclude '*.open' --exclude '*.tmp'

# the AWS CLI, or any S3-compatible endpoint with --endpoint-url
aws s3 sync /data/records s3://records --exclude '*.open' --exclude '*.tmp'
  • Copy, do not mirror deletions (rclone copy, aws s3 sync without --delete): retention deletes closed parts locally, and the store keeps them.
  • Run it from cron or a timer; a run is complete in the store once its CLOSED is there and sha256sum -c --ignore-missing SHA256SUMS passes in a copy of it.
  • A run cut off by a kill never gets CLOSED; its .open part stays local, the rows up to the last closed part are in the store.

Reproducible runs

taktwerk run --cycles N stops the engine after N ticks with a stop event cycle limit reached, at any speed; --speed max runs it unpaced and loses no row. Two runs of a deterministic project (no external inputs, no edits while it runs) give byte-identical parts and the same events.csv; run.json differs in run_id, engine_run and the UTC fields. taktwerk.overruns counts missed deadlines, which depend on the machine’s load; leave it out of signals when parts must match.

taktwerk run examples/recording/project.toml --cycles 200 --speed max --no-connectors

Remote recording

taktwerk record pulls the recorders of a running engine over OPC UA, over one connection, and writes the run files on the host it runs on, until SIGINT, SIGTERM or SIGHUP. Run it on an edge PC beside a PLC-class device that records with sink = "buffer":

taktwerk record opc.tcp://10.0.0.2:4840 --dir /data/records --recorder main
  • Without --recorder it pulls every recorder of the engine, each into its own <dir>/<project>/<recorder>/ runs; --recorder (repeatable) picks some. --namespace and --prefix match the server’s namespace and the engine’s system_prefix when they are not the defaults.
  • It starts with the oldest row the engine still holds and opens the run at the first row it gets: source in run.json is the endpoint, start.utc the puller host’s clock.
  • It pulls a recorder again at once while its batches come back full, else after a tenth of the smallest buffer_s pulled (at most 1 s). It stays lossless while it is never away longer than buffer_s.
  • A jump in the cycle numbers is written as a gap event, and so are engine events that left the engine’s log before they were pulled.
  • Events are pulled from the oldest the engine’s log (its newest 65 536) still holds, so a run opened after the engine started still gets the tunables’ start lines.
  • When the engine stops, its server stays up (at most 5 s) until every recorder pulled during the run has its last rows and events; the puller writes the stop event, the rows up to the last tick, and closes the run.
  • A lost connection is retried. When the engine restarted (engine_run changed), the run is closed and the next one opened. If its end had not been pulled (no stop event, or rows after it), a gap event cycles from <n> not pulled: … is its last event and run.json’s end says truncated: true: the rows from cycle n to the engine’s last tick are lost.
  • Its parts are written the same way as a local sink’s, so the same rows give the same bytes.

An integrator writing a puller of their own uses the pull interface.
