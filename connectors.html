taktwerk

Connectors

A connector syncs part of the process image with the outside. At init the engine builds each connector from its [[connector]] table, asks it for "from-server" lengths, builds the image and lets each connector verify its mapping (fail-closed). While running, connectors work on their own I/O threads; the cycle thread never waits for them.

Four kinds exist: the engine’s own OPC UA server, an OPC UA client and, in a build with the http feature, a REST client and an HTTP API.

OPC UA server

kind = "opcua-server" exposes every signal of the image, the engine’s own signals included.

[[connector]]
id = "ua"
kind = "opcua-server"
endpoint = "opc.tcp://0.0.0.0:4840"
namespace = "urn:taktwerk"
security = ["none"]
policies = ["basic256sha256"]
anonymous = true
anonymous_write = true
users = [
  { user = "op", password_env = "UA_PASSWORD" },
  { user = "view", password_file = "/etc/taktwerk/view.pw", write = false },
]
pki_dir = "./pki"
trust_client_certs = false

  • Endpoints: "none" is one endpoint; "sign" and "sign-encrypt" are one per policy.
  • Certificates: the server certificate and key (own/cert.der, private/private.pem) are generated in pki_dir when a secure endpoint or a user needs them. A client certificate is refused into <pki_dir>/rejected/ until moved to <pki_dir>/trusted/, unless trust_client_certs is set.
  • Passwords come from an environment variable (password_env) or a file (password_file, one trailing line break dropped; relative to the working directory like pki_dir), never from the project file. They are read at start. On a "none" endpoint the client encrypts the password with the server certificate (Basic256Sha256), so it never travels in clear; the values themselves do.
  • Write access: a user with write = false, or an anonymous session with anonymous_write = false, sees inputs and tunables read-only (their UserAccessLevel) and a write is refused with BadUserAccessDenied. Reads and recorder pulls are open to every accepted identity. Outputs and system signals are read-only for everyone.

The server is open by default: anonymous, writable, no encryption, all interfaces. On any network other than a closed machine network, bind it to one interface, turn off anonymous (or anonymous_write), add users and offer only secure endpoints. taktwerk tui and taktwerk record connect to such a server with --security, --policy, --user and the password in TAKTWERK_UA_PASSWORD.

Nodes

  • Every signal is a variable node with NodeId ns=<index of namespace>;s=<signal name>, for example ns=2;s=plant.y (the index is assigned by the server; read it from the server’s namespace array, or address the node by URI as nsu=urn:taktwerk;s=plant.y).
  • The browse path splits the name on . into folders under Objects: plant.y is Objects/plant/y, taktwerk.heartbeat is Objects/taktwerk/heartbeat.
  • Data types: f64 Double, f32 Float, i64 Int64, i32 Int32, i16 Int16, i8 SByte, u64 UInt64, u32 UInt32, u16 UInt16, u8 Byte, bool Boolean.
  • A scalar has ValueRank −1. An array has its rank and ArrayDimensions; matrix elements are sent in row-major order whatever the model’s storage layout.
  • A text signal is a scalar String node. A read gives the bytes up to the first NUL, decoded as UTF-8 (invalid sequences are replaced, not refused). A write takes a String of at most capacity − 1 UTF-8 bytes, copies it and zero-fills the rest; a longer one is refused with BadOutOfRange and one containing NUL with BadInvalidArgument, never truncated.
  • Outputs and system signals are read-only. Inputs and tunables are writable; a write goes to the image and is picked up at the next tick.
  • Every node follows each published tick, with the time the value was written into the image as its source timestamp. A value never written has status UncertainInitialValue.

Map

Each key is a signal of the image; each value a NodeId: ns=<index>;s=<id>, nsu=<uri>;s=<id> (the namespace is resolved by URI on every session), or the i=, g=, b= forms. Unmapped signals are not synced.

  • Inputs and tunables are read from their nodes, one bulk Read every sync_period_ms.
  • Tunables with sync = true are synced both ways in the same period.
  • Outputs and system signals are written to theirs, one bulk Write per published tick.
  • An entry with mirror = true is written whatever the signal’s direction and never read: an input another connector writes, or a tunable, shown on the peer (taktwerk plc-mirror generates such a map).

Every Read and Write, the verification reads included, is split into requests of at most max_nodes_per_request nodes and at most the server’s advertised MaxNodesPerRead and MaxNodesPerWrite (read at every session; 0 or unreadable means none). Set the key for a server that refuses large requests without advertising its limit.

Conversion and checks

A map entry may be a table instead of a NodeId string:

[connector.map]
"plant.y" = { node = "ns=4;s=Plant.y", scale = 0.01, offset = 0.0, min = 0.0, max = 1.0, max_unchanged_s = 60 }
"mpc.u" = { node = "ns=4;s=Plant.u", min = 0.0, max = 100.0 }
"mpc.cost" = { node = "ns=4;s=Plant.cost", gated = false }
keydefaultmeaning
noderequiredthe NodeId
scale, offset1, 0signal value = node value · scale + offset; f64 and f32 signals only
min, maxnonevalid signal values; numeric signals, not bool or text
max_unchanged_snoneinputs and tunables: a node value unchanged for longer is invalid
gatedtrue with a gateoutputs: whether the write gate holds it
mirrorfalsewrite the signal, whatever its direction, and never read it
syncfalsetunables: sync both ways instead of reading
clampfalsewritten signals with a range, f64 and f32: a finite value outside it is clamped onto min or max
  • An input is converted after the read, element by element: value = raw · scale + offset. An output is converted back before the write: raw = (value − offset) / scale. min and max bound the signal value, in the engine’s units, on both sides.
  • An array is converted and checked element by element; one invalid element makes the whole value invalid.
  • With a range, NaN and infinities are invalid.
  • An invalid input (out of range, or unchanged for longer than max_unchanged_s, compared bit for bit) is not written to the image: it ages and turns stale by its max_age_ms, as after a bad read. The problem is logged once until it clears.
  • An invalid gated output closes the gate. An invalid output without a gate, or with gated = false, is not written: the node holds its last value, the problem is logged once. Nothing is clamped unless the entry says clamp = true: then a finite value outside the range goes out as the nearer bound (a round-off below 0 as 0), and NaN and infinities stay invalid.

Verification

Every session is verified before it syncs: the first at init, every reconnect again. For each mapped node the client reads DataType, ValueRank, ArrayDimensions, AccessLevel and the value, and refuses the session listing every mismatch:

  • the node exists and its DataType is the signal’s type (String for a text signal); a vendor-defined DataType (a PLC’s STRING(n), say) counts as the built-in type it subtypes, followed along HasSubtype up to 8 levels, once per type and session;
  • a scalar signal maps to a scalar node, an array signal to an array node with the same element count (from ArrayDimensions, or the current value when the server reports none);
  • the node is readable, and writable when the engine writes it (outputs, system signals, mirrored and synced signals) and writes = "on";
  • the sync_epoch node is a UInt32 scalar, readable and writable.

A text signal maps to a scalar String node, typically a PLC STRING(n), and follows the server’s rules: a remote string longer than capacity − 1 bytes is not read into the image (the input ages, the problem is logged), and the PLC refuses an output longer than its own n. Array elements travel in the signal’s storage order. At init a refusal, or an unreachable server, stops the engine before the first tick. After a reconnect a refusal is logged and retried with backoff.

Dry run

A client whose map writes any node (an output, a system signal, a mirrored or synced signal) needs writes: without it check and run refuse the project, so no connector starts writing to a plant, or stops, without the project saying so.

  • writes = "on" writes.
  • writes = "dry-run" writes nothing: inputs and plain tunables are read as usual, the gate is evaluated, and at most once a second the client logs what it would write (dry run, not written: plant.u (ns=4;s=Plant.u) = 0.25, …). Synced tunables are idle, so no peer value is forwarded that the engine never seeded. Writability is not verified.

taktwerk run --write plc turns a dry-run connector’s writes on for one run (recorded in run.json); taktwerk check --live --write plc verifies writability as that run would. The workflow on a plant: check --live, run with writes = "dry-run" and read the log, then check --live --write plc and run --write plc, or set writes = "on".

Tunable sync

A tunable an operator edits on the server, typically a PLC program’s variable, with the engine’s value in force always shown there:

[[connector]]
id = "plc"
kind = "opcua-client"
endpoint = "opc.tcp://192.168.0.10:4840"
sync_epoch = "ns=4;s=Plant.sync_epoch"   # UInt32, the program leaves it alone

[connector.map]
"pi.r" = { node = "ns=4;s=Plant.r", min = 0, max = 80, sync = true }

Each sync_period_ms the client reads every synced node and the epoch, compares each node with the value it last synced (L, bit for bit, before scale and offset) and with the tunable in the image:

  • Seed: no L yet: the node gets the tunable’s value.
  • Forward: the node changed: an operator wrote it. The value is converted and checked like a read input and written into the image as a tunable write by the connector (events.csv: <old> -> <new> by plc). A value out of min/max, or not finite with a range, is refused (refused <value> by plc: <reason>) and the node is overwritten with the value in force in the next period.
  • Follow: the tunable changed elsewhere (another connector, a scenario): the node gets it. Both changed: the operator wins.

Every new session, and every period the epoch reads back other than the one last written, seeds every synced node instead of forwarding it, and writes a new nonzero epoch in the same Write; the epoch counts once that write succeeded. So a program that restarted or was re-initialised (its variables back at their initial values) is seeded with the values in force, never read back into the engine. An unreadable epoch, or a node that cannot be read, holds the routes. Syncing starts once the engine published its first tick, when every tunable holds its start value. The write gate does not apply: tunables stay editable while outputs are held. max_unchanged_s does not apply to a synced tunable.

Write gate

A gate table holds the connector’s outputs while something is wrong, so the PLC keeps its last values instead of taking bad ones:

[connector.gate]
open_after = 5                                  # good ticks in a row before writes resume
conditions = [
  { signal = "mpc.status", mask = 13 },         # closed while mpc.status & 13 != 0
  { signal = "plant.mode", min = 1, max = 1 },  # closed while not finite or outside [1, 1]
]

The gate is evaluated once per published tick the connector writes. It is good when

  • the engine status is running and the heartbeat advanced since the last tick (a skipped tick, a stopped engine or a repeated tick is bad);
  • no condition holds: mask on an integer or bool scalar, min/max on a numeric scalar;
  • every gated output is finite and within its mapping’s min and max.

One bad tick closes it; it opens after open_after (default 1) good ticks in a row. It starts closed and closes when the session is lost. While it is closed no gated output is written, so the PLC holds their last values; system signals (taktwerk.heartbeat, taktwerk.status) are always written, so the PLC sees the engine and owns the safe state.

With a gate, every output is gated unless its map entry says gated = false: an output added to the map later is safe by default. Without a gate nothing is held.

Each change is an event (gate: open or closed: <reason>), and the gate publishes system signals under <prefix>.connector.<id>.:

signaltypemeaning
gate_openboolwhether gated outputs are written
gate_opensu64times the gate opened
gate_closesu64times the gate closed
gate_heldu64published ticks whose gated outputs were not written

Reconnect and staleness

A lost session is closed and reconnected with exponential backoff. While disconnected, inputs are not written, so they age; with a max_age_ms the engine turns them stale and skips ticks until reads resume. An input read with a bad status, or a value that does not fit the signal, leaves that signal aging as well; the problem is logged once until it clears.

Stamp

stamp = "receive" stamps an input with the time the read response arrived: an input is as fresh as the last successful read. stamp = "source" uses the server’s source timestamp (or the receive time when it sends none). Servers that stamp a value only when it changes make a constant input look old under "source".

from-server

For an instance dimension bound "from-server", the client answers with the length of the node mapped to the dimension’s signal (its ArrayDimensions, else its current value’s length). taktwerk check contacts no server, so a project with such a dimension checks with check --live.

REST

kind = "rest" (feature http) syncs mapped signals with a server’s JSON API over plain HTTP/1.1: each mapping names its own path and picks its value by JSON pointer.

[[connector]]
id = "lab"
kind = "rest"
base_url = "http://10.0.0.20:8080/api/v1/"
auth = { scheme = "basic", user = "op", password_env = "LAB_PASSWORD" }
request_timeout_ms = 1000
reconnect_backoff_ms = 1000
period_ms = 1000
refresh_s = 60
writes = "on"                                    # or "dry-run"; required, the map writes

[connector.gate]
open_after = 3
conditions = [{ signal = "mpc.status", mask = 7 }]

[connector.map]
"plant.temp" = { get = "lines/1/values", pointer = "/data/temp", min = 0, max = 150, max_unchanged_s = 600 }
"plant.flow" = { get = "lines/1/values", pointer = "/data/flow", scale = 60 }
"mpc.feed" = { put = "setpoints/feed", pointer = "/value", body = { unit = "l/h" }, min = 0, max = 2, clamp = true }
"mpc.u[1]" = { put = "setpoints/air", pointer = "/value", scale = 60, min = 60, max = 300 }
"taktwerk.heartbeat" = { put = "setpoints/watchdog", pointer = "/value" }

Map entries

keydefaultmeaning
getinputs and tunables: the path whose answer holds the value
put, post, patchoutputs and system signals: the path the value is sent to
pointer""JSON pointer (RFC 6901) to the value in the answer, or in the body; empty is the whole document

Each entry sets exactly one of get, put, post and patch. A path starting with / is taken from the server’s root, any other below base_url; a query string is part of the path.

  • Reads: every period_ms, one GET per distinct path; every mapping of that path picks its value from the one answer, so a bulk endpoint serves many signals with one request. An input is stamped when the answer arrived, so with a max_age_ms it turns stale when reads stop. A number, a numeric string, true/false for a bool, an array of the signal’s length, a string for text. A value that is missing, null, of another form, or rejected by the mapping is not written: the signal ages, the problem is logged once until it clears.
  • Writes: on a published tick, at most once per period_ms, one request per output whose value changed since its last successful write (or, with refresh_s, was written that long ago). The value goes into a copy of body at pointer (missing objects are created), as JSON: a number, a bool, a flat array in storage order, or a string for text. A non-finite value is never sent. A 2xx answer is success; any other status is logged and the value is sent again at the next round.
  • Elements: name[i] sends element i of a one-dimensional output or system signal as a scalar, with its own path, conversion, range and gate, so one array of set points goes to one path per actuator. Signals the engine reads map whole.
  • Gate: evaluated once per round of writes. While it is closed no gated output is sent; when it opens every gated output is sent again.
  • Dry run: writes = "dry-run" reads as usual, evaluates the gate and sends nothing, the heartbeat included; at most once a second it logs what it would send. run --write <id> turns the sends on for one run.

At init the connector reads every GET path once and refuses the bind listing every mapping whose pointer finds nothing or whose value does not fit its signal; null passes (no value yet). Writes cannot be checked without writing: only their direction and settings are. An unreachable server stops the engine before the first tick. For a dimension bound "from-server" the connector answers with the length of the array at the mapping’s pointer.

Auth

Secrets come from the environment:

auth = { scheme = "basic", user = "op", password_env = "LAB_PASSWORD" }
auth = { scheme = "bearer", token_env = "LAB_TOKEN" }
auth = { scheme = "header", name = "X-Api-Key", value_env = "LAB_KEY" }
auth = { scheme = "login", path = "auth/login", body = { user = "op", password = "${LAB_PASSWORD}" }, token = "/access_token" }

basic takes the password from password_env or password_file (exactly one; an inline password is refused). login sends POST <path> with the JSON body (${NAME} in a string is replaced by the variable) and uses the string at the token pointer of the answer as a bearer token; a request answered 401 logs in again and is sent once more. A failed login is retried after period_ms. On a device the variables go into the bundle’s env file.

Transport

Plain HTTP/1.1 on one keep-alive connection; https:// is refused (put a TLS proxy beside the engine for a server that requires it). A request the connection gave back unsent is sent again on a new connection; a GET that broke on a reused connection is sent once more; a write that went out is never repeated. A request that gets no answer within its timeout marks the server lost: the gate closes, inputs age, and the connector retries with backoff. Answers over 4 MiB are refused. The connector works in wall time and is refused off real time.

Boundary

The connector maps fixed paths to signals. What a plant data system’s API needs beyond that stays a companion process of the bundle: ids looked up at run time (a variable’s id by its name, the running batch or process), paths that change during a run, reads that need several dependent requests, sessions other than a token from one login, set point ramps, rate limits and deadbands, TLS. The companion talks to the plant system on one side and to the engine on the other, through the OPC UA server or a rest connector pointed at itself.

HTTP API

A build with the http feature (cargo install taktwerk --features ui for the web UI too) adds the http connector: the engine’s signals, values and events as JSON and server-sent events, and the web UI. taktwerk run --http 127.0.0.1:8480 adds one to any project, also with --no-connectors.

[[connector]]
id = "web"
kind = "http"
listen = "127.0.0.1:8480"   # the default; loopback only
rate_hz = 10.0              # samples per second at most, 0.1 to 50
writes = false              # true accepts writes and stop, with the token
# token_file = "/run/taktwerk/web.token"
Endpoint
GET /api/infoconnector id, version, rate, whether writes are on; with a recorder recording: run id, tick, start time, recorders
GET /api/signalsevery signal: id, name, direction, type, shape, unit, max age
GET /api/values?signals=a,bthe latest sample: cycle, wall time (t_ms), values, ages
GET /api/stream?signals=a,bthe same as server-sent events sample
GET /api/events?after=Nthe event log from sequence number N and head, the next number (with a recorder)
POST /api/write{"signal": "pi.kp", "value": 2.5}: an input or tunable
POST /api/stopends the run as SIGTERM does

Values are JSON numbers (a bool as true/false), arrays flat in storage order, text as strings; NaN and infinities are null. Signals not named come in layout order. An age counts the engine’s clock, as an input’s max_age_ms does: wall time in real time, engine time under --speed.

The connector never waits on the cycle: one task reads every signal at most rate_hz times a second, and only while a stream is open or a request came in the last two seconds; every request and stream is answered from that sample.

Measured on a Raspberry Pi 5 shared with other jobs, SCHED_OTHER (no real-time priority), raw-pi at a 1 ms tick, 30 000 ticks twice per setup; wake-up lateness after the deadline:

Reading needs no credentials, like the OPC UA server’s anonymous default. Writes and stop need writes = true and Authorization: Bearer <token>. The token is TAKTWERK_HTTP_TOKEN when set, else a fresh one written to token_file (default $XDG_RUNTIME_DIR/taktwerk/http-<port>.token, mode 0600) and removed at shutdown. There is no TLS: keep listen on loopback, or on a network you trust. On loopback a request is refused (403) unless its Host is a loopback address or localhost and no browser marks it cross-site (Sec-Fetch-Site), against DNS rebinding.
