taktwerk

Connectors

A connector syncs part of the process image with the outside. At init the engine builds each connector from its [[connector]] table, asks it for "from-server" lengths, builds the image and lets each connector verify its mapping (fail-closed). While running, connectors work on their own I/O threads; the cycle thread never waits for them.

Three kinds exist: the engine’s own OPC UA server, an OPC UA client and, in a build with the http feature, an HTTP API.

OPC UA server

kind = "opcua-server" exposes every signal of the image, the engine’s own signals included.

[[connector]]
id = "ua"
kind = "opcua-server"
endpoint = "opc.tcp://0.0.0.0:4840"
namespace = "urn:taktwerk"
security = ["none"]
anonymous = true
users = [{ user = "op", password_env = "UA_PASSWORD" }]
pki_dir = "./pki"
trust_client_certs = false

"sign" and "sign-encrypt" use the Basic256Sha256 policy. The server certificate is generated in pki_dir when a secure endpoint needs one. A user’s password comes from exactly one of password (inline) and password_env (the name of an environment variable); prefer password_env so no secret sits in the project file.

The server is open by default: anonymous, no encryption, all interfaces. On any network other than a closed machine network, bind it to one interface, turn off anonymous, add users and offer only secure endpoints.

Nodes

  • Every signal is a variable node with NodeId ns=<index of namespace>;s=<signal name>, for example ns=2;s=plant.y (the index is assigned by the server; read it from the server’s namespace array, or address the node by URI as nsu=urn:taktwerk;s=plant.y).
  • The browse path splits the name on . into folders under Objects: plant.y is Objects/plant/y, taktwerk.heartbeat is Objects/taktwerk/heartbeat.
  • Data types: f64 Double, f32 Float, i64 Int64, i32 Int32, i16 Int16, i8 SByte, u64 UInt64, u32 UInt32, u16 UInt16, u8 Byte, bool Boolean.
  • A scalar has ValueRank −1. An array has its rank and ArrayDimensions; matrix elements are sent in row-major order whatever the model’s storage layout.
  • A text signal is a scalar String node. A read gives the bytes up to the first NUL, decoded as UTF-8 (invalid sequences are replaced, not refused). A write takes a String of at most capacity − 1 UTF-8 bytes, copies it and zero-fills the rest; a longer one is refused with BadOutOfRange and one containing NUL with BadInvalidArgument, never truncated.
  • Outputs and system signals are read-only. Inputs and tunables are writable; a write goes to the image and is picked up at the next tick.
  • Every node follows each published tick, with the time the value was written into the image as its source timestamp. A value never written has status UncertainInitialValue.

Map

Each key is a signal of the image; each value a NodeId: ns=<index>;s=<id>, nsu=<uri>;s=<id> (the namespace is resolved by URI on every session), or the i=, g=, b= forms. Unmapped signals are not synced.

  • Inputs and tunables are read from their nodes, one bulk Read every sync_period_ms.
  • Outputs and system signals are written to theirs, one bulk Write per published tick.

Every Read and Write, the verification reads included, is split into requests of at most max_nodes_per_request nodes and at most the server’s advertised MaxNodesPerRead and MaxNodesPerWrite (read at every session; 0 or unreadable means none). Set the key for a server that refuses large requests without advertising its limit.

Conversion and checks

A map entry may be a table instead of a NodeId string:

[connector.map]
"plant.y" = { node = "ns=4;s=Plant.y", scale = 0.01, offset = 0.0, min = 0.0, max = 1.0, max_unchanged_s = 60 }
"mpc.u" = { node = "ns=4;s=Plant.u", min = 0.0, max = 100.0 }
"mpc.cost" = { node = "ns=4;s=Plant.cost", gated = false }
keydefaultmeaning
noderequiredthe NodeId
scale, offset1, 0signal value = node value · scale + offset; f64 and f32 signals only
min, maxnonevalid signal values; numeric signals, not bool or text
max_unchanged_snoneinputs and tunables: a node value unchanged for longer is invalid
gatedtrue with a gateoutputs: whether the write gate holds it
  • An input is converted after the read, element by element: value = raw · scale + offset. An output is converted back before the write: raw = (value − offset) / scale. min and max bound the signal value, in the engine’s units, on both sides.
  • An array is converted and checked element by element; one invalid element makes the whole value invalid.
  • With a range, NaN and infinities are invalid.
  • An invalid input (out of range, or unchanged for longer than max_unchanged_s, compared bit for bit) is not written to the image: it ages and turns stale by its max_age_ms, as after a bad read. The problem is logged once until it clears.
  • An invalid gated output closes the gate. An invalid output without a gate, or with gated = false, is not written: the node holds its last value, the problem is logged once. Nothing is clamped.

Verification

Every session is verified before it syncs: the first at init, every reconnect again. For each mapped node the client reads DataType, ValueRank, ArrayDimensions, AccessLevel and the value, and refuses the session listing every mismatch:

  • the node exists and its DataType is the signal’s type (String for a text signal);
  • a scalar signal maps to a scalar node, an array signal to an array node with the same element count (from ArrayDimensions, or the current value when the server reports none);
  • the node is readable, and writable when the engine writes it.

A text signal maps to a scalar String node, typically a PLC STRING(n), and follows the server’s rules: a remote string longer than capacity − 1 bytes is not read into the image (the input ages, the problem is logged), and the PLC refuses an output longer than its own n. Array elements travel in the signal’s storage order. At init a refusal, or an unreachable server, stops the engine before the first tick. After a reconnect a refusal is logged and retried with backoff.

Write gate

A gate table holds the connector’s outputs while something is wrong, so the PLC keeps its last values instead of taking bad ones:

[connector.gate]
open_after = 5                                  # good ticks in a row before writes resume
conditions = [
  { signal = "mpc.status", mask = 13 },         # closed while mpc.status & 13 != 0
  { signal = "plant.mode", min = 1, max = 1 },  # closed while not finite or outside [1, 1]
]

The gate is evaluated once per published tick the connector writes. It is good when

  • the engine status is running and the heartbeat advanced since the last tick (a skipped tick, a stopped engine or a repeated tick is bad);
  • no condition holds: mask on an integer or bool scalar, min/max on a numeric scalar;
  • every gated output is finite and within its mapping’s min and max.

One bad tick closes it; it opens after open_after (default 1) good ticks in a row. It starts closed and closes when the session is lost. While it is closed no gated output is written, so the PLC holds their last values; system signals (taktwerk.heartbeat, taktwerk.status) are always written, so the PLC sees the engine and owns the safe state.

With a gate, every output is gated unless its map entry says gated = false: an output added to the map later is safe by default. Without a gate nothing is held.

Each change is an event (gate: open or closed: <reason>), and the gate publishes system signals under <prefix>.connector.<id>.:

signaltypemeaning
gate_openboolwhether gated outputs are written
gate_opensu64times the gate opened
gate_closesu64times the gate closed

Reconnect and staleness

A lost session is closed and reconnected with exponential backoff. While disconnected, inputs are not written, so they age; with a max_age_ms the engine turns them stale and skips ticks until reads resume. An input read with a bad status, or a value that does not fit the signal, leaves that signal aging as well; the problem is logged once until it clears.

Stamp

stamp = "receive" stamps an input with the time the read response arrived: an input is as fresh as the last successful read. stamp = "source" uses the server’s source timestamp (or the receive time when it sends none). Servers that stamp a value only when it changes make a constant input look old under "source".

from-server

For an instance dimension bound "from-server", the client answers with the length of the node mapped to the dimension’s signal (its ArrayDimensions, else its current value’s length).

HTTP API

A build with the http feature (cargo install taktwerk --features ui for the web UI too) adds the http connector: the engine’s signals, values and events as JSON and server-sent events, and the web UI. taktwerk run --http 127.0.0.1:8480 adds one to any project, also with --no-connectors.

[[connector]]
id = "web"
kind = "http"
listen = "127.0.0.1:8480"   # the default; loopback only
rate_hz = 10.0              # samples per second at most, 0.1 to 50
writes = false              # true accepts writes and stop, with the token
# token_file = "/run/taktwerk/web.token"
Endpoint
GET /api/infoconnector id, version, rate, whether writes are on
GET /api/signalsevery signal: id, name, direction, type, shape, unit, max age
GET /api/values?signals=a,bthe latest sample: cycle, wall time (t_ms), values, ages
GET /api/stream?signals=a,bthe same as server-sent events sample
GET /api/events?after=Nthe event log from sequence number N (with a recorder)
POST /api/write{"signal": "pi.kp", "value": 2.5}: an input or tunable
POST /api/stopends the run as SIGTERM does

Values are JSON numbers (a bool as true/false), arrays flat in storage order, text as strings; NaN and infinities are null. Signals not named come in layout order. An age counts the engine’s clock, as an input’s max_age_ms does: wall time in real time, engine time under --speed.

The connector never waits on the cycle: one task reads every signal at most rate_hz times a second, and only while a stream is open or a request came in the last two seconds; every request and stream is answered from that sample.

Measured on a Raspberry Pi 5 shared with other jobs, SCHED_OTHER (no real-time priority), raw-pi at a 1 ms tick, 30 000 ticks twice per setup; wake-up lateness after the deadline:

setupload average about 12: mean, maxload average 3 to 7: mean, max
no http connector0.18 to 0.26 ms, 14 to 16 ms0.11 to 0.18 ms, 10 to 14 ms
connector, no client0.16 to 0.20 ms, 12 to 48 ms0.14 to 0.17 ms, 11 to 16 ms

The client also polled /api/values at 20 Hz. The mean does not move; the worst case on the quieter machine grew with a streaming client. A cycle that must not see it runs with [engine.realtime] and leaves the connector off or at a low rate_hz.

Reading needs no credentials, like the OPC UA server’s anonymous default. Writes and stop need writes = true and Authorization: Bearer <token>. The token is TAKTWERK_HTTP_TOKEN when set, else a fresh one written to token_file (default $XDG_RUNTIME_DIR/taktwerk/http-<port>.token, mode 0600) and removed at shutdown. There is no TLS: keep listen on loopback, or on a network you trust.
